Agent 架构中 Skill 和 Tool 到底有啥本质区别？

一句话总论

Tool 解决的是模型「能不能做到」的执行能力；Skill 解决的是模型「知不知道怎么做」的领域经验。 两者不在一个维度上，是深度配合的黄金搭档，不是替代关系。

适用人群

  • ✅ 面试被问到「Skill 和 Tool 区别」的人 — 高频面试题
  • ✅ 零基础想搞懂 Agent 模块划分的人
  • ✅ 已经在用 Claude Code / Codex 但不清楚底层设计的人
  • ❌ 对 Agent 分层架构已经非常熟悉的资深开发者

核心总思路

盯死两件事：

Tool — 模型能不能做到（执行能力）
Skill — 模型知不知道怎么做（领域经验）

一个负责物理执行，一个负责业务经验。

核心概念卡

Tool — 物理执行能力

维度 说明
是什么 模型伸向外部世界的手脚。大模型本身是个被关在黑盒里的囚徒——没手没脚，查不了数据库、发不了邮件、调不了 API
怎么接入 通过 Function Call 或 MCP 这类标准协议接进来
怎么工作 模型看到工具的描述后决定调哪个、参数填啥。但真正去执行的是你后端的代码，执行完把结果喂回给模型
关键特性 有副作用 — 每次调用都在真实改变世界状态（比如扣了一次余额）
核心词 执行动作，改变状态

Skill — 领域经验与规范

维度 说明
是什么 一包打包好的业务 SOP（标准操作流程）和流程知识
物理形态 一个文件夹，里面装着说明文档、脚本模板、参考资料
加载机制 ⭐ 渐进式披露（Progressive Disclosure） — 平时只有名字和一句话描述常驻在 prompt 里，几乎不占空间；只有当模型判断任务相关时，才把完整内容读进上下文
为什么要这样设计 如果把上百个工具说明全塞进上下文，还没干活几万 token 就烧没了，模型直接陷入「上下文迷失」
核心词 经验规范，省 token

方法：面试回答模板

如果面试官问你「Skill 和 Tool 的区别」，按这四步走：

第一句：定维度

「Tool 和 Skill 不是一类东西。Tool 解决能不能做到，Skill 解决知不知道怎么做。」

第二句：讲 Tool

「Tool 是模型自己干不了的真实动作，靠 Function Call 或 MCP 接入，有副作用并返回结果。」

第三句：讲 Skill

「Skill 是打包好的领域经验/SOP，靠渐进式披露按需加载，极致省 token。」

第四句：讲关系

「两者在真实 Agent 里是深度配合的——Tool 给手脚，Skill 教打法，缺一不可。」

💡 一句话总结：Tool 是能动手，Skill 是会动手。

线上实战：两者的黄金搭档

场景 Tool 的角色 Skill 的角色
查账对账 提供查询数据库、拉流水的接口 封装对账流程规范：先校验 A 字段 → 再拉 B 流水 → 出错走 C 兜底
代码审查 提供读文件、搜索代码的接口 封装审查清单：按什么顺序检查、输出格式、常见漏检点
发布上线 提供部署、回滚的脚本执行能力 封装上线 checklist：前置检查 → 灰度比例 → 监控告警阈值

最大的坑

不能分层 — 把所有 SOP 硬塞进系统提示词，导致上下文越堆越长，模型反而抓不住重点。

正确做法：Tool 提供物理能力，Skill 注入肌肉记忆，各司其职。

自测题

  1. Tool 和 Skill 最本质的区别是什么？
  2. 为什么不能把上百个 Tool 的说明全塞进上下文？
  3. 什么是「渐进式披露」？它解决了什么问题？
  4. 为什么说 Tool 调用「有副作用」？
  5. 在代码审查场景中，Tool 和 Skill 分别扮演什么角色？
