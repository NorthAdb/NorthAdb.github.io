一句话总论

AI Agent 岗位正在从“会不会 LangChain、LangGraph、RAG、MCP”转向“能不能把 LLM 的不确定性包进一个可靠的软件系统，并用可观测、可评估的因果闭环证明它有价值”。

面试官不再满足于听技术名词，而会持续追问：

  • 为什么要用这项技术，而不是更简单的 Pipeline、SQL 或脚本？
  • 数据规模、业务约束或失败模式变化后，选型是否仍成立？
  • Agent 出错、越权、循环、成本失控时怎么办？
  • 指标变好真的是 Agent 或 Skill 带来的吗？
  • 当所有候选人都能用 AI 写代码时，谁能设计出更可靠的系统？

一、面试正在考什么：从“是什么”到“为什么”

UP 主早期以为 Agent 面试主要考 RAG、LangChain、LangGraph、Prompt、MCP 等概念，但秋招阶段遇到的问题明显深入：

  • RAG 文档怎么切，为什么这样切？
  • 向量数据库为什么这样选，数据扩大后怎么办？
  • 为什么需要 Multi-Agent，普通 Pipeline 为什么不行？
  • LangGraph 的 State 具体是什么，如何持久化和恢复？
  • Kafka 为什么发生消息堆积，怎样区分生产过快与消费能力不足？
  • 能否在允许使用 AI 的环境里，现场完成系统设计与编码？

简历里的每个名词都要经得住追问

如果简历写了“LangGraph + RAG + Multi-Agent”，面试官真正关心的不是组合听起来是否先进，而是：

  1. 业务复杂度是否真的需要它；
  2. 它解决了哪个不可替代的问题；
  3. 增加的成本、延迟和故障面是否值得；
  4. 如何证明效果来自该设计，而不是其他因素。

回答不出“为什么”，技术栈越华丽，越容易被判断为炫技或过度设计。

二、小红书案例：让 Agent 自动完成性能归因

场景题（约 04:34）

客户端启动到首屏展示之间存在多个埋点阶段。工程师通常会比较不同版本：如果网络阶段退化，就进一步查看网络细粒度指标；如果图片加载变差，就查看图片指标，最终完成 Root Cause Analysis。

问题是：怎样把工程师每天重复执行的分析 Workflow 改造成 Agent？

可拆成“感知—决策—执行—归因”

  1. 感知：通过固定 SQL 或 API 拉取性能数据，执行异常检测；
  2. 决策：判断发生退化的阶段，并选择下一步分析路径；
  3. 执行：调用对应的查询、聚合和诊断工具；
  4. 归因：结合业务知识解释根因，生成报告并发送给工程师。

这个 Agent 不一定需要聊天界面。它可以每天凌晨运行，读取前一天的数据，在发现版本退化后逐层定位，早上将报告发给工程师。企业真正愿意付费的 Agent，往往不是因为“像人聊天”，而是因为它能自动化原本由工程师重复完成的高价值 Workflow。

确定性计算不要交给 LLM（约 06:48）

面试官追加限制：报表数据必须准确，不能因幻觉而失去可信度。

UP 主复盘后提出两层设计：

层 适合承担的工作
Deterministic Layer 固定 SQL/API 查询、Python 聚合、指标计算、参数校验、阈值判断
LLM Reasoning Layer 理解上下文、选择分析路径、结合业务知识归因、生成解释和报告

能由确定性程序完成的步骤，就不应让 LLM 自由发挥。LLM 是系统里更贵、更慢、更不稳定的组件，应只用于其擅长的不确定性推理。

Workflow 与 Agent 不是二选一（约 08:16）

多 Agent 编排存在两个极端：

  • 完全预编排：节点和路径全部写死，稳定可控，但灵活性和自主性弱；
  • 完全动态编排：只给模型目标，规划和执行全部开放，灵活但可能无限循环、成本爆炸或偏离目标。

更现实的生产方案是 Controlled Autonomy（受控自主）：

Workflow 控制核心业务节点和安全边界；Agent 只在局部范围内动态选择工具、检索内容和分析路径。

三、阿里案例：从 RAG 一路追问到 Kafka

1. RAG 文档为什么这样切（约 10:03）

面对车型、故障码和故障类型等章节结构明显的技术手册，固定每 500 Token 切一刀会破坏语义：上一块可能只有故障现象，下一块才是解决办法。

更完整的回答应包含因果链：

  1. 根据标题和章节做 structure-aware chunking；
  2. 对过长 Section 再使用滑动窗口；
  3. Chunk 保留车型、故障码、章节路径等 Metadata；
  4. 这样既保留语义完整性，也支持后续过滤、引用和溯源。

面试不是问“会不会切片”，而是在验证你是否理解文档结构如何影响 Embedding 与召回质量。

2. 向量数据库不存在脱离场景的“最好”（约 11:23）

对于几十份技术手册、数千到数万个 Chunk、内部原型和低频查询，轻量方案可能比重型分布式向量数据库更合理。

只有当系统进入多租户、动态更新、高并发或高可用阶段，才需要重新评估存储。回答选型题时应覆盖：

  • 当前数据量与增长速度；
  • 查询并发和延迟目标；
  • 更新、删除与过滤需求；
  • 多租户、可用性与运维成本；
  • 何种条件出现时会迁移到另一方案。

面试官考的不是你能否背出数据库对比表，而是你是否有阶段性 Trade-off 判断。

3. LangGraph 的核心是具体 State（约 13:41）

如果声称使用 LangGraph，就应能说明：

  • Graph 中有哪些 Node；
  • State 包含哪些真实字段；
  • 每个 Node 读取和更新哪些字段；
  • State 如何持久化、失败后怎样 Resume；
  • 状态结构为什么匹配所选的存储模型。

车辆故障诊断 State 可以包含车辆信息、故障码、检索结果、诊断结论和执行状态。LangGraph 的价值不是“多节点框架”这个标签，而是让状态在节点间以明确规则流转和更新。

4. 什么时候才需要 Multi-Agent（约 15:43）

如果流程永远是 Input → 调用 LLM → Output，本质上只是 Pipeline，硬拆成三个 Agent 反而是过度设计。

Multi-Agent 更合理的条件包括：

  • 不同阶段确实需要完全不同的工具；
  • 各阶段需要不同的 Prompt 和上下文；
  • 路径需要动态分支、失败回退或重新规划；
  • 角色之间存在清晰的责任边界；
  • 拆分后的隔离、并行或专业化收益大于通信成本。

核心回答是：复杂度由业务要求产生，而不是候选人为美化简历主动创造。

5. 为什么 Agent 岗会问 Kafka（约 17:10）

生产 Agent 不会孤立存在：它可能消费 Event、调用多个 Tool、产生任务，再通过消息队列驱动后续 Workflow。流量增长后自然会遇到：

  • 消息堆积与端到端延迟；
  • 消费者 CPU、网络或下游依赖瓶颈；
  • 重复消息、乱序与失败重试；
  • 无法真正做到 Exactly Once 时的幂等设计；
  • 消费组、Partition、Rebalance 与 Offset 管理。

因此数据库、缓存、消息队列、并发、网络和分布式系统并非与 Agent 无关，而是 Agent 生产化的基础。

6. Text-to-SQL 的关键是控制犯错空间（约 18:54）

用户问“帮我查卖得最好的商品”，其中“最好”可能指销量、销售额或利润。数据库场景中猜错就是错误，不能只靠“把 Prompt 写好一点”。

合理策略是：

  1. 高置信且语义明确时执行；
  2. 存在关键歧义时先 Clarification，例如询问“销量最高还是销售额最高”；
  3. 检索 Schema、Metadata、字段描述、表关系和业务口径；
  4. 对重要指标执行结果校验；
  5. 允许系统拒绝高风险或无法确认的请求。

好的 Agent 不是什么问题都回答，而是知道什么时候执行、什么时候澄清、什么时候拒绝。

四、AI Coding 面试：候选人是 Tech Lead，AI 是 Junior Developer

题目形式（约 21:20）

在类似 Cursor 的沙盒中，用约 40 分钟设计并实现一个可扩展、线程安全、逻辑清晰的订单状态机引擎，允许使用 AI。

面试官观察的不是谁最快把整段题目复制给 AI，而是人与 AI 的协作过程：

  1. 自己是否先理解问题：至少建立初步设计框架，而不是放弃思考；
  2. 能否拆分任务：将状态、事件、转移规则、并发控制和测试等模块分步交给 AI；
  3. 能否验证输出：阅读代码、运行测试、检查边界，而不是看见绿色 Diff 就 Accept；
  4. 能否解释 Trade-off：例如 Enum、Metadata 或配置驱动状态定义分别适合什么场景；
  5. 设计决策是否属于候选人：最终代码能否运行不是唯一标准，关键是你能否说明为什么这样设计。

AI Coding 的核心不是“AI 会不会写代码”，而是你能否定义任务、建立约束、审查实现并对结果负责。

五、字节案例：Agent Loop 外围才是生产化复杂度

商业化场景会高度关注正确性、一致性、安全性与可追溯性。即使简历上写了 Agent，也会被大量追问传统后端问题。

“你的 Agent Platform 听起来并不复杂”（约 24:55）

从摘要上看，系统可能只是 Input → Agent 判断 → MCP → Output。真正的生产复杂度隐藏在箭头里：

  • 谁可以调用哪些 Tool？
  • 读权限和写权限是否相同？
  • 参数合法性由谁校验？
  • 高风险操作是否需要二次确认？
  • AI 生成的代码在哪里执行？
  • 超时、资源限制和未授权访问如何处理？
  • State、日志和操作结果怎样追踪与审计？

为什么需要沙盒

AI 生成的 Python 代码不能直接在生产机器运行。应放入隔离沙盒，并设置：

  • CPU、内存、时间和网络限制；
  • 文件系统与凭据隔离；
  • 未授权资源访问直接拒绝；
  • 超时强制终止；
  • 完整执行日志和审计记录。

ReAct Loop 可能几十行代码就能完成，但权限、状态、沙盒、监控、失败恢复和部署容灾，才决定它是 Demo 还是生产系统。

六、币安案例：稀缺的不是搭 Agent，而是证明 Agent 在变好

该部分涉及 Skill 检索、Tool 与 Skill 的区别、版本管理和路由，但更有价值的是评估与因果归因。

方案有效，不等于 Skill 有效（约 28:40）

上线一版方案后指标变好，需要回答：

  • 多久才能获得有统计显著性的 A/B Test 结果？
  • 整体方案改善中，Skill 的贡献有多大？
  • 是 Skill 内容、路由、模型、流量变化，还是其他系统改动带来的？

“成功会摧毁自己的证据”悖论（约 29:08）

新 Skill 上线后，原有 Bad Case 消失，Analyzer 因此再也抓不到它。但 Bad Case 消失可能来自：

  • Skill 真正发挥作用；
  • 用户流量或请求分布变化；
  • 上游产品或代码已自行修复；
  • 监控或采样方式改变。

而错误一旦消失，系统也失去了继续观察该错误的天然证据。可采用：

  1. 保留不使用新 Skill 的 Holdout 流量；
  2. 构造回归测试集，定期重放历史 Bad Case；
  3. 记录 Skill 命中日志、版本与输出轨迹；
  4. 分析 Skill 上线、命中与 Bad Case 消失的时间及实验相关性；
  5. 区分是在优化单条 Trajectory、路由规则，还是 Skill 本身。

搭建 Agent 的能力并不稀缺；稀缺的是证明闭环真的闭上，并且每一环的因果都站得住。

七、AI Agent 岗位的六层能力模型

UP 主将多场面试归纳为六层能力：

层级 核心问题 典型知识
1. 会不会用 LLM 能否稳定获得符合格式的输出？ Prompt、Structured Output、Tool Calling、模型基本能力与边界
2. 能否给 LLM 正确信息 上下文是否准确、充分、低噪声？ RAG、Chunking、Embedding、Retrieval、Rerank、Context Management
3. 能否控制 LLM 行为 如何限制规划和执行的不确定性？ Workflow、State Machine、LangGraph、Multi-Agent、Routing、Planning
4. 能否接入真实世界 Agent 如何读写系统并调用能力？ MCP、API、Database、Kafka、Python、权限与沙盒
5. Agent 犯错怎么办 如何检测、隔离、恢复和防止复发？ Eval、Guardrail、Retry、Fallback、Human-in-the-loop、监控与审计
6. 如何证明 Agent 有价值 效果是否真实、可归因、可持续？ A/B Test、Holdout、回归集、业务指标、成本、因果归因

前四层决定“能不能搭出来”，后两层决定“能不能进入生产并持续存在”。

八、高频追问的回答框架

面对任何技术选型，不要只回答“我用了什么”，而应按下面的链条展开：

场景 → 约束 → 选项 → Trade-off → 失败模式 → 切换条件 → 验证

部分 要回答什么
场景 谁在什么流程中解决什么问题？
约束 数据量、延迟、准确率、成本、权限、更新频率是什么？
选项 Pipeline、Workflow、Agent、数据库或框架有哪些候选？
Trade-off 为什么当前方案最匹配，而不是绝对最好？
失败模式 幻觉、循环、堆积、重复、越权、状态丢失时怎么办？
切换条件 规模或需求出现什么变化时会换方案？
验证 用哪些离线集、在线实验和业务指标证明有效？

例如回答“为什么用 Multi-Agent”时，不应说“因为角色协作更强”，而应明确：单 Pipeline 无法处理哪些动态分支；角色之间有哪些不同工具、上下文和权限；拆分后的收益是否覆盖通信、延迟和调试成本。

九、准备 Agent 面试的实用清单

1. 不要为了 Agent 而 Agent

能用 SQL 解决就用 SQL，能用 Script 解决就用 Script，固定流程能用 Pipeline 就不要强拆 Multi-Agent。LLM 是系统中最贵、最慢、最不稳定的组件之一，不是越多越好。

2. 为每项技术准备替代方案

对简历上的每个选型，都应能回答：

  • 为什么是它，而不是其他方案？
  • 当前规模下为什么合理？
  • 它的主要成本和失败模式是什么？
  • 数据量、流量或一致性要求变化后，什么时候会切换？

3. 传统后端基础不能丢

重点包括：

  • 数据库模型、索引、事务与一致性；
  • Kafka、消费组、Partition、Rebalance、Offset、幂等；
  • 缓存、并发、线程池、网络与分布式系统；
  • 服务化、高可用、存储、监控、部署与容灾；
  • 权限、沙盒、日志、审计和失败恢复。

Agent 不是飘在空中的智能，它最终仍运行在一个分布式软件系统中。

4. 学会坦诚表达不确定性

没在生产中做过的内容不要硬编进项目。更好的表达是：

“这个方案我没有在生产环境实践过；如果让我设计，我会从以下约束和 Trade-off 出发……”

这能展示判断力和发散能力，也避免追问后暴露虚构细节。

5. 练习 AI 协作，而不是 AI 代做

未来 AI Coding 面试可能从“能否独立手写全部代码”，转向“当所有人都有 AI 时，能否比别人做出更可靠的系统”。候选人需要负责：

  • 定义任务与拆解问题；
  • 做架构、定接口和安全边界；
  • 检查 AI 的推理和实现；
  • 编写或要求测试，验收结果；
  • 为最终决策和后果负责。

十、我的提炼：Agent Engineer 是 AI Native Software Engineer

视频最后的判断可以进一步压缩为一个公式：

Agent Engineer = LLM 能力理解 + 上下文工程 + 行为控制 + 软件工程 + 安全治理 + 评估归因。

只懂模型，会忽略系统可靠性；只懂后端，会不知道怎样利用 LLM 的推理和生成能力。真正的能力是：

  1. 知道 LLM 能做什么；
  2. 知道 LLM 有多不可靠；
  3. 用确定性软件、边界、工具和评测包住这种不确定性；
  4. 最终证明它比原来的业务流程更有效，而不只是“用了 AI”。

面试官真正寻找的四种判断力

  • 必要性判断：这里真的需要 Agent 吗？
  • 边界判断：哪些交给 LLM，哪些必须确定性执行？
  • 工程判断：怎样应对规模、权限、状态、失败和成本？
  • 价值判断：效果是否可度量、可归因、可持续？
