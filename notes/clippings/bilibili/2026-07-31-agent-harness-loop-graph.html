Agent 系统架构设计：Harness、Loop、Graph 到底怎么选

一句话总论

Harness、Loop、Graph 不是三个可选方案，而是 Agent 系统里相互嵌套的三层工程化架构。 Harness 解决「能不能工作」，Loop 解决「怎么证明做对了」，Graph 解决「复杂流程怎么控制」。很多 Agent 项目的成败不依赖模型能力，而在这三层的设计。

学完你应该获得什么

  • 能分清 Harness / Loop / Graph 各自解决的问题和职责边界
  • 知道每个层各自的坑（笨重、耗 token、过早固化流程）
  • 会用「先看层级再改」的排查思路定位 Agent 生产环境问题
  • 掌握「先 Harness 跑起来 → 攒 trace → 再固定成 Graph」的演进路径
  • 能对照 5 个常见分层错误做自检

三层架构速览

层 核心职责 解决什么问题 各自的坑
Harness 围绕模型的能力（工具、记忆、沙箱、权限、审批） 模型怎么应用到业务场景 实现容易笨重，影响执行稳定性
Loop 反馈环：运行 → 取结果 → 异常重试 怎么让 Agent 越跑越可靠 增加 token 消耗、带来延迟
Graph 执行分支编排：谁来做、选哪个 Agent 复杂多步流程怎么控制 流程未稳定就被过早固化

Harness — 能不能工作

核心组成

Agent = Model + Harness。模型能力在底层，往上依次是：规划、子 Agent、沙箱、授权、评判逻辑。加上这些，Agent 就不再是 chat 模型，而是能完成复杂任务的系统性能力。

判断 Harness 做得好不好

  1. 能不能根据任务去行动、真正执行起来
  2. 执行过程中有没有权限划分和边界条件判断
  3. 出问题能不能找到出问题的点并纠正

Harness 的「四周能力」（把模型放中间看四周）

方位 能力
上 输入给模型的上下文
右 当前 Agent 能调用的工具
下 记忆状态 + 运维监控
左 预算、审批等控制流条件判断

排查信号：执行进度/状态丢失、越过审批权限、调用的工具不好用 → 先检查这四周能力，通过观测或评测判断有无优化空间，再考虑调提示词或模型。

Loop — 怎么证明做对了

工作方式

以 Agent 改文件为例：在沙箱修改文件 → 提交 PR → 交给检查。收集反馈证据（链接能否打开、CI 是否通过、文件格式是否合规），证据足够 → 正常结束；不够 → 判断失败原因 → 重新修改。

核心要点

Loop 不是「让 Agent 继续做就算完成」，而是要有： - 明确的触发条件和目标 - 运行时保存状态并判断下一步 - 收集证据，把相关信息带给下一轮

四个停止判断逻辑

  1. 证据是否足够
  2. 预算（token 消耗次数）能否支持下一步
  3. 是否遇到不可逆转的错误
  4. 是否需要人工审批

区分：Prompt 负责「这一次怎么回答」，Loop 负责「回答之后要不要继续执行」。

Graph — 复杂流程怎么控制

组成元素

  • 节点：工作单元（模型调用、工具函数、专门 Agent、人工审批、checkpoint）
  • 边：执行条件，决定哪个节点接着运行
  • checkpoint：可恢复的位置

示例：范围界定 → 并行跑研究 A / 研究 B → 结果汇总 → 人工审查 → 不通过修改 → 回到总节点 → 通过后发布。

什么时候适合用 Graph

  • 流程顺序确定
  • 分支条件清楚
  • 并行结果需要合并整理
  • 执行中需要审批和恢复
  • 需要多 Agent 协同

什么时候不适合

  • 没有确定性执行路径，需要模型临时制定规划
  • 业务流程改造特别快
  • 只是「画了个图」就以为是一个完整系统

推荐路径：先用简单 Harness 把 Agent 跑起来 → 执行中积累 trace 数据 → 把反复出现的流程和规划固定成 Graph → 再做 Graph 编排。

三层如何组合（研究项目实例）

┌─ Harness（最外层）：浏览器、搜索、存储、密钥权限、trace、审批 ─┐
│   ┌─ Graph（中层）：规定怎么并行、来源怎么汇总、何时审查、    ─┐ │
│   │              由谁判断和发布                              │ │
│   │   ┌─ Loop（内层）：局部反馈任务                      ─┐   │ │
│   │   │  · 调研结果不足 → 补充检索信息                  │   │ │
│   │   │  · 引用数据有问题 → 修改                        │   │ │
│   │   │  · 内容过期 → 判断是否刷新数据                   │   │ │
│   │   └───────────────────────────────────────────────┘   │ │
│   └────────────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────────────┘

嵌套关系：Graph 运行在 Harness 提供的环境里；Loop 运行在 Graph 的某个节点或某条路径里。理解这个组合关系后，出问题就能准确判断该改哪一层。

排查问题：先定位层级，再动手

现象 检查层
拿不到数据、权限有问题、会话进度不理想 Harness
结果正确但输出不稳定、该停不停、该继不继 Loop
多 Agent 执行顺序和分支混乱 Graph
多任务执行问题难定位 Graph + Harness 组合（Graph 标记走到哪步，Harness 在各节点留下 trace 数据）

五个常见分层错误

  1. 没弄清楚真实工作，就先把流程拆成几十个节点 — 选型判断错误
  2. 同一个模型既执行又判断 — 缺乏独立的测评能力
  3. 只反馈、只让继续尝试 — 没限制执行次数和退出条件
  4. 给 Harness 太多工具和记忆 — 模型自己都不知道该调哪一个
  5. 状态、API 和停止规则出问题，却总觉得模型能力不够 — 一直在盲目更新模型

修复问题前，先确定问题属于哪一层，避免盲目尝试。

上线前五层检查清单

检查项 内容
Harness 工具权限是否清晰、权限是否最小化、状态能否保存、能否暂停/恢复
Loop 成功证据、失败反馈、重置次数、token 预算上限
Graph 路径并行状态、共享逻辑、恢复路径是否明确
评测能力 能回放 trace、比较版本、知道每次改动为什么生效/不生效
持续监控 成本、延迟、失败率、任务成功率、人工介入率

关键洞察

不要一开始就把三层做得很重，但要清楚当前问题属于哪一层——这样出问题时，才知道到底要改工具、改验证，还是改流程。

三个概念围绕模型展开，都影响 Agent 的可靠性；在正式环境运行时三层边界会变得模糊，所以工程化设计比模型能力更决定项目成败。

  4. Loop 的四个停止判断逻辑是什么？
  5. Prompt 和 Loop 的分工区别是什么？
  6. 什么场景适合用 Graph？什么场景不适合？
  7. 推荐的演进路径为什么是「先 Harness 跑起来再固定 Graph」？
  8. 多 Agent 执行顺序混乱，应该检查哪一层？
  9. 五个常见分层错误里，你最可能犯的是哪个？
  10. 上线前的五层检查分别查什么？
参考答案 1. Harness=能不能工作；Loop=怎么证明做对了；Graph=复杂流程怎么控制 2. Harness（Agent = Model + Harness） 3. 上：上下文；右：工具；下：记忆状态+运维监控；左：预算审批 4. ①证据足够 ②预算支持 ③无不可逆转错误 ④人工审批与否 5. Prompt 管「这次怎么回答」，Loop 管「回答后要不要继续执行」 6. 适合：流程确定/分支清楚/需合并并行/需审批恢复/多 Agent；不适合：路径不定/流程变得快/只画图 7. 因为流程未验证就固定成 Graph 会过早固化，先跑起来攒 trace 再固化更稳 8. Graph 9. 见原文五种错误 10. Harness 权限状态、Loop 证据预算、Graph 路径恢复、评测回放、持续监控成本延迟成功率
