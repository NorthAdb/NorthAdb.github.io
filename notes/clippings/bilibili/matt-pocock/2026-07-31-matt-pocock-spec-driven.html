Matt Pocock 实战教程：从原型到 spec-driven 开发

UP 主：ChHsich（搬运翻译） | 原作者：Matt Pocock 时长 ~8 分钟 | 事实主干：B站 AI 字幕（agent-reach / OpenCLI，164 段逐句） 证据等级：bilibili-ai-subtitles

一句话总论

不要一上来就写超详细 spec 指望一击即中——先把讨论的「保真度」提上来，用原型回答「它该长什么样、该怎么表现」这类问题。 在 AI 时代，生产代码成本大幅下降，做原型/spike 从未如此便宜；从「能跑的原型」跨到 production-ready 代码，比从「讨论+spec」跨过去简单得多。

学完你应该获得什么

  • 理解 Matt 反对「spec-driven 一刀切」的理由
  • 掌握「保真度（fidelity）」概念：什么问题是低保真讨论能解决的，什么问题必须靠原型
  • 学会 prototype skill 的用法：什么时候该上原型、怎么迭代、怎么交接
  • 知道原型不只适用于 UI/前端，也适用于后端逻辑和状态机
  • 记住关键判断标准：当关键问题是「它该长什么样」或「该怎么表现」时，就该上原型

核心论点：别急着写 spec

Matt 抓狂的习惯：很多人用 AI 写代码时，想着「我得先写一份 spec → 做个 plan → spec-driven development → 一击即中」。把精力全花在写超详细 spec，指望 AI 产出严丝合缝地匹配它。

他忘了的事：你其实可以直接写代码——在朝 spec 推进的过程中就可以写。原型和 spike 从 Agile 时代起就有，但大家现在不做原型了。

关键判断：「代码很廉价」这句话半对半错，但有一件事确实变便宜了——生产代码的成本大幅下降。所以做快速的一次性 spike，从来没有这么便宜、这么好用过。

保真度（Fidelity）概念

保真度 适用问题 方式
低保真 基础问题（弹窗有取消/确认按钮） 讨论里直接定下来
中保真 弹窗某些情况要展示数据、数据怎么展示 稍微提高保真度
高保真 「真看看它跑起来什么样、感受它怎么运作」 必须做原型

规划 spec 时很难想清楚东西到底该长什么样——很多问题只能靠做原型来回答。因为现在做原型成本前所未有地低，Matt 更倾向于在更高保真度下讨论。

Prototype Skill 是什么

定位：Wayfinder skill 的一部分（Wayfinder 是规划一大块工作的 skill，会把大块工作拆成不同规划 session，每个 session 有自己的 ticket）。

Ticket 类型对比：

类型 做什么 用途
grilling ticket 和 agent 聊天，敲定基本范围 低保真讨论
prototype ticket 做便宜、粗糙但具体的产物（stub / UI 逻辑代码） 把讨论保真度提上来

判断标准（不管用不用 Wayfinder）：当关键问题是「它该长什么样」或「该怎么表现」时，就该上原型。

实战演示：画图 app 的搜索功能

Matt 用 Wayfinder 扩展基于 tldraw 的画图 app，想要搜索历史图表的功能（数据模型复杂：图表 + 不同时间点快照）。

迭代过程

  1. 跑 prototype → 底部生成一个选择器，三个选项 A / B / C，每个编码了几条设计决策
  2. 看 A：原地重排、按行分组。喜欢搜索框在上面，但分组感觉不对
  3. 看 B：左边分组往下筛。不错
  4. 看 C：全内联、无筛选。不喜欢顶部的「搜索图表」和「current」显示
  5. 给反馈：「喜欢 A 的搜索框 + C 的布局」→ 得到 D 版本（A 的搜索框 + 想要的布局）
  6. D 完成：搜索 model 能看到效果，去重成功，功能可用

关键细节

  • token 消耗：原型 session 约 10 万 token → compact 后做一轮 QA（保留所有设计决策，继续给反馈）
  • 存储：原型存在 throwaway 分支上
  • 交接：交给 AFK agent 把所有东西接上、删掉旧原型代码、确保符合原始 spec
  • 结果：因为在高保真度下讨论（看真实跑着的版本给反馈），实现的人有实打实的前端代码可直接 copy/paste，而不只是一份 spec

关键洞察

  1. 「我写了这么漂亮的 spec，结果做出来的东西完全跑偏」 → 大概率是讨论的保真度不够高，当时就该做原型
  2. 原型不只是 UI/前端的事：前端获益最多，但后端活同样适用——「这段逻辑对吗？这个状态模型感觉对吗？」 - 例子：建一个小型可交互的终端 app，把状态机推到纸面上很难推理的 case 里——纯逻辑的原型
  3. 从讨论+spec 到 production 是大跨步；但从能跑的原型到 production 就很简单
  4. 趋势：随着 agent 越来越擅长处理 canvas 和设计工具，wireframe 一定会回归
  5. 高保真度有代价：token 成本随保真度上升；但换来的反馈无比宝贵

自测题

  1. Matt 反对「spec-driven 一刀切」的核心理由是什么？
  2. 保真度分哪几个层次？各解决什么问题？
  3. 「代码很廉价」这句话对在哪、错在哪？
  4. prototype ticket 和 grilling ticket 的区别是什么？
  5. 什么时候该上原型？（判断标准）
  6. 演示里为什么选择 compact 而不是开新会话？
  7. 原型为什么要存在 throwaway 分支？
  8. 后端逻辑原型长什么样？举例。
  9. 为什么说「从能跑的原型到 production 简单」？
  10. 原型 session 大约消耗多少 token？
参考答案 1. 可以直接写代码，不必先把所有东西一次性定好；原型/spike 便宜且好用 2. 低保真（基础框架）→ 中保真（数据展示）→ 高保真（必须看实际效果） 3. 对：生产代码成本确实降了；错：代码不「廉价」，只是变便宜了 4. grilling=讨论敲定范围；prototype=做粗糙但具体的产物提保真度 5. 关键问题是「它该长什么样」或「该怎么表现」时 6. 要保留原型的所有信息/设计决策，只是给反馈，所以同一处继续对话 7. 让实现者直接参考真实前端代码，可 copy/paste 8. 小型可交互终端 app，把状态机推到纸面难推理的 case 里 9. 原型是真实可跑的东西，实现者只需接线、清理、对照 spec 10. 约 10 万 token
