为什么现在的顶级大模型都在卷 MoE？

帖子原文

如果你最近关注 DeepSeek V4、GLM-5.1、Gemma 4，会发现一个明显趋势：旗舰模型正在从 Dense 走向 MoE。MoE 的本质不是简单堆参数，而是让模型拥有更大的总容量，同时每次只激活少数专家。本文从原理、架构和模型案例出发，系统拆解 MoE 为什么正在成为新一代大模型的底层答案。

图解内容（12 张轮播图）

以下是对轮播图的识图/OCR 整理；模型版本、参数规模和上下文长度均按图片原文记录，未在本笔记中独立核验。图片仍保留在每个小节下方，便于对照。

1. MoE 的工作原理：Router 按 token 选择专家

MoE 层可以理解为「Router + 多个 Expert FFN」：

  1. 上一层输出的 token/hidden state 进入 Router。
  2. Router 通过一个 FFN 对每个专家打分，再用 Softmax 得到概率分布。
  3. 只激活得分最高的 Top-K 个专家，未选中的专家不参与该 token 的计算。
  4. 将被选专家的输出按路由权重加权求和，作为 MoE 层输出传给下一层。

示意图中的专家得分为 0.45 / 0.19 / 0.05 / 0.31；若采用 Top-1，则只激活 Expert 1，输出按 p = 0.45 加权。

2. 为什么大模型越来越需要 MoE？

Dense 模型的参数基本每次都参与计算：模型越大，能力和容量可能越强，但训练成本、推理成本、显存占用与通信开销也同步上升。MoE 则把一个巨大的通用 FFN 拆成多个分工不同的专家：

  • 总参数量可以很大，模型拥有更大的知识与能力容量；
  • 每个 token 只激活少数专家，单次计算量不必与总参数量同比增长；
  • 模型从「每次都把全部参数算一遍」变成「按需调用」，即按需变大。

因此，MoE 解决的不是简单的「堆更多参数」，而是模型容量与单次计算成本之间的矛盾。

3. 用医院分诊理解 MoE

图片给出的类比是：

医院分诊系统 MoE 对应物
病人 输入 token / hidden state
导诊台 Router / Gate
内科、外科等科室专家 Expert FFN
挑选最合适的几个科室 Top-K 路由
汇总各科室意见 按权重融合输出

在 Transformer 中，MoE 通常替换的是 FeedForward/MLP（FFN）模块，不是 Attention 模块。Attention 一般保留，FFN 则变成 Router 加多个并行的 Expert FFN。

4. Dense Decoder 与 MoE Decoder 的结构差异

传统 Decoder Layer 大致是：

LayerNorm → Masked Self-Attention → 残差连接
         → LayerNorm → FFN → 残差连接

MoE Decoder 则将第二个 FFN 替换为：

LayerNorm → Router → 多个 Expert FFN → Weighted Sum/Combine → 残差连接

所以读模型结构图时，看到 MoE 出现在 FeedForward/MLP 那一块是正常的；它并不意味着整个 Transformer 层都被专家化。

5. MoE 的核心优势与工程难点

三个核心优势：

  1. 总参数容量更大：专家数量增加后，模型能覆盖更丰富的模式、知识和任务能力。
  2. 单次激活参数更少：每个 token 只调用少数专家，推理 FLOPs 增长慢于总参数量。
  3. 更适合大规模扩展：相比不断扩大 Dense 模型，MoE 可以通过增加专家扩展容量，同时控制单次计算。

必须解决的工程问题：

  • Router 是否偏爱少数专家，造成专家塌缩或负载不均？
  • 专家之间如何做负载均衡，避免部分专家训练不足？
  • Expert Parallel 训练时，跨设备通信成本如何控制？
  • 总参数量很大时，如何让部署、显存和推理延迟可控？

结论：MoE 不是「天然收益」，而是需要路由、负载均衡、并行通信、训练稳定性和部署系统共同支撑的工程方案。

6. DeepSeek V4：MoE + 系统工程 + 长上下文

图片将 DeepSeek V4 的路线概括为：MoE 扩容、系统工程提效、面向 1M context 设计。图中列出的对比数据如下：

模型 总参数 单 token 激活参数 上下文 每层 MoE 每 token 路由激活
DeepSeek V4-Pro 1.6T 49B 1M 1 shared + 384 routed experts 1 shared + 6 routed
DeepSeek V4-Flash 284B 13B 1M 1 shared + 384 routed experts 1 shared + 6 routed

图中强调的 V4 设计：

  • shared expert 始终参与，负责通用、稳定、反复出现的模式；
  • routed experts 根据 Router 选择，负责更细粒度、更有差异的处理；
  • 目标不是单纯把模型做大，而是让大模型在百万上下文中保持可用的推理效率。

图片还列出 CSA（Compressed Sparse Attention）、HCA（Heavily Compressed Attention）、混合注意力架构和 mHC（Manifold-Constrained Hyper-Connections）等系统组件，用于降低长上下文中的 Attention/KV Cache/通信压力。这里应将 MoE 理解为容量方案，而不是完整的长上下文解决方案。

DeepSeek V4-Pro 与 V4-Flash 架构对照（按图整理）

维度 V4-Pro V4-Flash
词表 129k 129k
上下文 1M tokens 1M tokens
层数 61 43
注意力头数 128 64
Embedding 维度 7,168 4,096
FFN 中间维度 3,072 2,048
前 3 层 hash-based MoE hash-based MoE
MoE 专家 1 shared + 384 routed 1 shared + 256 routed

两者共同体现「总参数很大，但每次只激活少量参数」；Pro 更大、更深、激活参数更多，Flash 则以更低推理成本为目标。

7. GLM-5.1：面向 Agent / Tool-use 的国产 MoE 路线

图片给出的关键信息：

  • 总参数 744B，激活参数 40B；
  • 核心结构为 MoE，整体思路与 DeepSeek-V3.2 有相似之处，但层数更深；
  • 前几层保留 Dense FFN，后续层使用 MoE；
  • MoE 的价值不止是预训练容量，也用于浏览、代码、工具调用和复杂任务链等 Agent 场景；
  • 图片将 DeepSeek V4 概括为「长上下文 / 系统效率」侧重，将 GLM-5.1 概括为「旗舰开源能力 / agentic 任务表现」侧重。

其结构示意中的参数包括：词表 155k、上下文长度 202k、78 层、Embedding 维度 6,144；前 3 层使用 Dense FFN（隐藏维度 12,288），MoE 层包含 256 个专家，每个 token 激活 8 个 routed experts 加 1 个 shared expert。

8. Gemma 4：Dense 与 MoE 并存

Gemma 4 的启发不是「所有模型都必须 MoE」，而是同一模型家族同时提供 Dense 和 MoE 两种答案：

  • Gemma 4 31B Dense：不是 MoE，但采用 GQA、5:1 的局部滑窗 + 全局混合注意力，支持更长上下文、多模态和更灵活的开源部署。
  • Gemma 4 MoE：总参数较大，但 active parameters 更可控；在性能接近时，具有更好的性能/成本比、硬件部署灵活性和边缘设备适配性。

图中 Gemma 4 MoE（26B-A4B）的结构数据：词表 262k、上下文 256k、Embedding 维度 2,816、前 30 层重复模块、128 个专家；每个 token 激活 8 个专家加 1 个 shared expert，总参数约 25.2B，单步激活约 3.8B，FFN 中间隐藏维度 704，使用 GEGLU。

9. 三个模型放在一起看：MoE 正从结构技巧变成系统路线

三组案例的共同点是：未来评价旗舰模型不能只看总参数，还要看：

  • 激活参数量：决定单 token 的主要计算成本；
  • Router 与负载均衡：决定专家是否被有效利用；
  • Expert Parallel 与通信效率：决定大规模部署是否可行；
  • 训练稳定性、KV Cache 管理和长上下文效率：决定真实使用体验；
  • Agent / tool-use 能力：决定模型在浏览器、终端、代码和复杂任务链中的实际价值。

Dense 不会消失：中等规模模型、训练配方成熟、部署简单或硬件适配更重要时，Dense 仍然有优势。更准确的结论是：当模型继续扩大、又要求控制单次计算时，MoE 会越来越接近旗舰模型的主流扩展路线。

📌 MoE 知识补充（非帖子原文，供学习参考）

💡 以下为基于帖子主题的通用补充知识，用于巩固图解中的概念；上面的「图解内容」才是本次对轮播图的识图整理。

Dense vs MoE 核心区别

维度 Dense（稠密） MoE（混合专家）
推理时激活 全部参数参与计算 只激活少数专家（如 8 选 2）
总参数量 = 实际计算量 总参数大，激活参数小
例子 70B Dense 每次用满 70B Mixtral 8×7B 总参 47B，每 token 激活 13B
成本 推理算力固定 用较少推理算力获得接近大模型效果
缺点 参数效率低 显存按总参数量算；路由不均衡可能让专家训练不充分

为什么旗舰模型都在转向 MoE

  1. 参数效率：MoE 用「大总容量 + 稀疏激活」，让模型记住更多知识，但推理成本只按激活部分算
  2. 算力约束：训练/推理成本受限时，MoE 是「用更少算力换更大模型」的主流方案
  3. 容量提升：专家可以 specialize（专精不同领域/任务），总容量远大于同等算力的 Dense

提到的模型案例

  • DeepSeek V4：深度求索，开源 MoE 路线（此前 V3/R1 已是 MoE 架构）
  • GLM-5.1：智谱，GLM 系列转向 MoE
  • Gemma 4：Google，Gemma 开源系列的新一代

MoE 的关键组件

  • Router/Gating：决定每个 token 激活哪些专家（Top-K routing）
  • Experts：复制多份 FFN 子网络，各自专精
  • 共享专家（可选）：部分模型加共享专家兜底通用能力

常见误解

  • ❌ MoE 就是「把多个小模型合在一起」——实际上专家不是独立模型，是 Transformer 内部的 FFN 副本
  • ❌ MoE 参数量虚标——总参数量是真的，但「激活参数量」才是推理成本的真实指标
  • ❌ MoE 只在训练时省钱——推理时稀疏激活同样省算力，但显存要装下全部专家
