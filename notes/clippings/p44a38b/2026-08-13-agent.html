多 Agent 通信实践全景：从编排到终端直连

来源：Datawhale《刚刚，Claude Code 的重大更新来了！》（2026-08-08）+ 网络调研综合 原文：https://mp.weixin.qq.com/s/R4EyCcdcBr50LIV1ZuuHA

来源：Datawhale《刚刚，Claude Code 的重大更新来了！》（2026-08-08）+ 网络调研综合 原文：https://mp.weixin.qq.com/s/R4EyCcdcBr50LIV_1ZuuHA

一句话结论：多 Agent 协作正在从「中心节点派生子任务」走向「平级会话直接对话」。 Claude Code 2026-08 新增的跨会话 SendMessage + ListAgents 让两个用户各自开的终端会话能直接互发消息、无需人工搬运；而底层的行业标准正在收敛到 A2A（agent 之间）+ MCP（agent 与工具）+ 共享状态（agent 与记忆） 三件套。

🎯 引子：Claude Code 跨会话更新（文章核心）

2026-08-08 Anthropic 发布重大更新，18 小时近 500 万人看过：不同的 Claude Code 会话现在可以互相聊天了。

以前多个会话一起跑（前端/后端两个终端、几个 worktree 并行开发），一个会话发现了什么、改了什么，得靠人工搬运（窗口 A 复制总结 → 粘贴到窗口 B）。现在：

  • 跟一个会话说"把刚才接口改动的事告诉另一个终端里跑的会话"，Claude 自己会找目标、写内容、发过去；
  • 双向：可以向另一个会话提问，并在当前会话收到回复；
  • 主动：当它的改动影响到另一个会话的工作时，Claude 能主动向其他会话发消息。

背后是两个新工具：ListAgents（找到能联系上的会话）+ SendMessage（把消息发过去）。

⚠️ 限制：传的是 Claude 自己写的一段文字——不是完整对话历史，也不带文件；改不了接收方配置，也批不了对方权限申请。想搬整个上下文，官方建议用 resume（恢复会话），不是发消息。

和之前的"多会话协同"有何不同

Claude Code 之前已有协作能力，但都属于同一棵树派生：

机制 特点 归属
subagent 一个会话内部派生的子任务 中心化
Agent Teams 今年二三月上线的实验功能，一组会话一起干活（需手动改 config 开启） 中心化
跨会话 SendMessage 🆕 连接用户自己分别在终端启动、原本互不知晓的会话，甚至不同机器。没有谁派生谁，也没有谁管着谁，是两个平级会话相互搭话 对等

Codex 一个月前的 Multi-agent v2

Codex CLI 一个月前转正了 Multi-agent v2：有 send_message 工具，/root 主会话用 spawn_agent 生成 /root/researcher、/root/builder 挂在路径树上，兄弟节点之间可以直接 send_message，不绕回 /root。但这棵树从头到尾仍由同一个 orchestrator 派生——本质上和 subagent / Agent Teams 是同一类机制。

真正对应"两个用户自己开的、互不隶属的终端会话"的，是 Codex 原生的多会话用法：两个终端各敲一遍 codex，就是两个完全独立的进程，没有内置通信通道——要互通得靠 tmux、把 Codex 当 MCP server 外接（codex-reply 续接线程）、或手动复制粘贴。

一、多 Agent 通信的 4 种架构范式

1️⃣ 编排式 / 中心化（Orchestrator-Worker / Supervisor）— 当前绝对主流

一个主 agent 派生多个子 agent，派活、收结果、汇总。通信是父子关系：子 agent 有独立 context，跑完把摘要/结果回传主 agent。

  • Anthropic Research 系统（官方架构）：LeadResearcher 派并行 Subagent 搜索，各自独立 context 窗口，回传发现 → 主 agent 综合 → 必要时再派新子 agent。官方数据：多 agent 比单 agent 在内部 eval 高 90.2%，代价是 token 约 15×。
  • Claude Code：subagent（会话内派生）、Agent Teams（多会话协同但都归一个主会话管）
  • Codex Multi-agent v2：/root 主会话派生、路径树管理

适合：研究、审查、并行搜索这类一个任务拆多个子任务的场景。

2️⃣ 对等式 / 去中心化（Peer-to-Peer / Mesh）— 刚成熟的新趋势

平级、各自独立的 agent 直接互发消息，不绕中心。

  • Claude Code 跨会话 SendMessage（2026-08 新增）：两个用户在不同终端/不同机器上各自启动的会话，原本互不知道对方存在，现在能互相发消息
  • Codex Multi-agent v2 的兄弟节点：/root/researcher ↔ /root/builder 直连

适合：多个长期运行、并行开发的会话互相同步（前后端并行、worktree 并行）。

3️⃣ 图 / 状态机式（Graph / Shared-State）— 流程确定时

LangGraph 是代表：agent 工作流建模为图，节点间通过共享 State + 消息传递通信（受 Google Pregel 启发，按 super-step 推进）。节点不是"互发消息"，而是往共享状态写更新，reducer 决定如何合并，下一跳节点读状态继续。

适合：流程相对确定、需要状态管理、断点恢复（checkpointer）与条件路由的工作流。

4️⃣ 黑板 / 共享存储式（Blackboard / Shared Memory）— 解耦最彻底

agent 之间不直接通信，都读写同一块共享中介：数据库、文件系统、向量库、Redis、issue tracker。

  • TencentDB Agent Memory：记忆作为多 agent 的共享层（见 Clippings/微信公众号/2026-08-11-TencentDB-Agent-Memory-实测笔记）
  • Matt Pocock skills：to-spec/to-tickets 把结论落到 issue tracker，另一个会话 implement 从 tracker 读，plan 文档做桥梁

适合：完全解耦、可审计、跨机器跨进程天然可行；代价是约定"写哪里、什么格式、谁轮询"。

二、成熟的通信手段 / 协议（按层次）

手段 代表 适用场景
进程内工具调用（Handoff） OpenAI Agents SDK：handoff 就是一个 transfer_to_xxx 工具 单进程内多 agent 分工，最简单
A2A 协议（Google 开源标准） a2a-protocol.org 跨框架 agent 互操作：HTTP + JSON，Task/Message/Artifact，agent 保持"不透明"（不共享内部 memory/工具）
MCP + Channels Model Context Protocol agent↔工具标准；MCP server 可当 channel 把消息推进会话（Telegram/Discord/webhook 事件驱动），Claude Code 官方支持
共享状态 / 事件总线 Redis pub/sub、消息队列、数据库 通用、语言无关、跨机器，自己定协议
文件系统 / git 共享文件、worktree、issue tracker、handoff 文档 零依赖的"异步邮箱"，Agent Memory / Matt Pocock 流程都这么干
CLI 会话级工具 tmux/screen、Remote Control、claude self-hosted-runner 人工或脚本层面共享终端/跨机器

行业共识的标准组合：工具用 MCP，agent 之间用 A2A。 A2A 官方原话："Build with any framework, equip with MCP, communicate with A2A to remote agents, local agents, and humans."

三、终端 ↔ 终端、无需人工干预（重点场景）

按"直接程度"从官方到自建：

🥇 Claude Code 原生（最新，最接近你要的）

核心工具： - ListAgents：发现当前能联系上的会话（含其他机器上的 Remote Control 会话、云会话） - SendMessage：把消息发给目标会话，双向 + 主动推送

官方 changelog 的关键细节： - 支持 macOS/Linux，跨机器（Remote Control 会话可按名字发起对话，ListAgents 显示 name [ref]） - 发送前过权限分类器评估（SendMessage 的消息先审后发） - crossSessionInbound + dialogExpiry 设置：发给"绕过权限"会话的消息会暂存等你批准，普通会话自动投递 - 投递失败报错、超长摘要自动截断、断开的 Remote Control 会话标记为 offline

🥈 Codex Multi-agent v2（一个月前转正）

  • send_message + 路径寻址：/root/researcher ↔ /root/builder 兄弟节点直连
  • 但整棵树仍由同一个 orchestrator 派生——本质是"中心化派生"
  • Codex 原生多会话（两个终端各跑 codex）没有内置通信，靠 tmux / MCP 外接 / 手动复制

🥉 通用自建方案（不依赖某个工具）

方案 做法 优点 缺点
MCP channel 桥接 让 agent B 以 MCP server 身份挂出去，agent A 通过 MCP 调用；或用 channels 把事件 push 进会话 有标准、复用 MCP 生态 要自己写 server 端逻辑
消息队列 / Redis A 往队列写，B 订阅/轮询 跨语言、跨机器、可持久化 无标准格式，要约定协议
共享文件 / DB A 写任务文件/记录，B 轮询目录或 DB 零依赖、可审计 有轮询延迟，需锁/幂等
A2A server 每个 agent 挂一个 A2A 端点，按 Task/Message 协议互调 跨框架、官方标准 生态早期，偏重

四、选型建议

你的场景 推荐
一个任务拆成多个并行子任务（研究/审查/搜索） 编排式：subagent / OpenAI handoff / LangGraph supervisor
两个独立终端会话互相同步、平行开发 Claude Code SendMessage（官方原生，现在就能用）
跨框架、跨厂商、生产级互操作 A2A 协议
多个 agent 共享知识/记忆、长期解耦 共享存储（DB/向量库/文件，如 Agent Memory）
流程确定、要状态回溯与断点 LangGraph（共享 State + checkpoint）

📌 延伸思考

  • Claude Code harness（Clippings/微信公众号/2026-08-11-Claude-Code大代码库harness-小林coding）讲的是单个 agent 在大代码库怎么用（subagent 探索/会话拆分），本篇讲多个 agent 之间怎么通信——前者是"一个 agent 怎么拆活"，后者是"多个 agent 怎么对齐"。
  • Agent Memory（Clippings/微信公众号/2026-08-11-TencentDB-Agent-Memory-实测笔记）是"黑板式"共享记忆的成熟实现——跨会话共享状态正是多 agent 协作的一种主力方案。
  • 可动手验证：升级 Claude Code 后开两个终端会话，让 A 会话把改动发消息给 B 会话，体验一下"无需人工干预"的对等通信；这是理解编排式 vs 对等式差异最快的方式。
