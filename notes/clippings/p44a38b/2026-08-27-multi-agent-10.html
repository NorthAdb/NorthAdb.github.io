靠这 10 个优化点，把 Multi-Agent 工作流成本降了 50%+

作者：lemonye | 来源：微信公众号「腾讯技术工程」 | 发布日期：2026-08-21 本文是对原文的结构化整理与实践提炼；图片已通过 PicGo 上传至 Gitee 图床。

一句话总结

Multi-Agent 降本的核心不是削弱能力，而是围绕三条原则治理上下文：

  1. 只让 AI 看到当前需要的上下文；
  2. 减少无关上下文；
  3. 减少重复上下文。

在一个由 1 个 TL（调度器）+ 6 个子 Agent 组成的前后端开发 Harness 中，作者通过 10 个方向改造，主 Agent 端到端 token 从 708,783（17 轮）降至 315,266（9 轮），下降 55.5%；完整中型需求预计降本 50%～65%。

1. 背景：为什么 Multi-Agent 很容易烧 token

典型工作流由 TL 统一调度：

TL
├── Wave 1（并行）：后端 Agent + 前端 Agent
├── Wave 2：质量审查 Agent
├── Wave 3：测试 Agent（用例生成 + 执行）
├── Wave 4：视觉验证 Agent
└── Wave 5：Agent 评测

一次中等需求可能经历 5～6 个 Wave、20+ 次子 Agent 调用和数百轮工具调用。

六类 token 消耗来源

来源 典型内容 成本特征
系统提示词 固定提示词、Skill、MCP Schema 每轮必带；工具越多越贵
工具返回 需求 JSON、设计稿节点树、截图 base64 体积不可控，后续轮次反复计费
文件读取 代码、知识库文档 盲搜会带入大量无关内容
长期记忆 历史经验、技术方案 全量加载后常驻会话
历史消息 多轮对话 append-only，越往后越贵
用户提示词 当前需求 只出现一次，通常最便宜

先度量，再优化

通过 AgentLens 按 TraceId 追踪调用链、按 SessionId 聚合完整需求，先定位成本主要落在哪些 Wave 和上下文来源，再做针对性压缩。

2. 总体架构与规模预判

拆分 Agent 本身有成本：每个 Agent 都会产生一份系统提示词开销。因此先做 S/M/L 规模预判：

  • S（小需求）：单 Agent 直接处理，避免无谓的编排开销；
  • M/L（中大型需求）：进入多 Agent 并行调度，利用短生命周期、角色隔离和并行执行控制上下文增长。

3. 十个优化方向

3.1 渐进式披露：Skill 分层按需加载

采用 Skill 的三层结构：

  • L1：元数据——名称、描述，用于触发判断；
  • L2：SKILL.md——只保留核心流程和决策骨架；
  • L3：references/、scripts/——详细步骤、模板和规则，真正需要时再读取或执行。

这样即使安装 20 个 Skill，初始加载也约 1,000～2,000 token，相比单体提示词可减少约 90%。

实践要点：

  • 将测试 spec 模板、DB 前置规则等条件性内容移至 references/；
  • 将 TL 的 S/M 工作流、Wave 派发 prompt 等细节移出正文，只保留“下一步怎么决定”；
  • 正文从 198 行降至 128 行（约 -35%）。

3.2 确定性操作交给脚本，能用 CLI 就不用 MCP

大模型适合推理，不适合反复拼接和试错命令。将数据库迁移、编译、服务启动、健康检查等固化到 dev-env.sh 等脚本中，让 AI 只传参数。

Playwright MCP → Playwright CLI 的改造尤其典型：

  1. AI 负责把自然语言用例翻译为 Playwright spec；
  2. CLI 负责批量执行 spec、重跑和并行 worker。

点击一次按钮不再消耗一次 MCP 推理轮次，测试也变得可重跑、可并行。

3.3 MCP 数据获取子 Agent 化

不要让最长生命周期的 TL 直接接收 TAPD/Figma 原始 payload（需求全文、设计稿节点树 JSON、截图）。为每类数据建立专属子 Agent，只返回结构化摘要：

  • 主会话不再永久携带原始数据；
  • 子 Agent 完成即销毁；
  • 实测单轮 input token 从 1,030,000 降至 634,905（-38.4%）。

3.4 长期记忆：先索引，后读正文

为历史经验和技术方案建立轻量 INDEX.md：

  1. 先读取标题、标签、摘要索引；
  2. 按关键词和类别权重计算相关度；
  3. 只读取 Top 3 正文；
  4. 索引不存在时，才回退到全文搜索。

这能避免“命中一篇文档就把整篇常驻 context”。

3.5 单体 Agent 拆成角色专职的多 Agent

让 TL 只负责调度，把编码、测试、视觉审查分给短生命周期子 Agent：backend-dev、frontend-dev、test-runner、visual-reviewer、code-reviewer 等。

收益不是简单减少系统提示词，而是：

  • 切断单会话历史的滚雪球；
  • 让 Wave 1 前后端并行；
  • 为工具裁剪、模型分层、稳定前缀等优化创造边界。

3.6 Agent 专属工具白名单与模型分层

每个角色只暴露必要工具。例如后端 Agent 只需要文件和命令工具，不暴露 Figma/TAPD 等 MCP Schema：

---
name: backend-dev
tools: list_dir, search_file, search_content, read_file,
  replace_in_file, write_to_file, execute_command
---

同时按任务特征做模型路由：测试、视觉比对这类规则性强、轮次多的任务切换到成本更低的模型，作者实测测试/视觉 Agent 成本下降 64%。

3.7 代码图谱替代关键词盲搜

使用 graphify 基于 AST 和语义建立文件索引、依赖关系：先查图谱锁定文件范围，再读取源码，减少无关匹配行和探索轮次。

实测同一任务：

指标 使用代码图谱 未使用 差异
总 token 676,987 875,352 -22.7%
输入 token 670,281 868,544 -22.8%
输出 token 6,706 6,808 -1.5% 
uv tool install graphifyy
graphify hook install   # 绑定 post-commit + post-checkout 增量更新

3.8 稳定前缀设计：让 Prompt Cache 命中

把稳定指令和动态内容分离：稳定部分前置，动态内容统一后置，避免每次派发时改变前缀。

另外，把会话中的完整进度看板外化到进度文件：Agent 唤醒时读取文件，阶段切换只输出一行。这样既保护缓存前缀，也支持会话中断后的现场恢复。

3.9 避免重复加载 Skill

信息应在上游收集一次，再通过文档传递给下游。比如 TL 已经加载历史经验并产出技术方案，前端 Agent 直接读方案即可，不必再次 use_skill 加载同一份 200 行 Skill。

3.10 用 rtk 压缩 CLI 输出，并行化无依赖调用

rtk 可在命令执行前将 git status、npm test、docker ps 等原始输出压缩，官方实测可减少 60%～90% 的 CLI 文本量。

接入注意：

  • CodeBuddy 不支持官方 --agent，需用 PreToolUse Hook 实现拦截；
  • updatedInput 要转换为 CodeBuddy 需要的 modifiedInput，否则会静默失效；
  • 用 rtk gain 或命令行对比评估，不要用两次完整工作流 A/B（模型路径波动会淹没工具效果）。

无数据依赖的调用必须并行：TAPD 摘要和 Figma 摘要放在同一轮派发；多个 Playwright spec 交给 CLI 多 worker 批量执行。省下的不只是等待时间，更是后续轮次重复打包历史的成本。

4. 效果汇总

维度 优化前 优化后 收益
主 Agent 端到端 token 708,783（17 轮） 315,266（9 轮） -55.5%，轮次 -47%
MCP 数据子 Agent 单轮 input 1,030,000 634,905 -38.4%
代码图谱总 token 875,352 676,987 -22.7%
CLI 输出 原始输出 rtk 压缩 -60%～90%
测试/视觉 Agent 模型成本 Sonnet GLM-5v -64%

5. 落地优先级（Checklist）

  • 先做 S/M/L 规模预判，小需求不盲目拆 Agent
  • 接入 AgentLens，按 Wave/Session/Trace 建立基线
  • 重排 SKILL.md：正文留骨架，细节移至 references/
  • 全局接入 rtk，压缩高频 CLI 输出
  • 把状态外化为进度文件，设计稳定 prompt 前缀
  • 排查无依赖调用并行化
  • 用脚本/CLI 替代确定性 MCP 操作
  • 为角色配置工具白名单和模型分层
  • 引入代码图谱，长期记忆采用索引化加载
  • 用文档在 Agent 之间传递上游结论，避免重复发现

6. 我的理解

  1. 最省钱的调用是不调用：把“执行”与“推理”分离，LLM 只处理真正需要语义判断的部分。
  2. 上下文的生命周期比单次大小更重要：原始 payload 放进 TL 会话，成本会随几十轮历史被反复放大。
  3. 多 Agent 的价值在隔离与可组合性：拆分不是直接省钱，而是切断历史滚雪球并打开缓存、裁剪、并行等优化空间。
  4. 文档是跨 Agent 的低成本信息总线：上游收集一次、结构化沉淀一次，下游直接消费结论。
  5. 应把 token 当作工程指标治理：建立基线、分项测量、局部 A/B，避免只看一次完整工作流的总数。
