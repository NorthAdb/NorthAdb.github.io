  • 🌟 什么是大模型幻觉？怎么降低幻觉？
  • 🧬 补充专题：RAG 范式演进 —— Vector RAG / BM25 混合检索 / GraphRAG / SAG / PageIndex

1️⃣ 什么是 RAG？

大模型的「知识困局」

大模型有三个核心困境：

困境 说明
知识截止日期 训练数据有时间窗口，之后的事不知道
私有数据不可知 公司内部文档从未出现在训练集中
幻觉 自信地编造听起来专业但错误的内容

RAG 的解决思路：开卷考试

RAG = Retrieval-Augmented Generation（检索增强生成）

  1. 检索（Retrieval）：从外部知识库中找到和问题相关的资料
  2. 增强（Augmented）：将检索到的资料作为上下文和问题一起给大模型
  3. 生成（Generation）：大模型基于真实资料生成回答

RAG 的起源

2020 年由 Facebook（Meta）研究团队提出，2023 年 ChatGPT 爆红后真正火起来。

RAG 不是万能的

  • × 不能改变大模型的推理能力
  • × 不能改变大模型的输出风格
  • × 不能保证 100% 准确性

2️⃣ RAG 整体工作流程

RAG 系统分为两个大阶段：

索引阶段（离线）— 把知识整理好

文档加载 → 文档切割(Chunking) → 向量化(Embedding) → 存入向量数据库
  1. 文档加载：PDF/Word/Excel/HTML → 统一纯文本
  2. 文档切割：长文档切成小块（Chunk），每个块几百到几千字符
  3. 向量化：用 Embedding 模型把文本转成数学向量
  4. 存入向量数据库：专门用于相似度搜索的数据库

查询阶段（在线）— 让大模型翻书找答案

用户提问 → 问题向量化 → 向量检索(相似度搜索) → 构造增强Prompt → 大模型生成回答

这是最基础的 Naive RAG（朴素 RAG）。实际生产中还会加入查询改写、多路召回、Re-rank 等高级技术。

3️⃣ 微调 vs RAG

维度 微调（Fine-tuning） RAG
类比 让学生去上课（闭卷） 配参考书架（开卷）
知识更新 重新训练，成本高 替换文档即可，即时更新
准确性 靠记忆，可能记错 基于真实文档，可追溯
风格控制 ✅ 强项（学风格/话术） ❌ 有限
初始成本 高（训练数据+GPU） 低（建知识库即可）
推理成本 较低 较高（检索+更多 token）

怎么选？

  • 大多数场景优先选 RAG：需严格基于文档、知识频繁更新、需可追溯
  • 微调更适合：特定输出风格/格式、某种"能力"而非"知识"、数据不大不常更新
  • 最佳实践：微调 + RAG 结合 — 微调学风格，RAG 提供知识支撑

4️⃣ 文档切割策略（Chunking）

文档切割是索引阶段最关键的一步。切割的两难：

  • 切太小 → 丢失上下文
  • 切太大 → 检索精度下降

五种切割策略

策略 原理 优点 缺点
① 固定大小切割 按固定字符/token 数切 简单可预测 破坏语义完整性
② 递归字符切割 按自然边界（段落→句子→短语）逐级切 保持自然完整性 仍可能跨语义单元
③ 基于文档结构 按 Markdown 标题/代码函数/HTML 标签切 语义完整 只适用于结构规范文档
④ 语义切割 用 Embedding 计算相邻句子的相似度，转折点切割 切割质量最高 计算成本大
⑤ Agent 驱动切割 用 LLM 判断合并/拆分 效果最好 成本最高

实战建议

阶段 做法
🚀 起步 RecursiveCharacterTextSplitter，256-512 tokens，重叠 10%-20%
⚡ 优化 文档结构清晰的切换为结构切割
🔥 进阶 语义切割或「父子块」策略（小块检索，父块返回）

5️⃣ Re-rank（重排序）

为什么需要 Re-rank？

向量检索（Bi-Encoder）有两个先天不足：

  1. 信息压缩损失：几百字文本压缩成向量，细节可能丢失
  2. 缺乏查询意图感知：文档向量是预计算的，不知道用户会问什么

Cross-Encoder 解决问题

Bi-Encoder 是「各自写好简历然后匹配」，Cross-Encoder 是「面对面面试」。

把查询和文档拼在一起，通过自注意力机制让两者充分交互。

两阶段检索架构

第一阶段: Bi-Encoder 快速从全部文档中筛出 Top-50~100（追求召回率）
第二阶段: Cross-Encoder 对候选做精细化重排序（追求精准度）

主流 Re-rank 模型

模型 特点
Cohere Rerank SaaS API，效果好、接入简单
BGE-Reranker ⭐ 开源标杆，中文场景表现好（智源研究院）
ms-marco-MiniLM 轻量级，推理速度快
Jina Reranker 支持多语言
bce-reranker 网易有道，中英双语

实战效果

查询类型 准确率提升
复杂多跳推理 40%-50%
模糊查询 30%-40%
简单事实查询 ~18%
幻觉率降低 ~35%（Databricks 测试）

6️⃣ Embedding 算法演进

第一代：静态词向量（2013）

Word2Vec（Google）：上下文相似的词语义也相似

  • CBOW：用上下文预测中间词
  • Skip-Gram：用词预测上下文

⚠️ 缺陷：一词一向量，无法处理多义词（"苹果"水果 vs 手机）

第二代：上下文嵌入（2018）

BERT（Google）：同一词在不同语境下生成不同向量

  • MLM：遮盖语言模型预训练
  • NSP：下一句预测

⚠️ 缺陷：早期版本仅 512 tokens 上下文窗口

第三代：融合与优化（2023至今）

BGE-M3（智源）— "M3" 代表三个多：

M3 含义
Multi-Granularity 多粒度，最大 8192 tokens
Multi-Functionality 稠密检索+稀疏检索+多向量
Multi-Language 支持 100+ 种语言

第四代：基于大模型（2025）

LLM2Vec、Qwen3-Embedding、Seed1.5-Embedding（字节跳动）—— 用大模型的理解能力做 Embedding，MTEB 中英文 SOTA。

选型建议

  • 看 MTEB 排行榜
  • 中文场景优先 BGE、M3E 系列
  • 长文档选支持长上下文的模型（如 BGE-M3 8192 tokens）
  • 数据安全要求高 → 开源模型私有化部署

7️⃣ 向量数据库

核心原理

海量向量 → 建立索引结构 → 毫秒级近似最近邻搜索（ANN）

三种主流索引思路

索引 类比 特点
HNSW 大楼导航系统，层层缩小范围 ⭐ 最快，召回率高，默认首选
IVF 快递分拣，先分区再搜索 内存效率高，适合超大规模
PQ 高清图→缩略图压缩 节省内存，常和 IVF 结合

主流数据库对比

数据库 特点 适合场景
Milvus 十亿级规模，生态完善 ⭐ 企业级大规模生产
Pinecone 全托管 SaaS，零运维 快速上线，不在意费用
Weaviate 原生混合检索（向量+BM25） ⭐ 混合检索场景
Chroma pip 安装即用，极致轻量 POC 验证、个人项目
Qdrant Rust 编写，单机性能极强 高性能自建方案

趋势：传统数据库的向量扩展（PG pgvector、ES 向量搜索）—— 如果已在用 PG/ES，运维成本几乎为零。

8️⃣ 多路召回

单路召回的局限

向量检索擅长语义匹配，但在精确匹配（产品编号、型号）方面有短板。

多路召回的核心思想

多条路各自召回，最后合并结果：

路 方法 擅长
① 向量检索（Dense） 语义匹配
② 关键词检索（BM25） 精确关键词匹配
③ 知识图谱检索（可选） 实体关系推理

融合算法：RRF（倒数排名融合）

不看绝对分数，只看在各路中的排名。排名越靠前得分越高，被越多路命中的文档综合得分越高。

实施效果

混合检索通常比单路好 10%-30%，精确匹配场景提升更明显。

高级召回策略

  • 查询改写（Query Rewriting）：用 LLM 把原始问题改写成更适合检索的形式
  • HyDE：先生成假设性答案文档，再用它的向量去检索
  • 多查询扩展（Multi-Query）：一个改写成多个子问题分别检索

9️⃣ 量化 RAG 效果

为什么评估更复杂？

RAG 由检索器 + 生成器两部分组成，需要分别评估。

检索质量指标

指标 含义
Recall@K 找全了没有？（相关文档召回比例）
Precision@K 找对了没有？（召回结果中正确比例）
NDCG 排对了没有？（相关文档排序质量）

生成质量指标

指标 含义
Faithfulness（忠实度） ⭐ 最重要的指标：回答是否忠实于检索文档？
Answer Relevance 回答是否真正回答了用户问题？
Context Relevance 检索到的文档是否和问题相关？

RAGAS 框架

目前最流行的 RAG 评估框架。用更强的大模型（如 GPT-4）作为"裁判"，自动化评估。

# RAGAS 使用示例
from ragas import evaluate

dataset = {
    "question": [...],       # 问题
    "contexts": [...],       # 检索到的文档
    "answer": [...],         # 模型生成的回答
    "ground_truth": [...]    # 标准答案
}
evaluate(dataset)

其他工具：DeepEval（单元测试集成）、TruLens（可观测性）、ARES（合成评估数据）

🔟 大模型幻觉与防范

什么是幻觉？

大模型自信地说出一些听起来很专业但实际上是编造的内容。不是"错误"，而是"不知道但假装知道"。

幻觉的两大类型

类型 说明
事实性幻觉 内容与客观事实不符（内在/外在）
忠实性幻觉 ⭐ RAG 场景常见：偏离检索文档内容

RAG 降低幻觉的机制

  1. 注入真实知识：减少凭空编造，研究表明可降低 20%-40% 事实性幻觉
  2. 注意力机制偏向：大模型约 70%-80% 注意力集中在检索片段
  3. 可追溯可验证：错误可定位到具体文档

降低幻觉的五道防线

第一道：Prompt 工程约束（零成本，立即生效）

- 限制知识范围：「仅基于参考资料回答，没有相关信息就说不知道」
- 要求标注来源：「每句标注出处」
- 鼓励承认不确定：「不确定就说不知道」
- 结构化推理：「先列事实再推理」

第二道：RAG 检索增强（中等成本）— 标配方案

第三道：输出验证（增加延迟，高风险场景必备）

  • LLM-as-Judge：用另一模型交叉验证
  • 规则引擎校验关键数据（数字/日期/人名）
  • 多次采样一致性验证

第四道：领域微调（高成本，特定领域最佳）

  • SFT + 高质量领域数据
  • RLHF 引导"诚实"（奖励说真话，惩罚瞎猜）

第五道：不确定性量化（UQ）（前沿技术）

  • 基于 token 概率分布
  • 基于多次采样一致性
  • 基于模型内部状态监控

风险分层管控

风险等级 场景 必须措施
🔴 高 医疗/法律/金融 RAG + 人工审核 + 输出验证 + 免责声明
🟡 中 客服/内容生产/代码辅助 Prompt 约束 + RAG + 输出验证 + 置信度阈值
🟢 低 头脑风暴/草稿/创意 基础 Prompt 优化

🧬 补充专题：RAG 范式演进 —— 从 Vector RAG 到 PageIndex

补充自公众号「小码AI笔记」《RAG入门：一文搞懂向量RAG、BM25、知识图谱(GraphRAG)、SAG、PageIndex工作逻辑、演进》（2026-07-23）。 核心观点：「干翻 RAG」多是吸引眼球的噱头，这些新技术大都属于广义 RAG。RAG 存在的目的就是解决大模型上下文受限与幻觉问题 —— 给 LLM 外挂一个知识库，问答时给它「塞小抄」。其中最难的部分是检索的构建（做知识库其实就是在做检索引擎）。

演进总览

阶段 范式 核心思路 解决什么
RAG 1.0 Vector RAG 解析 → 切片 → 向量化 → 向量召回 知识注入的基本盘
RAG 1.5 混合检索 向量 + BM25 关键词双路 精确匹配短板
RAG 2.0 GraphRAG LLM 提取实体关系，构建知识图谱 多跳推理
演进增强 SAG / SQL-RAG 实体、事件存 SQL，向量+SQL 动态拼接 GraphRAG 太贵、太慢
另辟蹊径 PageIndex 无向量、不切片，LLM 导航目录树 摆脱切片/向量依赖

RAG 1.0 的地基：向量为什么能「理解」语义

  • Embedding 把词句转成数字序列：苹果 -> [0.8, 0.7, 0.9]（实际常是 1024 维高维空间）
  • 含义相近 → 向量空间距离近：苹果≈香蕉，苹果⇎电脑；用空间距离判断语义相似度

向量检索的三大短板

  1. 缺乏多跳推理：「张三在李四的公司做过什么项目？」
  2. 无法应对复杂逻辑/条件筛选查询：「2025 年之后、Agent 落地、大于 5000 字的调研报告」—— 这在 SQL 数据库里轻松拿捏
  3. 容易产生语义噪音：「我去年买了台苹果电脑」与「我昨天吃了个苹果」向量化后数值很近，会被判为高相关，不相关内容进入上下文拉低回答质量

一句话：向量只擅长基于语义的「模糊匹配」。

RAG 1.5：混合检索（向量 + BM25）

关键点 说明
名字来历 BM = Best Match（最佳匹配），25 = 第 25 次算法调整的版本（前 24 次都不太行）
历史 上世纪 90 年代诞生，很多搜索引擎的底层算法
核心逻辑 看关键词在文中出现的次数与稀有度：次数越高、越稀有，文档权重越高（排前面）
工程现状 Milvus 已内置 BM25 与混合检索模式；向量 + BM25 已成主流知识库标配

RAG 2.0：GraphRAG

图数据库把知识变成一张带关系的网：

  • 节点 = 知识的「实体」：人物、地点、事件、公司等
  • 边 = 知识的「关系」：任职于、发生在、推出等

例：「张三在 2026 年加入了腾讯公司，主要负责知识库产品 ima 的开发」→

张三 - 2026年加入 -> 腾讯公司
张三 - 负责开发 -> ima知识库
腾讯公司 - 拥有产品 -> ima知识库

构建流程（实体关系主要靠 LLM 提取，人工提取不现实；注意还是需要分片，向量化是为了以后的混合检索）：

文档解析 → 文本分片 ─┬→ 提取实体关系 → 全局融合(合并去重) → 存入图数据库
                    └→ 计算文本向量化 → 存入向量数据库

多跳推理（图数据库的强项）：问「张三的公司做了什么产品？」→ ① 找到"张三" → ② 顺边找到"腾讯" → ③ 找到"ima 知识库"。基于 2 次关系即得答案，数据再大，图数据库处理关系检索也极快。

GraphRAG 三大痛点：

痛点 说明
⚠️ 幻觉悖论 靠 LLM 提取实体关系，LLM 自身就有幻觉 —— 本想用 RAG 治幻觉，构建 RAG 时先引入了幻觉
💰 成本高 LLM 提取实体关系的 token 消耗巨大
🐢 维护慢 一个文件的更新可能要重算整个图关系

关联：LightRAG（开源）= GraphRAG 轻量版，图增强文本索引 + 双层检索，大幅降低 Token 开销。对需要全局理解的问题（财报分析、合同义务梳理），GraphRAG 类方案比传统 RAG 效果更好。

演进增强：结构化 RAG / SAG（SQL-RAG）

思路转变：不建复杂的「全局图」，把分片抽成「实体」「事件」存入 SQL 数据库，用户提问时通过 SQL 语句动态拼接关联事件。

  • 向量依然是 C 位：SAG 本质 = 向量 RAG 之上加一层 SQL 结构查询
  • 落地简化版：给 Chunk 打标签（LLM 提取关键词），检索时经 Chunk 映射用 SQL 回查关系数据库

数据模型（两张表）：

表 记录内容
事件表 事件内容、发生时间
实体关联表 哪个事件提到了哪个实体

例：「张三在 2026 年加入腾讯，负责 ima 开发」被 LLM 提取为 → 事件：张三入职腾讯并开发 ima（发生时间：2026年）；关联实体：张三、腾讯、ima

多跳查询执行链条（向量语义检索 × SQL 精确查询「双剑合璧」）：

1. 向量语义搜索找到"种子"Chunk
2. 经 Chunk 映射取出 SQL 中的实体、事件
3. 拿实体到 SQL 精确查询，拿到所有相关事件
4. 原始 Chunk + SQL 拼出的事件结果一起打包注入 LLM 上下文

实战例子 —— 问「2026 年加入腾讯的那个谁，他以前在阿里做什么？」： 向量匹配含"腾讯"的 Chunk → 映射出实体"腾讯" → SQL 精确查询 → 事件「张三 2026 入职腾讯」→ 发现新实体"张三" → 继续 SQL 查询 → 拿到张三的全部经历与事件（2 跳，等价于图数据库的多跳查询）。

事件的双重角色：既是检索的桥梁和线索，又是注入上下文的高纯度「小抄」。

  • 📄 论文：arxiv.org/abs/2606.15971
  • 💻 开源参考仓库：github.com/Zleap-AI/SAG

SAG 依然是 RAG。能否替代 GraphRAG 尚无定论，但其思想值得学习 —— 用更低成本轻量实现"图能力"。

另辟蹊径：PageIndex —— 无向量、不切片

由 Vectify AI 提出（开源：github.com/VectifyAI/PageIndex），完全不用向量、不切片，工作逻辑非常像人类查资料：先通过目录看答案在第几页，再翻到对应页码。

流程：

文档解析 → LLM 构建目录树(JsonTree：章节/节点/页码行数定位/摘要) → 目录树存储
        → 问答时 LLM 看目录树定位章节 → 返回原文对应正文 → 完整注入上下文

两点局限：

  1. 每一步都强依赖 LLM（构建目录索引、摘要、检索导航）→ 小尺寸模型玩不转：能力不足、幻觉严重，目录树都建不好
  2. 海量文档难应对：单篇 100 页的文档问答挺好，100 篇？1000 篇呢？

海量文档的两个思路：

  • 先用向量检索缩小命中范围，再对命中的文档分别注入 JsonTree
  • 给整体文档建立文件级目录树，让 AI 像人浏览文件夹一样一级级打开子目录

范式选型结论

  • 没有最好的单一选择，实际落地通常多种模式混合使用
  • 向量 RAG + BM25：企业知识库落地最扎实、性价比最高的路径 ⭐
  • GraphRAG：补全多跳推理的关系检索
  • SAG：值得尝试的轻量化"图能力"实现
  • 🏆 推荐项目：腾讯开源企业级 RAG 知识库 WeKnora（1.8 万 Star，开箱即用，支持 Wiki）

💡 技术没有绝对的优劣，只有最适合业务的场景。

📝 总结速查

问题 核心答案
RAG 是什么？ 检索增强生成，给大模型开卷考试
工作流程？ 索引（离线建库）+ 查询（在线检索+生成）
微调 vs RAG？ 微调「内化知识」，RAG「外挂参考书」，互补
文档切割？ 递归字符切割起步，结构/语义切割进阶
Re-rank？ Cross-Encoder 精排，准确率提升 30-50%
Embedding？ Word2Vec → BERT → BGE-M3 → LLM-based
向量数据库？ Milvus/Pinecone/Weaviate 按需选型
多路召回？ 向量 + BM25 混合，RRF 融合，提升 10-30%
效果量化？ RAGAS 评估 Faithfulness/Relevance 等
幻觉怎么降？ Prompt → RAG → 输出验证 → 微调 → UQ 分层设防
范式演进？ Vector RAG → 混合检索(BM25) → GraphRAG → SAG → PageIndex，混合使用
