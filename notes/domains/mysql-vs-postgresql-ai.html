MySQL vs PostgreSQL vs SQLite：对比、AI 时代选型与学习曲线

面向想学关系型数据库的开发者。结论可直接看文首摘要。

N 我的笔记库 知识领域 阅读约 9 分钟
On this page

面向想学关系型数据库的开发者。结论可直接看文首摘要。

摘要

问题 简答
核心区别 MySQL 偏「简单够用、生态广」；PostgreSQL 偏「标准严、类型与扩展强」；SQLite 偏「嵌入式、零运维、单文件」
AI 时代更该学哪个 服务端 AI/RAG 优先 PostgreSQL；本地 Agent、桌面端、移动端和测试场景补 SQLite；MySQL 仍值得会基础
是否只学一个 先深 PostgreSQL 或 MySQL，再快速补 SQLite；三者共同底层仍是关系模型、SQL、索引和事务
学习曲线 SQLite 入门最平；MySQL 入门平且生态广；PostgreSQL 入门略陡，中后期上限更高

1. 它们分别是什么

  • MySQL：开源关系型数据库，长期以 Web/业务库为主。常见发行版：官方 MySQL、MariaDB（兼容分叉）、云厂商托管版（RDS 等）。
  • PostgreSQL（常称 Postgres）：开源对象-关系型数据库，强调 SQL 标准符合度与可扩展性。云上常见 Aurora PostgreSQL、Cloud SQL、阿里云 RDS PostgreSQL、Neon、Supabase 等。
  • SQLite：嵌入式关系型数据库，以一个本地文件提供 SQL、事务和索引能力，不需要独立数据库服务。常见于桌面端、移动端、边缘设备、测试环境和本地优先应用。

三者都能完成表、索引、CRUD 和事务，但部署模型完全不同：MySQL/PostgreSQL 是客户端—服务器数据库，SQLite 是进程内嵌入式数据库。

2. 主要区别（实用向）

2.1 定位与哲学

维度 MySQL PostgreSQL SQLite
设计倾向 简单、快、够用，InnoDB 为主 功能完整、标准优先、扩展丰富 零配置、嵌入式、单文件
SQL 标准 相对宽松，有不少方言 更贴近标准，复杂查询能力强 SQL 能力完整但有自己的限制和方言
典型印象 PHP/LAMP、电商、CMS、存量业务 分析型查询、GIS、复杂约束、AI/数据平台 手机 App、桌面软件、CLI、测试、边缘设备
部署方式 独立服务 独立服务 进程内库，无需单独服务

2.2 数据类型与建模

能力 MySQL PostgreSQL SQLite
JSON 有 JSON 类型与函数，实用 JSON/JSONB 成熟，JSONB 可索引 JSON1 扩展可用，但类型和生态更轻量
数组 / 复合类型 弱 原生数组、复合类型、范围类型丰富 没有原生数组/复合类型，通常用表或 JSON 表达
类型系统 常见类型够用，部分行为较宽松 类型系统最丰富，约束表达力强 动态类型 + type affinity，需更重视约束和校验
全文检索 有，能力中等 内置较好；还可接扩展 FTS5 适合本地全文搜索
GIS 有空间类型 PostGIS 是业界标杆 依赖 SpatiaLite 等扩展

2.3 事务、并发与可靠性

维度 MySQL (InnoDB) PostgreSQL SQLite
事务 成熟 ACID 成熟 ACID，MVCC 模型清晰 成熟 ACID，事务边界简单
并发 适合服务端高并发 适合服务端复杂并发 多读可并行，但同一数据库写入通常是单写者
DDL 历史上不少操作会锁表；新版本改善中 许多 DDL 可较友好；仍需注意长事务 迁移能力更简单，复杂变更通常需重建表
复制 / 高可用 异步/半同步等，生态成熟 逻辑复制、物理复制都很强 无内置服务端复制和集群能力，需应用或外部工具解决
用户与权限 服务端权限体系 角色、权限和 RLS 丰富 没有服务端用户体系，权限主要由文件系统控制

细节差异多，业务正确性都依赖正确用事务与约束，不要只靠默认隔离级别「感觉」。

2.4 扩展与生态

维度 MySQL PostgreSQL SQLite
插件/扩展 相对封闭，能力多在内核与周边工具 扩展极其丰富（PostGIS、pgvector、Timescale、Citus 等） 可加载扩展；JSON1、FTS5 常见，向量扩展生态仍较分散
ORM / 框架 几乎所有框架一流支持 同样一流支持 几乎所有语言都有驱动，适合嵌入式应用
运维资料 / 招聘 国内岗位与历史资料非常多 云原生与数据岗里很常见 更常作为应用内置数据库，较少单独招聘 DBA
云托管 到处都有 到处都有，现代后端常见 通常不需要托管，直接随应用部署

2.5 性能直觉（避免神话）

  • 没有绝对谁更快：取决于 schema、索引、查询、硬件、缓存与工作负载。
  • 简单主键点查、高并发短事务：两者都能做得很好。
  • 复杂 JOIN、窗口函数、分析型 SQL、半结构化 + 向量混合查：Postgres 往往更省心。
  • MySQL 在大量互联网存量系统里被调得很透，运维经验可以转化为性能。
  • SQLite 在单机、小数据量和本地读写场景中延迟很低，但不能把“单文件简单”误解为适合高并发写入、跨机器集群或大型服务端主库。

2.6 许可与发行版注意点

  • MySQL：Oracle 公司主导；生产常见 InnoDB。注意与 MariaDB 的兼容边界（不是 100% 相同）。
  • PostgreSQL：许可宽松（PostgreSQL License），分叉与云厂商改动多，但 SQL 与扩展生态仍以社区 Postgres 为共同语言。
  • SQLite：核心代码属于公有领域，适合嵌入商业软件；具体发行包、扩展和周边工具仍需单独查看许可证。

3. AI 时代应该学哪个？

3.1 推荐顺序（2025–2026 实用建议）

  1. 服务端 AI 主学：PostgreSQL
    原因与 AI/现代应用叠合度高： - pgvector（及同类扩展）把向量检索放进同一库，RAG/语义搜索原型极常见； - JSONB 适合存 LLM 结构化输出、元数据、工具调用结果； - 丰富 SQL（窗口、CTE、UPSERT）利于特征表、分析与管道； - 现代 BaaS / 开源栈默认 Postgres：Supabase、Neon、许多 Agent 记忆/会话存储示例。
  2. 求职与存量业务补学：MySQL 基础
    存量系统、面试、外包与传统业务库仍大量是 MySQL/MariaDB；会「读写模型 + 索引 + 事务」即可快速上手。
  3. 本地应用与实验补学：SQLite
    - 适合本地优先 Agent、桌面应用、移动端、CLI 工具和自动化测试； - 无需安装服务，复制一个数据库文件即可运行和迁移； - 可以存本地会话、工具调用日志、轻量 Memory、配置和缓存； - 但不适合作为多实例高并发服务、复杂权限系统或大规模集群的唯一主库。

3.2 什么时候反而应主攻 MySQL？

  • 团队/公司技术栈明确是 MySQL，且你短期要交付业务；
  • 岗位 JD 明确要求 MySQL 深度（复制、InnoDB、大厂中间件）；
  • 维护已有 MySQL 为主的遗产系统。

此时仍建议抽时间了解 Postgres + pgvector，避免 AI 相关项目完全陌生。

3.3 「AI 只用向量库，还要不要 SQL？」

要。向量库（Milvus、Qdrant、云向量服务等）解决相似度检索；真实系统仍需要：

  • 用户/权限/订单等事务数据；
  • 文档元数据、会话、审计、计费；
  • 与业务 JOIN、过滤、一致性。

模式经常是：Postgres（业务 + 元数据 ± 向量） 或 Postgres + 专用向量库。学好关系库不会过时。

本地优先 Agent 也可以采用 SQLite（会话/Memory/日志）+ 专用向量库，或 SQLite 配合本地向量扩展；但向量生态和并发能力不如 PostgreSQL + pgvector 统一。

3.4 一句话选型

为 AI 应用、副业与长期通用能力 → PostgreSQL 优先。
为入职传统业务组、改存量 → MySQL 也必须会。
为本地 Agent、桌面端、移动端和测试 → SQLite 优先。
理想状态：Postgres 深 + MySQL 熟 + SQLite 会用会取舍。

4. 学习曲线

4.1 总体对比

难度（主观）
入门:     SQLite ●○○○○  <  MySQL ●●○○○  <  PostgreSQL ●●●○○
进阶 SQL: MySQL ●●●○○  ≈  PostgreSQL ●●●●○（PG 天花板更高）
运维复制: MySQL ●●●●○  ≈  PostgreSQL ●●●●○（路径不同）
本地应用: SQLite ●●○○○  >  MySQL ●○○○○ / PostgreSQL ●○○○○
AI/扩展:  MySQL ●●○○○  <  SQLite ●●●○○  <  PostgreSQL ●●●●○
  • MySQL：教程多、中文资料多、XAMPP/宝塔/云 RDS 一键多，第一周就能做 CRUD + 索引。
  • PostgreSQL：概念（schema、角色、扩展、JSONB、MVCC 可见性）稍多，第一周也能做 CRUD，到 JSONB/窗口函数/扩展时斜率变陡，但换来的能力更值钱。
  • SQLite：几乎零安装成本，一个文件即可开始，最适合快速学习 SQL、做 Demo、写测试和构建本地应用；进阶难点主要转向并发写入、迁移、文件锁和数据备份，而不是服务端集群运维。

4.2 分阶段路径（通用，可套在任一库）

阶段 目标 大致时间（业余） 内容
L0 入门 会装会连会查 3–7 天 安装/Docker、客户端、库表、CRUD、主键
L1 建模 不写出灾难 schema 1–2 周 范式直觉、外键、索引（BTree）、EXPLAIN 入门
L2 事务 写对业务一致性 1–2 周 事务、隔离级别直觉、锁与死锁、连接池
L3 查询 复杂报表与性能 2–4 周 JOIN、子查询、CTE、窗口函数、慢查询
L4 生产 敢上线 持续 备份恢复、复制、迁移、监控、权限
L5 AI 向 能做 RAG 存储 1–2 周叠加 JSONB、全文、pgvector、混合检索取舍

4.3 PostgreSQL 建议练习项目（AI 向）

  1. 用户表 + 文章表 + 标签（多对多）+ 基础索引；
  2. 用 JSONB 存「LLM 抽取的结构化字段」，并建表达式索引；
  3. 接入 pgvector：文档块 embedding 入库，做 top-k 相似检索 + 元数据过滤；
  4. 简单会话/记忆表：多轮对话消息、token 用量审计。

4.4 MySQL 建议练习项目（补齐向）

  1. 同样的用户/文章模型用 MySQL 实现一遍；
  2. 看懂 EXPLAIN，人为制造并消灭全表扫描；
  3. 了解 binlog 与「备份 + 时间点恢复」概念即可（不必一上来深挖源码级）。

4.5 SQLite 建议练习项目（本地 Agent 向）

  1. 做一个 CLI 记账或待办应用：练习单文件数据库、CRUD、事务和迁移；
  2. 做一个本地 Agent 会话库：保存 sessions、messages、tool_calls、artifacts 和 token_usage；
  3. 用 WAL 模式观察多读单写、锁等待和事务边界；
  4. 用 FTS5 做本地文档全文搜索，再与向量检索组合；
  5. 把 SQLite 作为测试数据库，验证 Repository、事务回滚和数据迁移。

SQLite 练习的重点不是把它改造成“微型 PostgreSQL”，而是理解嵌入式数据库、文件持久化和本地优先应用的取舍。

4.6 从 A 迁到 B 难不难？

不难。难的是索引设计、事务边界、SQL 方言与运维习惯，不是「另一个产品要从零学语言」。
学会：

  • 关系模型与索引；
  • 事务与隔离；
  • EXPLAIN / 慢查询；

之后换引擎主要是查文档对齐语法（分页、UPSERT、JSON 函数名等）。

5. 速查：功能对照（常见点）

需求 更常选
个人项目 / AI demo / Supabase PostgreSQL
WordPress、老电商、大量 PHP 遗产 MySQL/MariaDB
本地 CLI、桌面端、移动端、自动化测试 SQLite
地理信息 PostgreSQL + PostGIS
向量检索与库内 RAG PostgreSQL + pgvector（或专用向量库）
本地轻量检索 / 离线 Agent Memory SQLite + FTS5（向量需求再加扩展或专用库）
纯高并发简单 KV 式业务表 两者都行，看团队
严格约束、复杂分析 SQL PostgreSQL
国内初级岗面试高频 两者都问，MySQL 题海更大

6. 学习资源（精简）

PostgreSQL

  • 官方文档：https://www.postgresql.org/docs/
  • 互动练习：https://pgexercises.com/
  • 向量扩展：https://github.com/pgvector/pgvector

MySQL

  • 官方文档：https://dev.mysql.com/doc/
  • 重点抓：InnoDB、索引、事务、EXPLAIN

SQLite

  • 官方文档：https://www.sqlite.org/docs.html
  • 重点抓：单文件模型、事务、WAL、锁、类型亲和性、FTS5、备份与迁移

共通

  • 任意一本「SQL 基础 + 索引」教程；
  • 用 Docker 起库，避免一上来纠结安装细节；
  • 在真实小项目里练，比只刷题有效。

7. 结论清单

  • 默认主线选 PostgreSQL，尤其计划做 AI/RAG/现代后端。
  • 用 Docker 起一个 Postgres，完成 L0–L2，再加 JSONB + pgvector 小项目。
  • 抽时间用 MySQL 把同一模型重做一遍，熟悉方言与生态。
  • 用 SQLite 做一个本地 Agent 会话/Memory 或 CLI 小项目，理解嵌入式数据库和 WAL。
  • 不要陷入「谁性能第一」争论；先保证建模、索引、事务正确。
  • 向量能力是加分项，关系建模与 SQL 基本功仍是底座；SQLite 适合本地，PostgreSQL 适合服务端 AI。
