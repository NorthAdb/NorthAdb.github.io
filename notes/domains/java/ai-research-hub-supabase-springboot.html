目标：从 0 构建一个“个人/团队 AI 知识库 + Agent”Demo，逐步演进出一套现代后端架构。

核心思想：先跑通最小闭环，再逐层增加 Redis / Kafka / Elasticsearch / Agent / Docker / CI/CD / Monitoring。

本文既是学习路线，也是可以直接交给 Coding Agent 执行的项目规格。

1. 项目定位

1.1 项目名称

AI Research Hub

一个支持以下能力的知识库应用：

  • 用户注册 / 登录
  • 创建知识库
  • 上传 PDF / Markdown
  • 文档解析与切分
  • Embedding
  • PostgreSQL + pgvector 向量检索
  • BM25 / Hybrid Search
  • Reranker
  • RAG 问答
  • 文档引用（Citation）
  • Agentic RAG
  • 异步文档处理
  • 缓存、搜索、消息队列
  • Docker 本地开发
  • CI/CD
  • Monitoring

4. 非目标（第一版不要做）

为了避免 Coding Agent 过度设计，第一版明确不做：

  • 微服务拆分
  • Kubernetes
  • Service Mesh
  • 多 Region
  • 复杂 RBAC
  • 分布式事务
  • 自建向量模型
  • 自建 LLM
  • 多租户企业级权限体系
  • 高可用 Kafka 集群
  • 高可用 Elasticsearch 集群

第一目标永远是：

一个开发者可以在本地和 Supabase 云环境中跑通完整 Demo。

12. Chunking 最低要求

第一版支持：

  • 固定 Token / 字符长度
  • overlap
  • metadata

例如：

{
  "source": "paper.pdf",
  "page": 3,
  "section": "Introduction"
}

推荐默认：

chunk_size = 500 ~ 1000 tokens
overlap = 50 ~ 150 tokens
top_k = 5 ~ 10

实际参数不要硬编码在业务逻辑中，统一配置。

14. Phase 7：Redis

当以下问题出现时加入 Redis：

  • 高频重复查询
  • LLM 成本较高

第一版只做：

Query Cache

 └── MISS
       ↓
      RAG
       ↓

不要一开始让 Redis 承担所有状态。

17. Phase 10：Elasticsearch

此时再引入 Elasticsearch。

为什么

PostgreSQL：

  • 业务主数据
  • 事务
  • pgvector
  • 基础全文搜索

Elasticsearch：

  • 复杂全文搜索
  • Search-as-you-type
  • 高亮
  • Facet / Aggregation
  • 日志分析（后续）

架构

                  Search Service
                       │
              ┌────────┴────────┐
              ▼                 ▼
         PostgreSQL        Elasticsearch
         业务 / vector     full-text / BM25

注意：

Elasticsearch 不替代 PostgreSQL。

PostgreSQL 仍然是主要业务数据源。

27. Coding Agent 实现时的约束

把下面这些原则直接交给 Coding Agent：

原则 1：先做能运行的最小版本

每一个 Phase 必须：

实现
 ↓
运行
 ↓
验证
 ↓
再进入下一阶段

不要一次性生成整个系统。

原则 2：不要无理由增加依赖

每加入一个组件必须回答：

为什么需要？
解决什么问题？
没有它会怎样？

原则 3：数据库优先于“伪造的数据层”

必须真实连接 PostgreSQL。

禁止第一版大量使用：

  • Mock Repository
  • In-memory database
  • Fake vector search

原则 4：配置外置

例如：

DATABASE_URL
SUPABASE_URL
SUPABASE_ANON_KEY
SUPABASE_SERVICE_ROLE_KEY
REDIS_URL
KAFKA_BOOTSTRAP_SERVERS
ELASTICSEARCH_URL
LLM_API_KEY
EMBEDDING_API_KEY

敏感信息不要进入 Git。

原则 5：保留可替换接口

例如：

interface EmbeddingService
interface RerankerService
interface LlmService
interface SearchService
interface DocumentParser

这样以后替换 OpenAI / Claude / DeepSeek 不需要大范围修改业务代码。

30. 最终你应该真正理解的东西

完成这个 Demo 后，不是只得到一个项目，而应该形成下面这张“技术地图”：

最终形成的认知应该是：

Supabase 不等于 Spring Boot。

Supabase 负责 PostgreSQL、Auth、Storage、Realtime 等通用后端能力； Spring Boot 负责复杂业务逻辑和应用层编排； Redis / Kafka / Elasticsearch 分别解决缓存、异步消息、复杂搜索； pgvector / RAG / Agent 构成 AI 应用层； Docker / CI/CD / Monitoring 负责工程化交付。
