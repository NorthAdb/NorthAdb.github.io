Agent Eval：智能体评估体系、组成与主流框架

核心结论

Agent Eval 不是某一个框架，而是一套用于验证 Agent 是否“正确、稳定、安全、高效”完成任务的工程体系。

核心组成：

Dataset + Environment + Runner + Trace + Evaluator + Metrics + Regression + CI/Production Feedback

LangSmith、Promptfoo、Langfuse、Braintrust、Phoenix、Opik、DeepEval、Inspect AI 等，都是这套体系在不同层面的实现。

1. Agent Eval 是什么？

传统 LLM Eval 主要回答：

“模型回答得好不好？”

典型流程：

Input
  ↓
Prompt
  ↓
LLM
  ↓
Answer
  ↓
Score

而 Agent 是一个多步骤执行系统：

User Task
    ↓
Agent
 ├── LLM Call
 ├── Tool Call
 ├── Tool Result
 ├── State Update
 ├── LLM Call
 ├── Retry
 └── Final Answer

因此 Agent Eval 不只评价最终答案，还评价：

  • 是否完成任务
  • 是否选择了正确工具
  • 工具参数是否正确
  • 工具调用顺序是否合理
  • 是否出现无意义调用、循环、异常重试
  • 是否正确修改系统状态
  • 是否违反安全与权限策略
  • Token、成本、延迟是否合理
  • 多次执行是否稳定

Agent Eval = 对 Agent 整个执行过程和最终结果进行系统化评估。

维度 LLM Eval Agent Eval
输入 Prompt Task + Environment
输出 Text Action Sequence + Final Output

Judge 常见 更复杂

可以记成：

LLM Eval
    ↓
回答好不好？

Agent Eval
    ↓
任务完成没有？
+
过程对不对？
+
工具调用对不对？
+
状态改对了吗？
+
安全吗？
+

3. 为什么 Agent Eval 特别需要 Trace？

Agent 与普通 LLM 最大的区别之一，就是存在大量中间行为。

例如：

用户：
“给 order_123 退款”

Agent：

1. LLM 分析任务
2. get_order(order_123)
3. get_user(user_456)
4. 检查用户身份
5. refund(order_123)
6. Final Answer

最终可能只返回：

退款成功

但只看最终答案无法判断：

  • 有没有验证用户身份？
  • 有没有调用错误的订单？
  • 有没有绕过权限？
  • 有没有重复退款？
  • 有没有进行无意义工具调用？
  • 花了多少 Token？
  • 是否经历了错误重试？

因此需要保存：

Trace = Agent 一次完整执行过程的结构化记录。

4. Trace 的基本结构

Trace
├── User Input
├── Agent Version
├── Model
├── Prompt Version
├── LLM Call
│   ├── Input
│   ├── Output
│   ├── Token Usage
│   └── Latency
├── Tool Call
│   ├── Tool Name
│   ├── Arguments
│   ├── Result
│   ├── Error
│   └── Latency
├── Retrieval
├── State Change
├── Retry
├── Final Output
├── Total Cost
└── Total Latency

Trace 的重点是记录 Agent 的外部执行行为和系统状态，不等于记录模型内部 Chain-of-Thought。

对于 Agent Harness 来说，更重要的是：

LLM
 ↓
Decision
 ↓
Tool
 ↓
Result
 ↓
State
 ↓
Next Decision

5. Agent Eval 的核心组成

5.1 Dataset：测试集

Dataset 是 Eval 的输入。

最简单：

{
  "task": "查询订单123",
  "expected": "paid"
}

Agent Eval 往往需要更丰富的信息：

{
  "task": "给订单123退款",

  "initial_state": {
    "order_status": "paid",
    "user_verified": true
  },

  "expected_state": {
    "order_status": "refunded"
  },

  "constraints": [
    "must_verify_user",
    "must_not_refund_twice"
  ]
}

因此 Agent Dataset 不一定只有：

input
expected_output

还可能包含：

task
initial_state
available_tools
expected_state
constraints
reference_trajectory
metadata

Dataset 的来源

人工编写
    ↓
历史生产 Trace
    ↓
失败案例
    ↓
用户反馈
    ↓
人工标注
    ↓
Regression Dataset

6. Environment：Agent 所处的环境

这是 Agent Eval 与普通 LLM Eval 的一个关键区别。

例如 Coding Agent：

Agent
 ├── File System
 ├── Shell
 ├── Git
 ├── Network
 └── Package Manager

客服 Agent：

Agent
 ├── CRM
 ├── Order DB
 ├── Payment API
 └── User Profile

Eval 需要能够控制这些环境。

例如：

Case 1
order = paid

Case 2
order = already_refunded

Case 3
user = not_verified

Case 4
payment_api = timeout

Case 5
get_order = 500

然后观察 Agent：

Tool Error
    ↓
Agent
 ├── Retry
 ├── Fallback
 ├── Stop
 └── Infinite Loop

这类测试可以验证：

Agent 的错误恢复能力。

7. Runner：执行 Agent

Runner 负责真正把测试 Case 跑起来。

Dataset
   ↓
Runner
   ↓
Reset Environment
   ↓
Run Agent
   ↓
Capture Trace
   ↓
Evaluator
   ↓
Score

伪代码：

for testcase in dataset:
    reset_environment(testcase)

    trace = run_agent(
        task=testcase["task"],
        tools=tools,
        state=testcase["initial_state"]
    )

    score = evaluate(
        trace,
        testcase
    )

    save_result(trace, score)

Runner 本质上需要解决：

如何让被测试的 Agent 在可控、可重复的环境中执行。

被测试对象通常称为：

SUT（System Under Test）

8. Evaluator：如何判断 Agent 是否正确？

Evaluator 是 Agent Eval 的核心。

主要可以分成以下几类。

8.1 Code Evaluator

通过确定性代码判断。

def evaluate(result):
    return result["order_status"] == "refunded"

可以检查：

JSON 是否合法
Tool 是否正确
参数是否正确
文件是否存在
文件内容是否正确
数据库状态是否正确
Exit Code 是否为 0

基本原则：

能用代码判断的问题，优先不要用 LLM Judge。

原因：

  • 确定性高
  • 成本低
  • 可解释性强
  • 适合 CI

8.2 Trajectory Evaluator

Agent 的执行轨迹：

A → B → C → D

可以直接进行评估。

例如要求：

get_user
    ↓
check_permission
    ↓
refund

实际却是：

get_order
    ↓
refund

应该失败。

但通常不应该要求 Agent 100% 复刻某个专家轨迹，因为可能存在多个合理解法。

Strict

完全匹配：

Expected:
A → B → C

Actual:
A → B → C

Subset

要求某些关键步骤必须出现：

A、B 必须出现

实际允许：

X → A → Y → B

Superset

只要求实际轨迹包含最基本的必要步骤：

A → B

实际可以：

A → X → Y → B

核心问题：

哪些行为是必须的，哪些行为可以自由变化？

8.3 LLM-as-a-Judge

对于难以用规则判断的问题：

这个回答是否完整？
这个方案是否合理？
有没有明显幻觉？
工具使用是否适当？
是否真正解决了用户问题？

可以让另一个 LLM 作为 Judge。

Agent Trace
    ↓
Judge LLM
    ↓
Rubric
    ↓
Score

例如：

评分标准：

1. 是否正确完成任务？
2. 工具是否使用合理？
3. 是否存在未经授权的操作？
4. 最终回答是否准确？

输出可以是：

{
  "score": 0.85,
  "pass": true,
  "reason": "..."
}

优点

  • 灵活
  • 能处理复杂语义
  • 能评价开放式任务

缺点

  • Judge 本身可能判断错误
  • 成本更高
  • 存在 Judge Bias
  • 稳定性不如确定性代码

8.4 Agent-as-a-Judge

进一步发展：

普通 LLM Judge

Trace
 ↓
LLM
 ↓
Score

变成：

Evaluator Agent
 ├── 查看 Trace
 ├── 分析 Tool Call
 ├── 检查 State
 ├── 调用辅助工具
 └── 输出 Score

例如判断：

“Agent 是否违反退款政策？”

Evaluator Agent 可能需要：

读取 Trace
    ↓
找到 refund Tool Call
    ↓
查看用户身份
    ↓
查询退款政策
    ↓
检查订单状态
    ↓
综合判断

也就是说：

Evaluator 本身也是一个 Agent。

8.5 Human Evaluation

自动 Eval 不是万能的。

典型流程：

Automatic Eval
      ↓
发现疑难 Case
      ↓
Human Review
      ↓
人工标注
      ↓
加入 Dataset

尤其对于：

高风险任务
安全
权限
金融
医疗
复杂业务规则

不能完全依赖自动 Judge。

9. Agent Eval 的主要评价维度

可以把核心指标记成：

Outcome
Trajectory
Tool
State
Safety
Efficiency
Reliability

9.1 Outcome：任务成功率

最重要的指标。

100 个 Task
82 个成功

Task Success Rate = 82%

9.2 Trajectory：路径质量

关注：

Tool Selection
Tool Ordering
Planning
Unnecessary Steps
Loops
Retry

9.3 Tool Correctness：工具调用正确性

检查：

Tool Name
Tool Arguments
Tool Order
Tool Result Handling

例如：

{
  "tool": "refund_order",
  "order_id": "123"
}

检查：

Tool 是否正确？
参数是否正确？
参数是否完整？
是否调用非法工具？

9.4 State Correctness：最终状态正确性

这是 Agent Eval 非常重要的指标。

例如：

Agent：
“订单已经成功退款”

不能只看文本，还应该检查实际系统状态：

SELECT status
FROM orders
WHERE id = '123';

是否真的变成：

refunded

因此：

State-based Evaluation 往往比只检查 Final Answer 更可靠。

9.5 Safety / Policy

例如：

未认证用户
    ↓
要求退款

Agent
    ↓
直接 refund

虽然最终回答：

退款成功

但 Eval 应该：

FAIL

原因：

Policy Violation

常见安全评估包括：

Prompt Injection
权限越权
Tool Misuse
敏感信息泄漏
危险操作
Policy Violation

9.6 Efficiency：效率

不仅判断：

成功 / 失败

还要判断：

Steps
Tool Calls
Token
Cost
Latency
Retries

例如：

Agent Success Steps Cost Latency
A ✅ 6 $0.03 4s
B ✅ 34 $0.62 47s

两者成功率一样，但 Agent A 更高效。

9.7 Reliability：稳定性

Agent 有明显的随机性。

一次成功：

run 1 → success

并不能证明稳定。

应该多次运行：

run 1 → success
run 2 → success
run 3 → fail
run 4 → success
run 5 → fail

关注：

Pass Rate
Consistency
Pass@k
Pass^k

17. 从 0 搭一个最小 Agent Eval

其实完全没必要一开始就上完整平台。

可以先自己实现一个最小版本：

eval/
├── dataset.jsonl
├── runner.py
├── evaluator.py
├── metrics.py
└── results.jsonl

{"task":"查询订单123","expected_status":"paid"}
{"task":"退款订单456","expected_status":"refunded"}
{"task":"查询订单789","expected_status":"cancelled"}

runner.py

for case in dataset:
    reset_env(case)

    trace = run_agent(case["task"])

    score = evaluate(
        trace,
        case
    )

    save_result(
        trace,
        score
    )

evaluator.py

def evaluate(trace, case):
    return {
        "task_success": check_final_state(trace, case),
        "tool_correct": check_tools(trace),
        "policy_ok": check_policy(trace),
        "steps": len(trace.steps),
    }

metrics.py

task_success_rate
tool_error_rate
policy_violation_rate
average_steps

average_cost

CI

20. 一句话区分几个概念

概念 一句话理解
LLM Eval 模型回答得好不好
Agent Eval Agent 是否正确完成任务
Trace Agent 到底做了什么
Evaluator 如何判断它做得对不对
Dataset 拿什么题测试
Environment Agent 在什么世界里执行
Benchmark 一套标准化考试题
LangSmith Eval + Trace + Observability 平台
Promptfoo Eval + Testing + Assertion + Red Team
Regression Eval 新版本有没有把旧能力搞坏
Online Eval 线上真实 Agent 是否持续表现良好

最终可以把 Agent Eval 理解成：给 Agent 建立一套类似软件工程中 pytest + observability + CI/CD + benchmark 的质量保障体系。

21. 最值得记住的公式

Agent Harness
= 负责执行

Agent Eval
= 负责验证

Trace
= 连接执行与验证的证据

Benchmark
= 标准化测试任务 / 环境

LangSmith / Promptfoo / Langfuse / ...
= 将上述能力工程化的工具或平台
