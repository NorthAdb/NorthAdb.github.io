学习历程——天气预报员（Weather Reporter）重设计划

← 返回 README

概述

围绕一个贯穿始终的示例——天气预报员代理（weather reporter agent）——重设计从第 7 页开始的所有幻灯片。叙事弧线按照目录的可见顺序（代理 Agent → 技能 Skill → 上下文 Context → CLAUDE.md → 命令 Command + 工作流 Workflow）展开，让观众先认识天气预报员，然后理解他们知道什么、如何思考、遵循哪些规则，最后了解如何用一个命令触发他们。

当前章节 当前幻灯片 操作 新位置
主题 1：上下文 7-11（第 7 页为章节页） 移至主题 3 第 17-21 页
主题 2：CLAUDE.md 12-17（第 12 页为章节页） 移至主题 4 第 22-27 页
主题 3：代理 18-23（第 18 页为章节页） 移至主题 1 第 7-12 页
主题 4：技能 24-29（第 24 页为章节页） 移至主题 2 第 13-18 页
主题 5：命令 30-32（第 30 页为章节页） 与工作流合并为主题 5 第 28-32 页
主题 6：工作流 33-36（第 33 页为章节页） 合并入命令章节 （无独立章节页）

等等，让我重新计算：

当前：第 7-37 页 = 31 页。 - 代理章节：6 页（18-23）→ 成为主题 1（7-12） - 技能章节：6 页（24-29）→ 成为主题 2（13-18） - 上下文章节：5 页（7-11）→ 成为主题 3（19-23） - CLAUDE.md 章节：6 页（12-17）→ 成为主题 4（24-29） - 命令 + 工作流合并：3 + 1 章节页 + 4 内容页 = 命令（3）+ 工作流（1 章节页 + 3 内容页）= 7 页 → 成为主题 5（30-36） - 结束页：1 页（37）

新总数：37 页（没有页面被删除；工作流章节页成为合并后的命令+工作流章节的一部分——我们将其保留为子章节，或删除其 data-level 以避免出现第二个章节分隔符）。

决定：保留全部 37 页。删除原有工作流章节分隔符（第 33 页）的 data-level，使其被视为内容页而非章节分隔符。命令章节覆盖 30-36 页。工作流章节分隔符成为命令章节内的可视化"章节标题"。

实际上，更简单：将工作流章节分隔符保留为没有 data-level 的内容页。旅程栏保持在 commands 级别。章节编号文字从"主题 6"改为只是一个副标题。

2. 新 LEVELS 映射（键名和颜色不变）

新的章节顺序是：代理 Agent → 技能 Skill → 上下文 Context → CLAUDE.md → 命令 Command。workflow 级别键从 data-level 使用中退役（章节分隔符失去 data-level）。LEVELS 映射仍会携带 workflow 用于旅程栏历史显示，但没有幻灯片会触发它。

修订方案：由于没有幻灯片携带 data-level="workflow"，因此从 LEVELS 映射中彻底移除 workflow 级别。旅程栏最高到 commands（83%）。这没问题——工作流章节作为命令章节内部的高潮呈现，而非独立主题。

实际上旅程栏填充到 83% 而不是 100% 作为结尾章节感觉不够完满。更好的方案：将命令 + 工作流合并为一个名为"命令与工作流"的章节，使用 data-level="commands"。在 LEVELS 中将 workflow 级别保留为 100%，并将 data-level="workflow" 分配给原工作流章节分隔符页——它在命令章节内成为一个视觉过渡。这样旅程栏在工作流幻灯片处填充到 100%。

最终决定：在 LEVELS 中同时保留 commands（83%）和 workflow（100%）。将 data-level="commands" 分配给命令章节分隔符，将 data-level="workflow" 分配给工作流子章节页。旅程刻度保持不变。这与当前结构完全一致——只是内容页重新排序。

  3. 更新章节页的 data-level 属性。
  4. 更新章节分隔符上的章节编号文字和 h1。
  5. 更新第 6 页目录的 goToSlide 目标。
  6. 更新工作流章节页（原第 33 页）的章节编号文字。
  7. 在需要的地方进行有针对性的内容编辑，调整为天气预报员框架。
