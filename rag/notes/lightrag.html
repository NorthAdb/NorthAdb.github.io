源码阅读笔记：LightRAG（refs/LightRAG）

RAG

阅读任务（第 11 节布置）：① 找到实体抽取的 Prompt；② 找到“图 + 向量混合检索”的位置。 阅读日期：2026-09-12 · 版本：main 分支浅克隆

定位 1：实体抽取 Prompt 在哪里

lightrag/prompt.py —— 所有抽取相关 Prompt 集中在 PROMPTS 字典：

  • PROMPTS["entity_extraction_system_prompt"]（56 行起）：Knowledge Graph Specialist 角色， 分两步——先抽实体（entity_name / entity_type / entity_description），再抽关系 （source_entity / target_entity / relationship_keywords / relationship_description）；
  • 有两种输出格式：默认分隔符行格式（entity{tuple_delimiter}名称{tuple_delimiter}类型{tuple_delimiter}描述， 关系行 5 段）与 entity_extraction_json_system_prompt（175 行起，JSON 模式，注释说 "for higher extraction quality"）；
  • 细节值得抄：
    • 命名一致性：要求“title case + 全程一致命名”，因为抽取结果要做全局合并去重；
    • 限流字段：max_total_records / max_entity_records + completion_delimiter—— 控制单次抽取的成本上限，超限立即停；
    • 无向关系：“Swapping source and target does not constitute a new relationship”—— 合并时省一半去重逻辑；
    • 第三人称、禁代词（“本文”“我们”）：保证描述可拼接。

对照我们的玩具实验（scripts/toy_graph.py）：我们的抽取 Prompt 是它的极简版 （只有 s/r/o 三元组，没有实体类型、描述、限流、命名规范化）。差异直接对应能力差异： LightRAG 能把同一实体在多篇文档的描述合并成实体节点，我们做不到—— 这就是“玩具”和“系统”之间的距离。

定位 2：图 + 向量混合检索在哪里

  • 查询模式在 QueryParam.mode：naive / local / global / hybrid / mix （lightrag/base.py 定义、lightrag/operate.py 的查询管线分发）；
    • naive = 纯向量检索 chunk（等价于我们的 Dense）；
    • local = 从 query 抽关键词 → 匹配实体 → 图邻居 → 邻居关联的 chunk；
    • global = 匹配关系/社区摘要层；
    • hybrid = local + global；mix = naive + 图检索一起上；
  • 检索后的重排在 lightrag/rerank.py（外部 reranker 接口）——和我们第 7 节同款思路。

对照我们的玩具：我们的 graph_recall() = local 模式的一跳版（实体子串匹配 → 邻居 → 来源文档）；没有 global 层（关系/社区摘要），所以“全局主题”类问题接不住—— 这正是计划书说“LightRAG 砍社区摘要换轻量”时丢掉的东西，玩具实验里同样丢了。

一页笔记：问题 / 方法 / 代价 / 不做什么

项 内容
问题 扁平向量检索接不住实体关系/多跳问题；Microsoft GraphRAG 全家桶（社区检测+分层摘要）太贵
方法 抽实体+关系建轻量图；双层检索（实体层=local，关系层=global）；图检索与向量检索结果融合；可选 rerank
代价 建库时每 chunk 一次 LLM 抽取（贵）；图存储与增量维护复杂（kg/ 下十几种存储后端：neo4j/postgres/milvus/...）；查询时的关键词→实体匹配质量决定上限
不做什么 不做社区检测、不做分层社区摘要（GraphRAG 的 global 靠它，LightRAG 靠关系层替代）；不做多跳遍历（默认一跳邻居）；不训练模型
