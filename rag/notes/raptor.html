源码阅读笔记：RAPTOR（refs/raptor）

RAG

阅读任务（第 11 节布置）：找到“聚类摘要的递归终止条件”。 阅读日期：2026-09-12 · 版本：main 分支浅克隆

建树流程（raptor/tree_builder.py）

TreeBuilder.build_from_text()（260 行）：

split_text(text)                 → 叶子 chunks
multithreaded_create_leaf_nodes  → 叶子节点（每个 chunk 一次 embedding）
construct_tree(all_nodes, ...)   → 递归逐层向上（抽象方法！）

construct_tree 是抽象方法（298 行 @abstractclassmethod）——基类只定义骨架， 真正的“聚类→摘要→建父节点”循环在子类 cluster_tree_builder.ClusterTreeBuilder 里。

定位任务答案：递归终止条件（raptor/cluster_utils.py）

聚类用的是 GMM + UMAP 降维（global_cluster_embeddings 先全局降维， local_cluster_embeddings 簇内再降维），循环在 perform_clustering（69 行）：

if len(global_cluster_embeddings_) == 0:      ...  # 终止条件 1：没有数据
if len(global_cluster_embeddings_) <= dim + 1:     # 终止条件 2：样本太少，无法降维/聚类
# GMM_cluster: labels = [np.where(prob > threshold)[0] ...]   threshold=0.1

再加上 ClusterTreeBuilder 里的 if len(cluster_nodes) == 1（单节点簇不再摘要）， 以及 TreeBuilderConfig.num_layers（最大层数）。四层保险：

递归终止 = 簇内节点数 ≤ dim+1  或  概率阈值过滤后为空  或  单节点簇  或  达到 num_layers

对照论文：这就是论文里“recursively cluster until a threshold is hit”的工程形态—— 终止条件不是“树高固定”，而是数据的可聚类性（样本太少就不再强行分组）。

检索（raptor/tree_retriever.py）

TreeRetriever.retrieve() 有两种模式：

  • retrieve_information_collapse_tree（158 行）：collapsed tree——把所有层节点拉平 混在一起做向量检索，命中哪层用哪层（摘要节点和叶节点同台竞争）；
  • 分层模式：自顶向下逐层选 top-k 再往下走（论文的 tree traversal）。

配置项 TreeRetrieverConfig 里 top_k / num_layers / max_tokens / collapse_tree。

一页笔记：问题 / 方法 / 代价 / 不做什么

项 内容
问题 扁平 chunk 检索是“点对点”匹配，接不住需要抽象层级/全局视角的问题
方法 GMM 聚类（UMAP 降维）→ LLM 逐簇摘要 → 摘要再聚类，递归成树；检索时 collapsed tree（全层拉平）或分层遍历
代价 每个“簇 × 每层”一次 LLM 摘要（建树贵、更新更贵：局部改动可能牵动整棵子树的摘要）；摘要是 LLM 生成的——摘要幻觉会被当作证据检索出来；UMAP+GMM 对 embedding 质量敏感
不做什么 不做实体关系（那是 GraphRAG 的事）；不改检索器本身（还是向量相似度，只是检索对象多了摘要节点）；不做增量（原实现按全文重建）

与本课程的连接

  • 第 10 节 Parent-Child：“检索单元 ≠ 生成单元”的概念，RAPTOR 推广成“摘要也是检索单元”；
  • 我们的 rg_parents 表是它的“只有一层的树”（叶子=chunk，父=小节，无摘要）；
  • 若要手写玩具版（计划书允许的上限）：每章 1 次摘要 + 摘要向量入库 + strategy=chapter_summary， 用 meta_filter={"strategy_tag":...} 就能在现有 pgvector 架构上实现——留作练习。
