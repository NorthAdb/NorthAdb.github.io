LightRAG 源码导读（refs/LightRAG）

RAG

配套第 11 节的源码阅读任务。本页给一条带行号的阅读路线：按顺序读， 每站都有"看什么、对照课程哪里"。行号对应当前 refs/LightRAG 快照， 有漂移时用 grep -n "锚点" 文件 重新定位。

前置阅读：LightRAG 一页总结（一页总结）。 阅读心态：不是通读 8000 行，而是验证四个命题——每站结束问自己"我看到了吗"。

路线图（预计 60-90 分钟）

第 1 站  抽取 Prompt        lightrag/prompt.py:56, :175     （对应课程第 14 节）
第 2 站  抽取的落地与容错    lightrag/operate.py:3943, :711, :775
第 3 站  查询模式分发       lightrag/base.py:93 → operate.py:4657
第 4 站  混合检索与重排      lightrag/operate.py:6661 + lightrag/rerank.py

第 1 站：抽取 Prompt（lightrag/prompt.py:56 起）

打开 lightrag/prompt.py，找到 PROMPTS["entity_extraction_system_prompt"]（:56）。 通读这一段（约 120 行），重点核对本课程第 14 节总结的四条军规在工业实现里的样子：

课程玩具的军规（toy_graph.py:27-35） LightRAG 的工业版 行号
"实体用文中原名" 要求 title case + 全程一致命名（抽取结果要做全局合并去重） 在 prompt 正文中搜 "consistently"
无限流 max_total_records / max_entity_records 限流字段 + completion_delimiter 超限即停 :95, :132
s/r/o 三元组（无向由邻接表保证） "Swapping source and target does not constitute a new relationship"——无向关系写进 Prompt，合并时省一半去重逻辑 prompt 正文
无实体类型/描述 每个实体带 entity_type + entity_description（第三人称、禁代词）——这是它能"合并同名实体描述"的原料 prompt 正文

再看 :175 的 PROMPTS["entity_extraction_json_system_prompt"]——同一任务的 JSON 输出变体，注释明说 "for higher extraction quality"。对比两种输出格式 （分隔符行 vs JSON）各自好解析在哪里，这就是第 15 节"格式化生成"的工业样本。

命题 1：工业版抽取 Prompt 的复杂度主要用于"合并友好"而不是"抽得更多"。 你同意吗？

第 2 站：抽取的落地与容错（lightrag/operate.py）

  • extract_entities（operate.py:3943）：抽取主循环。看它如何分块（chunk 分片）、 如何并发、如何把模型输出喂给上面的 Prompt；
  • _handle_single_entity_extraction（:711）与 _handle_single_relationship_extraction （:775）：单条记录的解析与容错。对照我们玩具里的 re.search(r"\[.*\]", out, re.S) + 字段校验（toy_graph.py:48-55）—— 工业版的容错多了什么？（提示：分隔符行解析、字段缺失跳过、记录级日志。） LLM 输出必然有脏，容错层永远是你自己的代码——第 15 节 15.6 的共同结论在这里放大。

命题 2：解析失败的处理策略是"跳过并继续"，不是"重试到成功"。 为什么这个取舍合理？ （提示：重试贵且可能反复失败在同一个坏块上；漏一条边对图的伤害是局部的。）

第 3 站：查询模式分发（base.py:93 → operate.py:4657）

  • lightrag/base.py:93：QueryParam.mode 的五种取值—— local / global / hybrid / naive / mix（另有 bypass 直通 LLM）；
  • lightrag/operate.py:4657 的 kg_query：图查询主入口。跟一遍 mode 分发逻辑：
naive  = 纯向量检索 chunk                    ≈ 课程第 4 节 Dense
local  = query 抽关键词 → 匹配实体 → 邻居 → 关联 chunk   ≈ 课程第 14 节 graph_recall（一跳版）
global = 匹配关系/社区摘要层                 → 玩具没实现这一层
hybrid = local + global；mix = naive + 图一起上

命题 3：我们的 graph_recall 是 local 模式的一跳退化版，缺的是 global 层。 所以第 14 节"全局主题类问题接不住"的根源在结构缺失，不在参数。

第 4 站：混合检索与重排（operate.py:6661 + rerank.py）

  • operate.py:6661 的 naive_query：纯向量通路。注意它检索的是 chunk 表 （图抽取并不替代原文 chunk，两者并存）——"图 + 向量"是融合不是替换， 对应第 6 节"融合是粗排合并"的思想；
  • lightrag/rerank.py：查询后的外部 reranker 接口——与课程第 7 节同款组件， 位置也相同（检索后、生成前）。

命题 4（结业对照）：把 LightRAG 的管线画成第 1 节 1.3 那张流水线图—— 你会发现多出来的只有 Layer 1 的"抽实体建图"与 Layer 2 的"图召回一路"， 其余每一层（清洗/切分/向量/融合/rerank/引用）与我们的 Playground 一一同构。

读完之后

  1. 把四条命题的回答写进 LightRAG 一页总结（追加"验证记录"一节）；
  2. 动手（可选）：给 toy_graph.py 的 EXTRACT_PROMPT 加 entity_type 字段 （instruction/organization/person），重抽（--force）后观察邻接表变化—— 这就是"描述合并"的第一块砖；
  3. 思考：如果给我们的 KB 系统加第三路"图召回"（第 14 节的 graph_recall 产出 Hit 列表），rrf_fuse 需要改吗？（第 6 节 6.7 已经给过答案。）
