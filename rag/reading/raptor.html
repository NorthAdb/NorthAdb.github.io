RAPTOR 源码导读（refs/raptor）

RAG

配套第 11 节的源码阅读任务：找到"聚类摘要的递归终止条件"。本页给一条 带行号的阅读路线（约 40-60 分钟）。行号对应当前 refs/raptor 快照， 有漂移时用 grep -n "锚点" 文件 重新定位。

前置阅读：RAPTOR 一页总结（一页总结）。

第 1 站：树的骨架是抽象类（tree_builder.py:260, :297）

  • build_from_text()（:260）：入口，三步—— split_text 切叶子 → multithreaded_create_leaf_nodes 逐块 embedding → construct_tree 递归建层；
  • :297-298：construct_tree 是 @abstractclassmethod——基类只定义骨架， "聚类→摘要→建父节点"的真正循环在子类 ClusterTreeBuilder。

设计启示：RAPTOR 把"树的形状策略"做成可插拔（基类定流程、子类定策略）—— 这也是为什么论文的变体（不同聚类/摘要模型）可以只换配置不换骨架。

第 2 站：递归建树与终止条件（cluster_tree_builder.py:87-101）

这是本任务的核心答案，逐行读 ClusterTreeBuilder.construct_tree：

for layer in range(self.num_layers):                  # :87 保险 1：最大层数
    node_list_current_layer = get_node_list(current_level_nodes)
    if len(node_list_current_layer) <= self.reduction_dimension + 1:   # :96 保险 2
        self.num_layers = layer                       # :97 记录实际到达的层
        logging.info("Stopping Layer construction: ...")
        break                                         # :101 递归终止！
    clusters = self.clustering_algorithm.perform_clustering(...)   # :103 聚类
    # 每个簇 → summarization_model 生成摘要文本 → create_node 建父节点

:96 就是终止条件的主体：当前层节点数 ≤ 降维维度 + 1 时停止聚类 （UMAP 降维到 reduction_dimension 后，样本太少无法有意义地聚类）。 注意它不是"树高固定"，而是数据的可聚类性——这正是论文 "recursively cluster until a threshold is hit"的工程形态。

第 3 站：聚类的两道闸（cluster_utils.py）

  • global_cluster_embeddings（:23）与 local_cluster_embeddings（:37）： UMAP 降维的两级（先全局、簇内再降）；
  • GMM_cluster（:60）：高斯混合模型聚类， labels = [np.where(prob > threshold)[0] ...]（:65）—— threshold=0.1 的概率过滤是保险 3：某点对任何簇的概率都不够高 → 它不属于任何簇（噪声点不强行分组）；
  • perform_clustering（:69）：开头两道空/小样本短路——保险 4。
递归终止 = 层内节点数 ≤ dim+1（:96）  或  概率阈值过滤后为空（:65）
        或  样本太少短路（:69）      或  达到 num_layers（:87）

对照第 10 节的 Parent-Child：我们的 rg_parents 是"只有一层的树" （叶=chunk，父=小节，无摘要、无聚类）；RAPTOR 把层数推广到 N、把父节点 从"标题小节"换成"LLM 摘要"。结构与代码量都变了，但"检索单元 ≠ 生成单元" 的思想没变。

第 4 站：检索（tree_retriever.py:158, :252）

  • retrieve_information_collapse_tree（:158）：collapsed tree 模式—— 把所有层的节点（叶 chunk + 各层摘要）拉平混在一起做向量检索， 命中哪层用哪层。摘要节点与原始 chunk 同台竞争；
  • retrieve()（:252）：统一入口，collapse_tree 参数切换两种模式 （另一种是自顶向下逐层选 top-k 的 tree traversal）。

关键认知：RAPTOR 没有发明新的检索器——还是余弦相似度，只是把 "摘要节点"作为一种新的可检索单元放进了同一个向量空间。这就是为什么它 能无缝复用我们第 4 节的全部机制（docs/02 结尾的"手写玩具版"练习： 每章 1 次摘要 + 摘要向量入库 + strategy=chapter_summary）。

摘要幻觉的评测钩子

第 11 节提过：摘要可能幻觉且被当证据检索出来。评测上的落地： 在金标/引用检查里区分"引用的是叶节点还是摘要节点"（collapsed tree 模式下 尤其重要——Hit.meta 里应带层级标记）。这正是第 13 节 judge Prompt 可以 顺手检查的事。

读完之后

  1. 把四道保险的验证过程写进 RAPTOR 一页总结 （追加"验证记录"一节：每个终止条件标注你亲眼看到的行号）；
  2. 动手（可选，计划书授权上限内）：给 KB 语料的每章做一次 LLM 摘要， 以 strategy=chapter_summary 入库（meta 带 {"node_type":"summary"}）， 在 Playground 对比全局题（"这套资料的主要主题有哪些"）的命中变化；
  3. 思考：collapsed tree 让摘要节点与 chunk 竞争 Top-K 名额——什么时候这是 好事（全局题），什么时候是坏事（精确事实题被摘要挤掉）？路由（第 14 节 14.6）能不能解决？
