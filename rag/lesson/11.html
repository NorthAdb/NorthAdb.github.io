结构化 RAG 扫盲：RAPTOR / GraphRAG / LightRAG

第 11 节约 35 分钟本节自测

树与图分别解决什么；为什么手册语料不适合 GraphRAG；源码阅读入口；v4：扁平 RAG、多跳、聚类、社区检测在首次出现处展开。

本节任务：建立"问题类型 → 数据结构"的选型直觉：树/图各自解决哪类 扁平 RAG 答不好的问题，以及什么时候不该用它们。本节是扫盲课—— 理解"解决什么问题、代价是什么"，不在本课程从零复现论文系统。

课程地图上的位置：视野扩展。上一节 10 PC 与评测；下一节 12 框架对照。

11.1 为什么扁平 RAG 会遇到天花板

扁平 RAG 把每篇文档切成块，块和块之间没有"谁包含谁、谁指向谁"。 检索就是在这一摊块里找相似。前面 10 节的优化（清洗、切分、Hybrid、Rerank、装填） 都在提高"找到相关块"的能力。

有三类问题，相关块找到了也答不好：

问题类型 例子 扁平 RAG 为什么吃力
层级/全局 "从 SIMD 总体讲到具体指令集演进" 答案散在 5 篇以上，没有任何单块覆盖全貌
多跳关系 "Jim Keller 和 Apple 是怎么连起来的" 要沿着关系走好几步，单块里没有这条链
汇总统计 "这套资料的主要主题有哪些" 需要看过全库再概括，相似检索做的是"找附近"

三个方案，三种结构，各自对应一类问题。它们是并列的工具，不存在"图比树高级"。

跳（hop）是沿一条关系走一步。A 和 B 有直接关系，是一跳；还要经过 B 才能到 C， 是两跳。需要走多步才叫多跳。扁平检索一次只能捡到和问题在词面或语义上接近的块， 接不上中间那一站。

RAPTOR      树   → 按抽象层级组织：chunk → 聚类 → 摘要 → 再聚类 → 根
GraphRAG    图   → 按实体关系组织：Entity / Relation / Community / 摘要
LightRAG    图+向量 → 轻量版：图检索与向量检索协同，成本大幅降低

11.2 RAPTOR（树）

RAPTOR（Recursive Abstractive Processing for Tree-Organized Retrieval） 按抽象层级把语料收成一棵树：底下是原文块，往上每一层都是更粗的摘要。

        总体摘要（根）
       /          \
   主题A摘要      主题B摘要      ← 聚类 + LLM 摘要，逐层向上
   /  |  \        /  |  \
  C1 C2  C3      C4 C5  C6      ← 原始 chunk（叶子）
  • 聚类（clustering）：按向量远近把块分成若干簇，人不给类别名。 同一簇里的块彼此接近，被当成"在讲邻近的事"。每一簇调用一次 LLM 写成摘要， 摘要自己再变成节点，继续聚类，直到这一层节点很少或到达深度上限。 建树的费用因此是每层每簇一次摘要调用。
  • 叶子是树上不再往下分的节点，这里就是原始 chunk。根是最顶上那一份总体摘要。
  • 检索有两种走法。**collapsed tree（拉平的树）**把每一层的节点——叶子和各层摘要—— 放进同一个向量索引，谁离问题近就取谁。层级遍历先在上层摘要里定位"大概在哪一枝"， 再只钻进那一枝的子节点。前者实现简单，后者在树上很大时少看无关的枝。
  • 适合章节型长文档的层级导航和全局总结。本课程的 CPU 语料 （SIMD → AVX → AVX-512）就是这种由总到分的结构。
  • 摘要可能幻觉（第 8 节：模型写出资料里没有的句子）。这句摘要一旦入库， 检索会把它当成证据交出来。评树方案时要能分清命中的是叶子还是摘要节点。

11.3 GraphRAG（图）

Documents → 实体抽取 → 关系抽取 → 知识图 → 社区检测 → 社区摘要
                                          ↓
              Local 查询（实体邻居）/ Global 查询（社区摘要）

图上的四种对象：

对象 是什么
Entity（实体） 可以被指称的对象：人、公司、产品、架构
Relationship（关系） 两个实体之间的一条边，例如"创立""主导"
Claim（断言） 带出处的一句事实。比关系更细，两条断言可以互相矛盾
Community（社区） 图上一团彼此连得很密、和团外连得稀的节点

社区检测自动找出这些团，人不指定"这是半导体公司圈"。 GraphRAG 用的是 Leiden 这一类图聚类：反复把连得紧的节点留在同一组、把跨组的边切开。 每个社区再写一篇摘要。全局问题读的是这些摘要，而不是把全库的块塞进上下文。 这是它能回答"这批资料主要在讲什么"的本钱，也是建库贵的主要来源： 全库都要做 LLM 抽取，每个社区还要再摘要一次。

两种查询：

  • Local（局部）：从问题里认出的实体出发，读它的邻居和相关原文。 适合"某人和某公司是什么关系"。
  • Global（全局）：先读社区摘要，再汇总。适合看全库主题。

适合实体关系丰富的语料（人物、公司、产品）。CPU 手册里的实体多是指令和寄存器， 彼此的关系浅，图上的边帮不上忙。这只能说明这批语料不吃图，不能据此否定图方法。 换一批关系密的语料再评。

本课程准备了对照语料 data/graph_corpus/（12 篇人物/公司/架构短文： Intel、AMD、Gordon Moore、Jerry Sanders、Jim Keller、Zen、Apple Silicon…）， 里面的关系链（桑德斯与诺伊斯同出仙童 → 分别创立 AMD/Intel → 交叉授权 → AMD64 → x86-64）足够演示"多跳"。索引版本 graph_flat500 （data/graph_corpus 由 build_index(corpus="graph") 入库， meta corpus=graph 隔离——第 9 节的机制）。

11.4 LightRAG（轻量图）

Microsoft 的 GraphRAG 把社区摘要做到很全，建库因此很贵。 LightRAG 留下实体和关系的抽取，以及那张图，砍掉按层级生成的社区摘要。 查询时让图检索和向量检索一起干活，Local / Global 两类问题仍能问 （全局问题改由关系描述和向量兜底，不再靠社区摘要）。 贵的是建图（每篇文档都要调用 LLM 抽取），查询本身只是在已经建好的结构上走。 LightRAG 的取舍是：结构少建一点，查询时多用向量补上。

11.5 如何运行：亲手体感"扁平检索在关系题上吃力"

# 1) 确认图谱语料已入库（graph_flat500）
python -c "
from playground.db import q
print(q(\"SELECT strategy, count(*) FROM rg_chunks WHERE meta @> '{\\\"corpus\\\":\\\"graph\\\"}'::jsonb GROUP BY strategy\"))
"

# 2) 终端跑一道多跳题（扁平 Hybrid，注意 Top-5 里没有'答案所在文档'）
python -c "
from playground.rag import RAGPipeline, PipelineOptions
t = RAGPipeline(PipelineOptions(retriever='hybrid', corpus='graph',
                                strategy='graph_flat500', generate=False)).retrieve('AMD 的 Zen 架构是谁主导的？')
print([h.doc_id for h in t.fused[:5]])
"

# 3) 对照：第 14 节的图引导检索（python -m scripts.toy_graph --query 同一题）

预期：纯向量 Top-3 全是 zen 相关文档（因为问题里就带 "Zen"），而答案 （吉姆·凯勒）在 jim-keller 文档里——词面和语义都够不着。第 14 节的 图路会正面解决这题。

11.6 选型判断（把第 12 节的卡片提前看一眼）

局部事实/符号/语义          → 扁平 Hybrid（+Rerank）足够
命中要准、生成要完整        → + Parent-Child
章节长文档的全局/层级题    → 考虑 RAPTOR（摘要树）
实体关系/多跳、语料自带图  → 考虑 GraphRAG / LightRAG

不要问"谁最好"——同一批数据上 GraphRAG 不如 Hybrid，只说明这批数据 不需要图结构。先跑通扁平方案 + 金标评测，有数据、有对照，再决定要不要上树/图。

11.8 注意事项

  • 树和图的构建成本随语料规模增长：每篇文档、每一簇都要调用 LLM。 文档数量翻 100 倍，抽取和摘要的费用大约也翻 100 倍。16 篇可以玩，1600 篇要先算预算。 这种"费用和文档数成比例"常写成 O(语料规模)：大 O 表示增长的量级， 这里忽略常数因子，只强调它跟着语料一起变大，而不是只在用户提问时才付钱。
  • 树和图换了一种失真。树的摘要会丢掉细节，也会写进原文没有的句子。 图把一段话收成三元组（主体、关系、客体三条一组的原子事实，第 14 节会抽）， 时间和语气就留在了原文档里。这里的三元组和第 13 节的"评估三元组" （Faithfulness、Answer Relevance、Context Relevance 三个分数）不是同一个词。 两种结构都要和扁平方案在同一套金标上对照，单独的一个分数说明不了它们值不值得上。
  • 本课程的图语料（graph_corpus）是为实验写的短文。关系链是设计出来的， 这样"图多找回的那几篇"才能归因到图，而不是归因到两批语料本来就不一样 （与第 2 节 make_dirty 的对照方法相同）。
