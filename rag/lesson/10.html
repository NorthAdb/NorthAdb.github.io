Parent-Child 与评测体系

第 10 节约 45 分钟本节自测

小块检索大块生成；auto-merging；Recall/MRR/噪声率/拒答率；失败诊断清单；v4：回表、IN、HitRate 与 nDCG 在首次出现处展开。

本节任务：两个半场——前半场理解"检索单元与生成单元可以不是同一块" （Parent-Child），后半场掌握四个指标的定义与一张 8 步排障清单。读完你应该 能独立诊断"RAG 答错了"到底坏在哪一层。

课程地图上的位置：Layer 2 的收口 + Eval 的正式登场。上一节 09 知识库工程；下一节 11 结构化 RAG 扫盲。

10.1 Parent-Child：拆开"又要短又要长"的矛盾

矛盾：块要"短"才好精确命中（信号集中）
      块要"长"才够 LLM 理解（上下文完整）

解法：检索单元 ≠ 生成单元
      子块 child（~200 字）→ 索引与检索
      父块 parent（整节）  → 命中后回表，送进 Context

数据侧的支撑在第 3、9 节已经埋好：chunker.parent_child_chunks() （chunker.py:120-144）切子块并返回 {parent_id: 整节文本}； 父块存 rg_parents 表（scripts/init_db.py:29-35，parent_id = doc_id::sec<i>）。

10.1.1 代码走读（playground/retrieve/parent_child.py，92 行）

完整通路 parent_child_search（parent_child.py:73-91）——子块召回方式 可以任选 dense / bm25 / hybrid（:79-90），然后交给出厂改编：

def expand_to_parents(children, strategy_suffix="", auto_merge_boost=True):   # :29
    per_parent: dict[str, list[Hit]] = {}
    for h in children:
        pid = h.parent_id or h.chunk_id          # :40 没有父块id的块自认父块
        per_parent.setdefault(pid, []).append(h) # :41 按父块分组

    parents = _load_parents(list(per_parent.keys()))     # :43 一次 IN 查询回表
    for pid, hits in per_parent.items():
        best = max(hits, key=lambda h: h.score)          # :46 组内取最高分子块
        n_hits = len(hits)
        boost = 1.0 / (config.RRF_K + 1) * (n_hits - 1) if auto_merge_boost else 0.0   # :48
        content, section = parents[pid] if pid in parents else (best.content, ...)   # :50-51
        out.append(Hit(..., content=content,             # ← 整节文本，生成单元变大
                       score=round(best.score + boost, 5),
                       meta={"child_hits": n_hits}))     # :64 命中数进 meta（可观测）

回表：子块行上只有约 200 字和一只 parent_id，整节正文在 rg_parents。 检索先给子块打分，再拿 parent_id 去父表把整节读出来，送给模型的 content 换成这份长文本（:50-51）。"回"指的是：主查询已经结束，按键再查一次相关表。 检索看小块，生成读大块，差别就在这一次替换。

IN：WHERE parent_id IN (%s, %s, ...)（parent_child.py:22-24）表示 "值落在这份名单里"。一次取回全部命中的父块。占位符个数随名单变化， 所以用 ",".join 现拼 %s，值仍走参数，不写进 SQL 字符串 （第 9 节的参数化查询）。

RRF_K 是第 6 节 RRF 的平滑常数，钉在 60（config.py:63）。 某一路检索排第 1 时，贡献是 1/(RRF_K+1) ≈ 0.0164。 :48 的 auto-merging 加分用的就是这个步长：同一父块下每多命中一个子块， 加上一路"排第 1"那么多的分。只命中一个子块时 (n_hits - 1) 为 0，不加分。 加分和 RRF 分数量纲相同，多命中一节会明显往前挪。 意思是：两个不同子块都落到同一节，答案多半横跨这一节，父块该往前排。 分组本身已经把同一父块收成一条（:40-46）；加分只改这条的名次。

本课程是"只要命中就回表"。LlamaIndex 的 AutoMergingRetriever 多一档判断： 同一父块命中的子块不够多时，仍然返回子块，够多才换成父块。 :48 借了它的信号，没有借它的门槛。

编排层怎么接入：PipelineOptions.parent_child=True 时，rag.py:172-173 在融合之后、精排之前执行 expand_to_parents(fused)。

10.1.2 三个变体：命中之后，上下文往外扩多少

三者做的是同一类事：先用小片段命中，再把更多原文送去生成。差别是扩多大、何时扩。

名字 检索单元 命中后送去生成的文本 LlamaIndex 里的类
Sentence Window（句子窗口） 一句 这句前后各若干句，叫一个窗口 SentenceWindowNodeParser
Parent-Child（本节） ~200 字子块 只要命中，就换成整节父块 层级节点（父节点另存）
Auto-merging（自动合并） 子块 同一父块的子块命中够多，才换成父块；不够就留子块 AutoMergingRetriever

第 12 节的映射表只对照到 Node 自带父子链接，这三个类名记在这里。

10.2 实验 5 结果

来自 python -m scripts.run_eval 第 5 组（exp5_parent_child）：

方案 Recall@5 MRR@5 noise@5
Flat 500 + Rerank 1.00 0.928 0.557
Parent-Child 200 0.957 0.895 0.714*
Parent-Child + Rerank 0.957 0.895 0.714*

（口径：30 题金标中的 23 道可回答题，文档级指标。）

怎么读这张表——先说反直觉的部分：文档级指标上 PC 没有赢。

  • Flat+Rerank 在这套小语料上已接近满分（1.00 / 0.928），PC 没有可追赶的空间； "子块召回 → 合并回父块"多了一步，个别题反而掉出 Top-5（0.957）。这不是 "Parent-Child 没用"，而是文档级指标量不出它的收益（下一条）；
  • *noise@5 偏高是指标口径问题：父块是整节文本，主题比 500 字块杂， "不含答案关键词"的比例天然高——与 Flat 方案不可直接比较（exp5 报告的 口径说明）。PC 的优势本来就不在"块干不干净"，而在 Context 完整性 （生成单元是整节）：做 10.6 练习 1 那道跨小节题，对比两种方案 "最终进 Context"的块内容，差异肉眼可见；
  • 一个重要的历史注脚：v1 口径（20 题时代）这张表曾显示 PC"Recall 补满、 MRR 全场最优"；换到 30 题口径后排名反转。同一份代码、同一套语料， 换一套金标结论就会变——这是"先金标、后改进"与"注明口径"两条纪律 最好的一次教训。

与 RAPTOR 的关系：Parent-Child 先让你理解"检索单元与生成单元可以不是 同一块"，RAPTOR 是在这之上再加一层"摘要节点也是检索单元"。先 PC 后 RAPTOR， 概念坡度平缓。

10.3 评测体系：代码走读（playground/eval/evaluate.py，201 行）

10.3.1 数据结构：Question 与 CaseResult

class Question:                     # :21-35，金标集一题的内存形态
    id / type / question            # type ∈ fact/symbol/semantic/.../unanswerable
    gold_docs: list[str]            # 命中哪几篇算对（文档级）
    gold_keywords: list[str]        # 块级关键词（kw_hit / noise 用）
    answerable: bool                # False = 不可回答题，只考察拒答

class CaseResult:                   # :44-52，一次评测的原始记录
    hit_rank: int | None            # 第一个 gold doc 命中的名次（1-based），未命中 None
    top_contents / refusal / answer

10.3.2 两个入口：检索层 vs 完整链路

case_retrieval（:55-66）只跑检索（generate=False 时 hit_rank 从 trace.fused 里数文档名次）；case_full（:69-80）跑完整链路， hit_rank 从引用列表里数（:74-77）——注意口径差异：完整链路的"命中" 是"答案引用了金标文档"，更严格也更接近用户视角。

10.3.3 指标本体

先把表头里的词定下来，再看每一列量什么。

@K：只考察排在最前的 K 条。@5 就是 Top-5，第 6 名及以后这道题里当作没出现。

1-based：名次从 1 起算，第一名的 hit_rank 是 1。倒数排名要做除法， 从 0 起算会在第一名上除以零。

文档级：金标标在文档上。gold_docs 是 doc_id 列表。Top-K 里出现该文档的 任意一块，这道题算命中。切分方式变了，金标不用重标——这是第 1 节就冻住的约定。

块级：看块的正文里有没有 gold_keywords。用来区分"捞到了那篇文档" 和"捞到的那一块就是答案所在"。

Recall@K 在检索文献里一般是"相关文档被捞回的比例"。多个相关文档时， 捞回 1 篇和捞回全部不是同一个分数。本课程的实现（:83-92）更窄： 一道可回答题，Top-K 里有任一 gold doc 就记 1，否则记 0，再对题目取平均。 这个算法的名字是 HitRate@K（有没有命中）。金标多为一篇文档时，两者数值一样， 所以表头沿用了 Recall。10.7 把两个名字拆开。

MRR（Mean Reciprocal Rank，平均倒数排名）：每道题取第一个命中的名次 rank，贡献 1/rank；K 以内没有命中则贡献 0；再对题目取平均。 第 1 名得 1，第 2 名得 0.5，第 5 名得 0.2。它专门惩罚"捞到了，但排得很后"。

kw_hit@K：Top-K 的正文里，至少一块包含任一金标关键词，这道题记 1。

noise@K：在写了关键词的那些题上，Top-K 里"一块关键词都不含"的块占多少比例， 再对题取平均。0 表示每块都沾到关键词，1 表示全是凑数。

拒答率：只统计 answerable=False 的题。模型给出拒答（refusal=True）算对。 这些题没有 gold_docs，若放进 Recall，分母和分子都没有意义，所以 :87-88 把它们跳过。

四个指标各自回答一个问题（实现行号标注；Recall 这一列的实现其实是 HitRate，见上文）：

指标 回答什么 实现 什么时候看
Recall@K 金标文档进没进 Top-K（文档级） _recall_mrr :83-92 前半 召回问题：根本没捞到
MRR@K 第一个命中排第几 _recall_mrr :90 1/hit_rank 排序问题：捞到了但靠后
kw_hit@K Top-K 里有没有块真含答案关键词（块级） _kw_recall :95-111 "捞到的是不是答案本身"
noise@K Top-K 里几块是凑数的（1 - 关键词命中率） _noise_at_k :114-132 Rerank/融合的质量
拒答率 不可回答题是否正确拒答 run_eval :180-182 生成层诚实度

run_eval（:135-194）把它们组装成多方案报告：K ∈ {3,5,10}（:153）、 按题型分组统计（:167-177）、结果同时落 .md（人读）与 .json（机器读， save_report :197-200）。

[!TIP] 16 篇文档的小语料上，文档级指标很快饱和（R@5 普遍 0.95+）。 区分方案好坏要靠块级指标（kw_hit / noise）和逐题 Trace 对比。 语料变大后文档级指标自然拉开——这是"指标要配数据规模"的实例。

10.3.4 失败诊断清单（按顺序查，不要跳步）

1. 源文件脏/切错章/索引过期？        → 清洗与 checksum（第 2、9 节）
2. Chunk 切碎了关键句/一坨多主题？    → 切分策略与大小（第 3 节）
3. 符号题只走了向量？                → Hybrid（第 5-6 节）
4. 金标根本不在候选里？              → 召回问题：改召回，加改写（第 8 节）
5. 在候选里但排到后面？              → 融合/精排问题（第 6-7 节）
6. 进了 Top-K 但没进 Context？       → 预算/去重/装填（第 8 节）
7. 进了 Context 但答案仍编造？       → Prompt 约束/引用（第 8 节）
8. 资料确实没有？                    → 应拒答，别改检索器（第 8 节）

分层对应：1-2 是 Layer 1（知识工程），3-5 是 Layer 2（检索工程）， 6-8 是 Layer 3（上下文工程）——三层心智模型直接落地成排障顺序。

10.5 注意事项

  • kw_hit/noise 依赖 gold_keywords 的质量：关键词选得太宽（如 "cache"） 会高估，太窄（如 "STTNI"）会低估——写金标时要自查一遍关键词是否真的出现在 gold_doc 的正文里；
  • 不可回答题的"正确"只有一种形态：refusal=True。任何"看起来很努力"的 错误答案都是 0 分（:180-182 数的就是这个）；
  • 对比两个方案时，strategy 与题目口径必须完全相同——实验报告的表头里 写 strategy 就是为了这个。

10.7 加厚（v3）：指标家族延伸——MRR 之外的排名指标

本节的 Recall/MRR 用"文档级金标 + 第一个命中"就够用。金标变得更富（多个相关 文档、相关性分强弱）时，指标也要跟着升级：

指标 回答什么 何时用它
HitRate@K 前 K 里有没有命中（宽松版 Recall） 只关心"有没有"，不关心名次
Recall@K 相关文档被捞回的比例（多个相关文档时按比例算） 相关文档不止一个
MRR@K 第一个命中的名次倒数 单一正确答案的事实/符号题（本课程主力）
MAP 所有相关文档的平均精度的均值 多个相关文档且同等重要
nDCG 分级相关性 × 位置折损（排越后贡献越小） 相关性有强弱之分（"权威定义段" vs "顺带提过"）

四个名字里，HitRate 和"多个相关文档时的 Recall"在 10.3.3 已经分开。 剩下两个要看到公式才不会和 MRR 混成"都是看名次"。

MAP（Mean Average Precision，平均精度均值）照顾"相关文档不止一篇， 而且每一篇排得靠不靠前"。对一道题，沿着名次往下走，每遇到一篇相关文档， 记下此时的精度：到这一名为止，相关篇数 ÷ 当前名次。这些精度再平均，得到这道题的 AP。 MAP 是所有题的 AP 再平均。只看第一个命中的 MRR，第二篇相关文档排在第 2 还是第 9 都不再影响分数；MAP 会把后面那几篇也算进去。

nDCG（normalized Discounted Cumulative Gain，归一化折损累计增益）还允许多个 相关等级，例如 0 无关、1 顺带提到、2 就是答案段。计算分四步：

  1. 增益（gain）：这一名文档的相关性等级；
  2. 折损（discount）：名次越后，增益要除得越多。常用除数是 log2(名次+1)。 第 1 名的除数是 log2(2)=1，第 3 名是 log2(4)=2，所以同样强的文档排在第 3， 贡献大约是排在第 1 的一半；
  3. DCG：把折损之后的增益加总；
  4. IDCG：把这道题的相关文档按理想顺序重排后的 DCG，也就是这道题的理论上限。 nDCG = DCG / IDCG，落在 0 到 1。漏掉相关文档，或把强相关排到后面，都会让它变小。 不相关文档的增益是 0，排到哪里都不加分。

本课程的金标没有等级，只有"是不是这篇文档"和"块里有没有关键词"。 kw_hit 看有没有沾到答案，MRR 看第一命中的名次，两件事分开报。 等金标写出等级，再换成 nDCG，比较的仍是同一批检索结果。

最后再连一次第 13 节：这些排名指标管检索层；生成层的 Faithfulness/AR/CR 没有金标可比，只能靠 LLM-as-judge 做相对比较——两套工具各管半场，别互相替代。
