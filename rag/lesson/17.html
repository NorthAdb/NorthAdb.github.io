从实验台到产品：个人知识库系统

第 17 节约 40 分钟本节自测

课程积木装配成 /kb 完整系统：上传入库、多轮 condense、CRAG 纠错、流式引用回答；v4：SSE、APIRouter、幂等、ILIKE 在首次出现处展开。

本节任务：理解课程手写的检索积木如何被装配成一个可日常使用的产品 （/kb 个人知识库），并把第 16 节的 CRAG 真正接进产品。这一节也是 "从 Playground 到 RAGFlow/AnythingLLM"的差距地图。上一节 16 高级范式。

课程地图上的位置：产品篇，全课的收束。设计调研与选型对照见 docs/04-RAG生态调研与个人知识库系统设计.md。

17.1 为什么"能用"和"能实验"是两套要求

Playground 的第一原则是可对比：固定语料、钉死参数、金标评测。知识库产品 （RAGFlow、Dify、FastGPT、AnythingLLM 这类）的第一原则是可用性：

维度 Playground（实验台） KB（产品）
语料 16 篇固定章节 用户随时上传的任意 md/txt/pdf/docx
切分 strategy 版本化，多版本并存对比 固定 kb600x120，换参数=重建
检索 5 种方案任选对比 默认 Hybrid+Rerank（实验结论直接变成默认值）
输出 完整 Trace 逐层可视化 流式答案 + [n] 引用 + 拒答
会话 无 多轮对话 + 持久化 + 导出
评测 25/30 题金标 无金标——用户的问题就是评测

最重要的认知：实验的结论沉淀为产品的默认值。第 6 节证明 RRF 不被量纲 绑架，所以 KB 的融合只留 RRF；第 8 节的引用与拒答约束直接变成对话的硬约束； 第 16 节的 CRAG 变成可勾选的开关。

17.2 结构与数据流

kb/
  config.py   KB 专属参数：kb600x120 策略、上下文预算 4800、拒答阈值 0.35
  parser.py   md/txt（编码兼容）/ pdf（pymupdf 抽文本）/ docx（python-docx，含表格）
  store.py    持久层：文档/块复用 rg_documents+rg_chunks（corpus='kb'）
              会话/消息建 rg_kb_sessions + rg_kb_messages
  ingest.py   上传入库：落盘 → 解析 → 清洗 → 切分 → 嵌入（共享缓存）→ 先删后插
  chat.py     condense 改写 → 混合检索 → 精排 → CRAG → 装填 → 流式生成 → 拒答
  routes.py   /kb 页面 + /api/kb/*（FastAPI 的 APIRouter，由 course/app.py 挂载）
course/static/kb.html   单页前端（用 fetch 读 SSE 流；SSE 见 17.5）

pymupdf 是把 PDF 页面抽成文本的库。python-docx 读 Word 文件，包括里面的表格。 APIRouter 是 FastAPI 里的一组路径。include_router 把这一组挂到主应用上， /kb 和 /api/kb/* 不用在 app.py 里逐个函数重写。

路由挂载只有两行（course/app.py）：

from kb.routes import router as kb_router     # kb/routes.py 里的 APIRouter
app.include_router(kb_router)                 # /kb 与 /api/kb/* 一次性接入

数据流的关键决策是同表、不同命名空间。命名空间在这里不是 Python 的 package， 而是"同一张表里用前缀和标签把两批数据隔开"。KB 的块写进课程主表 rg_documents / rg_chunks，靠三个约定看不见课程语料，课程检索也看不见 KB：

doc_id = "kb::<文件名>"                     # kb/ingest.py:36-37 的 doc_id_for()
meta = {"corpus": "kb"}                     # 检索过滤（第 9 节的 meta @>）
strategy = "kb600x120"                      # kb/config.py:11，与课程索引并存

课程手写的 dense_search / bm25_search 不用改就能检索 KB。 第 1 节的统一命中结构 Hit，加上第 9 节的 corpus 过滤，在这里接到了产品上。 删文档时的级联也是表结构里现成的：rg_chunks.doc_id 外键指向 rg_documents （scripts/init_db.py:39，ON DELETE CASCADE 的含义在第 9 节 9.2.2）。 父块表的外键在 :31，KB 的固定切分不写父块，实际清理走的是 chunks 那一条。

17.3 入库管线走读（kb/ingest.py，125 行）

ingest_file()（kb/ingest.py:40-77）是唯一入口，其余都是它的包装：

def ingest_file(path, original_name, embed=True):
    filename = _safe_filename(original_name)          # :42 去 ../、控制字符（:29-34）
    if ext not in kb_config.ALLOWED_EXTENSIONS: ...   # :43-44 白名单
    title, text = parser.parse_file(path)             # :46 md/pdf/docx → (标题, 纯文本)
    text = cleaner.clean_text(text)                   # :47 复用第 2 节清洗器！
    did, checksum = doc_id_for(filename), sha256(...)[:16]
    old = store.get_document(did)
    if old and old["checksum"] == checksum:           # :59 内容没变 → 跳过
        return {..., "status": "unchanged"}
    chunks = chunker.fixed_chunks(text, did, size=600, overlap=120)   # :63 复用第 3 节
    embeddings = get_embedder().embed_batch(...)      # :65 复用第 4 节（缓存共享）
    store.upsert_document(did, title, str(path), checksum)
    store.replace_chunks(did, chunks, embeddings)     # :67 先删后插（store.py:66-92）

三个值得学的点：

  1. 同名重传 = 版本更新。checksum 与库里相同就跳过嵌入（kb/ingest.py:55-58）。 粘贴建文档（ingest_text，:93-104）只是先落盘一个 .md，再走 ingest_file；
  2. 嵌入缓存全局共享。缓存键是 sha256(模型名 + 文本)（第 4 节 4.2.1）。 KB 重传、课程实验、重建索引，同一段文字只付一次嵌入 API 的钱；
  3. 入库后清 BM25 缓存。replace_chunks 末尾调用 clear_retrieval_caches() （kb/store.py:173-176）。lru_cache 记的是进程内存里的旧倒排表 （第 9 节 9.1.4），库更新了它不会自己知道。

前端对应的入口：上传、粘贴、查看切块、重建、删除。 上传走 multipart：HTTP 正文分成一段段，有的是普通字段，有的是文件字节。 python-multipart 是 FastAPI 用来拆这种正文的库（routes.py 的上传接口）。 浏览器 <input accept="..."> 只影响文件选择框里看得见哪些后缀，拦不住人改请求。 扩展名和大小的检查在 kb/ingest.py 里做（17.7）。

17.4 对话管线走读（kb/chat.py，278 行）

一次提问在 routes.py:161 的 kb_chat 里经过五步，然后转成 SSE 事件流：

① 会话准备（routes.py:167-182）：session_id 不给就建新会话；先读历史、
   存用户消息、首条消息自动命名会话（question[:24]）
② prepare()（chat.py:217-256）：condense 改写 → retrieve_kb（含 CRAG）→
   装填 → 拒答判定
③ stream_answer()（chat.py:258-275）：拒答 → 固定话术不调 LLM；
   否则 DeepSeek SSE 流式（llm.py:56 的 chat_stream）
④ SSE 事件（routes.py:156-181）：meta（检索词/命中/引用/CRAG步骤）→
   delta（逐字）→ done；客户端断开时 finally 落库部分答案
⑤ 持久化：用户消息先存，assistant 消息带 citations+trace 存档（store.py:224）

17.4.1 多轮改写：condense_question（chat.py:160-185）

追问"那它和 BM25 有什么区别？"不能直接拿去检索。"它"指的是上文。 **condense（压缩改写）**把这种依赖历史的问句，收成一句不看对话也能检索的话。 做法和 FastGPT、Dify 相同：最近若干条历史加上最新问题，交给 LLM 改写。 历史很长时只取最近 N 条（KB_HISTORY_MESSAGES），避免整段对话都塞进检索词。

def condense_question(history, question):
    recent = [m for m in history if m["role"] in (...)].[-KB_HISTORY_MESSAGES:]
    if not recent:
        return question, False                      # 无历史 = 不改写
    if not getattr(mod, "is_real", False):
        return question, False                      # LLM 降级 = 跳过（:166 保底）
    rewritten = mod.chat(prompt, system=_CONDENSE_SYSTEM, max_tokens=120)
    return (rewritten, True) if rewritten else (question, False)

实测："那多轮对话又是怎么处理的？" → "系统的多轮对话是怎么处理的？" 改写后的检索词显示在回答脚注里——可观测原则在产品层依然成立。

17.4.2 CRAG 在产品里的形态（chat.py:85-145）

retrieve_kb(query, use_rerank, top_k, crag=False) 的三段逻辑 （第 16 节 16.3 已给过实测数据）：

fused = _recall(query)                    # :28 dense+bm25 → RRF（课程第 4-6 节）
scored = rk.rerank(query, fused, ...)     # :95-96 第 7 节精排
verdict = crag_verdict(best)              # :42 pure：None→unknown / ≥0.35→correct
if crag and verdict == "incorrect":       # :133 第二次机会
    expanded = _expand_query(query)       # :73 LLM 扩展查询（与 condense 是两个 Prompt）
    merged = _merge_candidates([fused, fused2])    # :55 chunk_id 去重合并
    scored2 = rk.rerank(expanded, merged, ...)     # 合并候选整体再精排

crag_verdict（:42-52）是纯函数（有单测 tests/test_kb.py）： 没开精排时返回 unknown——RRF 分数量纲与相关性阈值不在一个世界 （第 6 节教训），没有评估器就不该硬评估。每轮的检索词/top1 分数/判定 放进 crag_steps，随消息落库、随 meta 事件发到前端"检索过程"面板。

17.4.3 拒答的双层设计

第一层在检索后（chat.py prepare 内）：零命中，或开了精排且 top1 < 0.35 （kb/config.py:25 的 KB_LOW_SCORE_REFUSAL）→ 直接标记 refusal。 第二层在生成 Prompt（kb/config.py:31-35 的 KB_SYSTEM_PROMPT）： 只按资料回答、[n] 引用、矛盾要指出。阈值证据（实测 top1 分布）： 具体问题 0.9+，含糊多段问题 0.14-0.22，分界清晰——0.35 放在空带里。

17.5 前端与 SSE 协议（course/static/kb.html）

SSE（Server-Sent Events，第 8 节）是服务器向浏览器单向持续推送文本的协议。 一次聊天的响应不是一个完整 JSON，而是按时间往后追加的若干条事件。 每条事件有名字和一段 data。本接口的四个名字：

事件 什么时候发 data 里有什么
meta 检索结束、还没开始生成 检索词、命中、引用、CRAG 步骤
delta 生成过程中，多次 新写出来的那几个字
done 生成结束 message_id、最终引用、耗时
error 中途失败 错误信息

事件之间用空行分帧。规范里的分隔是 \n\n（两个换行）。 sse-starlette（服务端写出 SSE 的库）用的是 \r\n\r\n。\r 是回车， 和 \n 一起组成 Windows 风格的换行。前端若只按 \n\n 切，分隔符对不上， 会一直等下一条，看起来像卡住。解析前先把 \r\n 换成 \n。

浏览器自带的 EventSource 能收 SSE，但只能发 GET。聊天要把问题放在 POST 正文里， 所以改用 fetch：它能 POST，响应体是 ReadableStream，字节一段段到达， 前端自己把字节凑成一帧再解析。

中断生成用 AbortController。前端调用 abort()，这次 fetch 被取消。 服务端的生成器收到取消后，finally 仍会执行——finally 是无论正常结束、 抛错还是被取消都会走的收尾。已生成的半截答案在这里写入数据库，刷新页面不会丢。

Markdown 渲染是手写的大约 60 行：代码块先摘出来，再按行解析列表、表格和引用， 最后把代码块放回去。列表遵循 CommonMark（Markdown 的一份正式规范）里的一条： 列表项之间的空行不会结束这个列表。渲染器若把空行当成"列表结束"， 模型写出的 1. 2. 3. 会全部显示成 1.。

每条回答有"复制"和"检索过程"。后者展开 meta 里的命中和 crag_steps： Playground 的 Trace，收成产品里的一个折叠面板。

# （CREATE TABLE IF NOT EXISTS，不会把已有的表删掉重建）
python -m scripts.init_db

# 启动网站 → 打开 /kb
python -m course.app

# 终端直接体验完整链路（不经网站）
python -c "

print(ans)

"

# KB 单测（34 个中 KB 部分的 22 个）
python -m pytest tests/test_kb.py -q

页面操作路径：文档页签上传/粘贴/查看切块/重建/删除 → 会话页签提问 → 回答里点 [n] 展开出处 → 工具栏勾选 CRAG 再问一次超纲问题，看两轮检索步骤。

标准调参流程（/kbtest 检索测试台）：① 输入一个有代表性的问题； ② A/B 对比——A 保持现状配置，B 只改一个变量（如开/关 Rerank、开/关 CRAG）； ③ 看双列的 top1 分数与小结行，确认改动"值得"再进 /kb 的默认配置； ④ 满意的配置用真实会话验证，点 👍 沉淀进金标，跑一次评测记录趋势。 这四步就是第 10 节"先金标后改进"在产品里的日常形态。

17.7 注意事项

  • KB 与课程实验共享数据库：KB 的块写进主表（隔离靠 corpus+doc_id 前缀）， 做 exp 重跑时别把 corpus='kb' 的块当垃圾清了；反过来，KB 的"重建全部" 只碰自己的 doc_id；
  • LLM 降级时condense 与 CRAG 自动跳过（is_real 检查），此时多轮追问 退化为"拿原始问题直接检索"——产品不会崩，但体验变差，徽章会提示；
  • doc_id 用文件名当主键。同一目录下同名文件会互相覆盖，这是设计：重传就是更新。 若要同名的不同版本并存，可以改成内容寻址：用内容的哈希当 id， 内容一变 id 就变，同名文件不再抢同一行；
  • 流式回答的 llm_ms 在 done 事件里才完整（meta 时还没生成）——前端 耗时脚注用的是 done 的 timings；
  • 50MB 上限和扩展名白名单在后端校验（kb/ingest.py 的 ALLOWED_EXTENSIONS）。 前端的 accept 只影响文件选择框，拦不住改过的请求。安全边界在服务器上。

17.8 评测闭环：反馈 → 金标 → 自有评测

产品层最有价值的一块（第 10/13 节评测思想的落地）：用户对回答点 👍/👎， 点赞的问答对自动沉淀成用户自有金标，再在其上评测 KB 的检索配置。

回答操作行的赞（`kb/store.py` 的 `set_feedback`，写入 `rg_kb_messages.feedback`）。
给已有表加这一列的迁移也是幂等的：列已经在，就不再加一次。
   ↓ 「沉淀金标」（kb/eval.py:49 build_gold → data/kb_eval/gold.json）
问题 + gold_docs = 回答引用的文档列表（用户背书："这些文档答对了我的问题"）
   ↓ 「运行评测」（kb/eval.py:76 run_kb_eval）
三方案对比（Rerank off / on / +CRAG）× 文档级 recall@5 / mrr@5
—— 与第 10 节 _recall_mrr 同一思想，检索路径走 kb.chat.retrieve_kb

金标口径的取舍：gold_docs 来自"回答实际引用的文档"，比专家标注宽松 （引用了≠唯一出处）；但它是用户背书的、随使用自动增长、零标注成本—— "用户自有金标"与"专家金标"的取舍正是第 12 节选型卡片在产品里的体现。 评测页签在 /kb 侧栏第三个标签，点赞后两键完成闭环。

另有同轮加的限定范围提问：文档列表新增「📌 问这篇」，检索被钉在该文档内 （kb/chat.py 的 _recall(doc_ids=...)，双路召回后按 doc_id 过滤再融合）； 限定范围内 CRAG 自动关闭——范围是用户钉死的，扩展查询不能突破它。 注意当前实现是"检索后过滤"（候选窗 30 再筛），个人规模够用；文档数上千时应 把 doc_id 写进 SQL WHERE（第 9 节 9.1 的"检索中过滤"）。

v3 补充的产品件：① ↻ 重新生成——服务端删旧回答（store.py:224 delete_message + last_exchange 定位最后一组问答）后复用同一条聊天管线； ② 只检索不生成。generate=false 时跳过 LLM，检索面板自动展开。 这类消息不进金标。筛选用的是第 9 节的 ->>：trace->>'generate' 从 jsonb 里取出文本， 条件是它不等于 'false'； ③ 评测历史。每次 run_kb_eval 向 history.jsonl 追加一行。 JSONL 是"每行一条 JSON"的文本，方便追加，不用每次重写整个数组。 配合使用概览（会话数、问答数、反馈、拒答率、平均耗时，用 SQL 聚合 trace 里的 jsonb） 构成 KB 的仪表盘雏形； ④ 金标口径收紧——👍 时展开"哪些引用真正答对了"勾选面板，勾选结果以 JSON 存进 feedback_note，gold_candidates 优先采用（校验：只接受出现在 引用列表里的 doc_id，不信任前端）；⑤ 检索测试台 /kbtest——免开会话、 只跑检索侧的调参页（Rerank/CRAG/top_k/范围可调，逐轮命中+耗时）； ⑥ 溯源闭环——引用卡「📍原文」一键打开原文切块弹窗并高亮定位到被引用 的那一块（citations 已带 chunk_id）； ⑦ 测试台 A/B 对比——/kbtest 支持双配置并排跑同一问题（如 Rerank 开 vs 关）， 自动生成"top1/拒答"差异小结——单变量消融的产品化形态； ⑧ 数据资产化——/api/kb/export 把文档原文+会话+金标+评测历史打包成 JSON 备份；每次评测同步写 experiments/kb_eval.md 进课程实验报告目录； ⑨ 备份导入恢复——/api/kb/import 反向恢复：文档重入（checksum 去重， 同名同内容自动跳过）、会话追加迁移（含反馈）、金标覆盖、评测历史追加； pdf/docx 为二进制不经 JSON 导出，重传原件即可； ⑩ 金标管理——评测页签直接查看金标清单（问题 + gold_docs），一键删除 单道题（delete_gold_item 只动金标文件，不碰会话与反馈）； ⑪ 趋势折线与服务器快照。评测页签用 SVG 画三方案 recall@5 随运行次数的折线 （SVG 是用标签描述图形的一种 XML，放大不会糊）。data/kb_snapshots/ 保留最近 10 份全量快照， 可下载、可删除。文件名过一道白名单正则，拒绝 ../ 这类路径穿越： 文件名里夹上上级目录，就能读到数据目录以外的文件。正则只允许预期的那一种文件名。 ⑫ 跨会话搜索。会话页签顶部搜历史问答。SQL 用 ILIKE：不区分大小写的模糊匹配， % 匹配任意长度的一段字。用户输入里的 % 和 _ 要先转义， 否则一个百分号会变成"匹配任意内容"。点结果会跳到那次会话，滚动到对应消息并闪一下。 消息节点带 data-mid，用来在页面上找到那一条； ⑬ 示例语料一键导入——「📚 导入示例语料」把 data/mineru_corpus 的 Agent 教程 12 章（约 1164 块）喂进 KB（ingest_sample_dir，重复导入安全）， 空知识库立刻变成可真实问答的助手；配合引用排行（SQL 聚合 citations 的 jsonb 数组）看哪些文档贡献最大；一键清空会话（只删对话，文档/金标不动）。

17.9 对照生态：你在哪、接下来去哪

能力 Dify/RAGFlow/FastGPT 本项目 KB
文档上传 md/txt/pdf/docx/网页… md/txt/pdf/docx（≤50MB）
深度版面解析 MinerU/LayoutML 级 最小文本抽取（复杂 PDF 走第 2 节 MinerU 闭环）
混合检索 + 重排 内置 ✅ 复用课程管线（RRF + bge-reranker-v2-m3）
带引用回答 + 拒答 内置 ✅ [n] 编号引用，点开看原文；低分/零命中双层拒答
多轮对话改写 内置 ✅ condense question（降级自动跳过）
CRAG / 检索纠错 部分产品有 ✅ 可开关，步骤落库可观测
流式输出 SSE 或 WebSocket ✅ SSE 逐字上屏
文档管理/重建/去重 内置 ✅ checksum 去重、单篇/全量重建、级联删除、切块检查
多用户/权限/工作流 ✅ ❌ 明确不做（个人单机定位）

WebSocket 是浏览器和服务器之间的双向长连接。SSE 只允许服务器往浏览器推。 逐字输出用 SSE 就够，本项目没有再开一条 WebSocket。

四个扩展方向（生态趋势 → 对应课程位置；评测闭环与口径收紧已于 17.8 接入）：Agentic 化（第 16 节控制流地图）； GraphRAG（第 14 节的 graph_recall 可以作为第三路召回接进 _recall）； 深度解析（scripts/ingest_mineru.py 的产物转投 KB，换 parser 而已）； 把独立检索测试台（/kbtest，免开会话的调参页）接进日常调参流程。

17.10 动手练习

  1. 上传一份你自己的文档（或粘贴一段文本），用"查看切块"检查 kb600x120 的切分质量，找一块被切断的上下文，想想该调 size 还是 overlap；
  2. 勾选 CRAG 问一个超纲问题，展开"检索过程"面板，数一数几轮检索、 每轮 top1 分数多少——对照 16.3 的阈值证据；
  3. 开/关 Rerank 各问同一题，对比拒答行为的变化（没精排时拒答只剩"零命中" 这一层——为什么？回看 17.4.3 与 crag_verdict 的 unknown 分支）；
  4. 导出一次会话为 Markdown，人工核对答案中的 [n] 与引用列表是否对得上 ——这就是最简单的 Faithfulness 抽查（第 13 节的裁判干的也是这事）。
