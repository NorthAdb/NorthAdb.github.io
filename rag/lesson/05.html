BM25 稀疏检索：为什么它还没死

第 05 节约 30 分钟本节自测

TF-IDF → BM25 公式逐项拆解；jieba 分词；符号题吊打 Dense 的现场；v3：BM25 的工程亲戚（tsvector/BM25F）。

本节任务：把 BM25 公式的每一项与代码对上号，理解"分词器是这个实现里 最重要的决策"，并能解释为什么 2026 年的生产 RAG 依然人手一路 BM25。

课程地图上的位置：Layer 2 第二站。上一节 04 向量检索；下一节 06 RRF 融合——BM25 与 Dense 是融合的两路输入。

5.1 从 TF-IDF 到 BM25

BM25 的打分公式（playground/retrieve/bm25.py:3-5 的模块注释里也写着）：

score(q, d) = Σ_t  IDF(t) · tf · (k1 + 1) / (tf + k1 · (1 - b + b·|d|/avgdl))

逐项拆开，每一项都在修 TF-IDF 的一个毛病：

项 作用 修的毛病
IDF(t) 词在多少文档出现过：越罕见越有区分度 "的、是、和"人人都有，区分度≈0
tf（分子） 词在本文档出现越多分越高 早期 TF 线性放大
k1≈1.5 词频饱和：出现 3 次很重要，30 次不会重要 10 倍 长文档堆砌关键词刷分
b≈0.75 长度归一：长文档天然词多，把便宜压回去 长文档霸榜

直觉总结：BM25 问的是"关键词对不对得上"，Dense 问的是"意思像不像"。

5.2 代码走读（playground/retrieve/bm25.py，90 行）

5.2.1 分词器（bm25.py:26-35）——本实现最重要的决策

_TOK_RE = re.compile(r"[a-zA-Z0-9][a-zA-Z0-9\-_.]*")     # :26 英文 token 的形状

def tokenize(text):
    zh_removed = _TOK_RE.sub(" ", text)      # :30 先把英文 token 挖掉
    tokens = _TOK_RE.findall(text)           # :31 整体切出英文 token
    tokens += [t for t in jieba.cut(zh_removed)      # :32 剩下的中文给 jieba
               if re.search(r"[\u4e00-\u9fff]", t)]  # 只留含汉字的
    return [t.lower() for t in tokens if t.strip()]  # :35 全部小写归一

这个两段式分词器是符号题的命脉：

  • 若把 AVX-512 按连字符切成 avx + 512，查询"AVX-512 寄存器"就会匹配到 所有含 512 的块（包括"512 KB L2"）——噪声暴增。正则 :26 里的 \-_. 让 SSE4.2、AVX-512、VPGATHERDD 各自是一个完整 token；
  • 中文走 jieba（bm25.py:19 顶部 import），对技术文档够用；生产中文检索常见 做法是领域词典 + jieba 自定义词（jieba.add_word）；
  • 英文先挖再分的顺序很讲究：如果先 jieba 整句，jieba 会把英文拆成碎片再交回来。

单测 tests/test_core.py 里专门有 tokenize 的保护用例：改分词器后跑 python -m pytest tests/test_core.py -q，把 AVX-512 拆开的改动会被当场拦下 （第 13 节讲这个"指标保护"思路）。

5.2.2 索引构建（bm25.py:38-51）

BM25 本体直接用 rank_bm25.BM25Okapi（工业标准实现），但索引构建是手写的：

@functools.lru_cache(maxsize=8)              # :38 进程内缓存，key=(strategy, corpus)
def _build(strategy, corpus):
    rows = q("""                              # :41-47 从 rg_chunks 拉块
        SELECT id, doc_id, chunk_index, content, section_path, parent_id
        FROM   rg_chunks
        WHERE  strategy = %s AND meta @> %s::jsonb
        ORDER  BY doc_id, chunk_index """, (strategy, f'{{"corpus":"{corpus}"}}'))
    corpus_tokens = [tokenize(r[3]) for r in rows]       # :49 每块分词
    bm25 = BM25Okapi(corpus_tokens) if corpus_tokens else None   # :50 建倒排
    return rows, bm25

三个要点：

  1. BM25 索引在内存里，不在数据库里——这里的"索引"指倒排表： "一个词 → 出现在哪些块"的查找表（搜索引擎的经典地基）。每次进程重启后 第一次检索要重建（本语料毫秒级；生产会换 tsvector 或专用引擎）；
  2. lru_cache 的 key 是 (strategy, corpus)，与向量检索的隔离维度完全一致；
  3. 缓存失效要手动：入库/删库后必须 bm25._build.cache_clear()——KB 系统 就是在 kb/store.py:169 的 clear_retrieval_caches() 里做这件事。 这是"进程内缓存 + 数据库"组合的经典坑：数据库变了，缓存不知道。

5.2.3 查询（bm25.py:54-81）

def bm25_search(query, top_k=config.BM25_TOP_K, strategy="flat500x80", corpus="main"):
    rows, bm25 = _build(strategy, corpus)
    if not rows or bm25 is None:
        return []                                  # 空库直接返回（:58-59）
    scores = bm25.get_scores(tokenize(query))      # :60 一次算全库分数
    order = sorted(range(len(rows)), key=lambda i: scores[i],
                   reverse=True)[:top_k]           # :61 取前 K
    for r_i, i in enumerate(order):
        if scores[i] <= 0:                         # :64 零分 = 完全没词面重合，不进结果
            break
        hits.append(Hit(..., score=float(scores[i]), source="bm25", ...))

:64 附近的丢弃条件值得停一下（v3 修正版）：它判断的不是"分数 ≤ 0"而是 "词面零重合"（qtok & set(corpus_tokens[i]) 为空才丢弃）。原因是一个真实踩到的 边界 bug：超小语料里独有词的 IDF 会退化成 0（N=2 篇时 log(1.5/1.5)=0）， 只看分数会把"有词面重合"的有效命中也丢掉——两篇文档的知识库永远检索不到东西。 这个案例的教训：用分数大小近似"相关性"时，先检查分数在极端语料规模下的退化行为。 对比 Dense：余弦相似度永远 > 0（除非正交），Dense 没有"零重合"这个概念， 这正是两路互补的根源之一。

5.3 如何运行

5.4 实验 1 的分题型数据（Dense vs BM25）

同样出自 python -m scripts.run_eval 的第 1 组（exp1_retrievers，报告里的 "分题型表现"表）：

题型 Dense（recall@5 / MRR@5） BM25（recall@5 / MRR@5） 谁赢
near_confusion（AVX vs AVX-512） 1.00 / 1.00 0.75 / 0.75 Dense —— 词面几乎相同的两篇，IDF 分不清
semantic（语义改写题） 1.00 / 1.00 1.00 / 1.00 平（语料小；大语料上 Dense 优势明显）
symbol（STTNI、PCMPGTQ…） 1.00 / 0.75 1.00 / 0.75 文档级打平——名次内的差异要靠 Playground 逐题看
全部 23 道可回答题 1.00 / 0.880 0.957 / 0.808 Dense

（口径：30 题金标中的 23 道可回答题；文档级指标，即"正确答案所在文档进没进 Top-5、排第几"。）

三个值得记住的现象：

  1. BM25 的 MRR 输给 Dense：它只看词面，命中但排不进最前；
  2. 符号题在文档级打平，不代表两路一样：BM25 查询里的生僻 token（STTNI） IDF 巨大、一锤定音，第一名的分数远比 Dense "自信"。去 Playground 分别用 Dense/BM25 问"PCMPGTQ 属于哪个扩展"，对比第一名的分数与块内容—— 文档级指标看不出名次内的形态差异，要靠块级分数与逐题 Trace（第 10 节）；
  3. near_confusion 是 BM25 的死穴：AVX 与 AVX-512 在词面上互为前缀， 纯词法模型区分不了"说的是哪一代"，需要语义（或元数据过滤）。

5.5 为什么"有了 Embedding"还要 BM25

把实验 1 的两个单路放在一起看：

Dense  R@5=1.00  MRR=0.880   ← 语义泛化强，符号题排名飘
BM25   R@5=0.957 MRR=0.808   ← 符号题一锤定音，语义改写弱
Hybrid R@5=1.00  MRR=0.928   ← 互补之后的和，稳过任一单路（下一节的主角）

生产场景里 BM25 不可替代的还有两个理由：

  • 新词免疫：产品代号、错误码今天刚发明，Dense 模型没见过，BM25 照抓；
  • 可解释：BM25 的分项（IDF、tf、长度）都能算给你看，出问题能定位。

5.6 注意事项

  • 改了分词器 = BM25 索引全部作废：_build 的 lru_cache 里缓存的是旧分词 结果，进程要重启，且旧索引是用旧 tokenize 建的——严格说要清缓存重建；
  • BM25 内存索引不跨进程共享：网站进程与脚本进程各建各的，改库后两边都要 失效（多进程生产环境要么用共享索引，要么接受重建成本）；
  • 中文查询先想想分词对不对：doc_freq_stats 是你的放大镜——某词命中 0 篇， 多半是分词把它切碎了，而不是语料里没有。

5.7 加厚（v2）：稀疏检索 vs 稀疏嵌入——术语矩阵

常见疑问："有稀疏检索，那稠密检索呢？稀疏嵌入/稠密嵌入涉及吗？" 先把**任务（检索）和表示（嵌入）**分开，再拼成一张矩阵就清楚了。

统计派（权重是公式算的） 学习派（权重是模型训的）
稠密表示（每维都有值） 词袋哈希投影（我们的降级 HashingEmbedder） 稠密嵌入：BGE-M3 dense → 稠密检索（第 4 节）
稀疏表示（绝大多数维为 0） BM25 / TF-IDF → 传统稀疏检索（本节） 稀疏嵌入（learned sparse）：SPLADE、BGE-M3 的 sparse lexical weights

所以：

  • 稠密检索 / 稠密嵌入：有，就是第 4 节（"向量检索"是它的通俗叫法）；
  • 稀疏检索：有，就是本节的 BM25——但注意它是统计派；
  • 稀疏嵌入：课程没有专门实现。它指"模型学出来的稀疏表示"（SPLADE 是代表； BGE-M3 本身有 Dense / Sparse / Multi-Vector 三种表示——本课程只用了 dense 输出， 因为硅基流动的 embeddings 接口实测只返回 dense，不含 sparse 权重）。

学习派稀疏 vs BM25：learned sparse 能给同义词/变体分权重（"汽车"→"车辆" 也有非零权重），且不需要人工分词器；代价是要专门训练/加载模型、索引格式特殊。 课程选 BM25 的三个理由：① 透明可手写（公式 10 行）；② 存储友好（内存倒排表）； ③ BM25 + dense 经 RRF 融合已覆盖两路主要信号。想亲手玩 learned sparse： FlagEmbedding 库本地跑 BGE-M3 可同时输出三种表示——"用 BGE-M3 sparse 权重 替换 BM25 路、其余不动、金标对比"就是一个标准的单变量消融（留作练习）。

5.8 动手练习

  1. Playground 用 BM25 模式查"AVX-512 引入年份"，再查"向量计算的指令集有哪些"， 体会同一检索器在两类问题上的表现差；
  2. 跑 5.3 的 doc_freq_stats，解释为什么 512 这个 token 的文档数远多于 AVX-512（答：正则保护 + 语料里单独的数字到处出现）；
  3. 思考：如果文档是纯英文技术手册，tokenize 需要改什么？（提示：jieba 那条路 会空转，但没错；真正要小心的是大小写与复数。）

5.9 加厚（v3）：BM25 在工程里的亲戚

手写 BM25 是为了懂原理；生产里你大概率用现成实现，各有各的生态位：

实现 生态位 与本课程的对应
PostgreSQL tsvector / ts_rank 同库内全文检索：不引外部引擎，SQL 一条 @@ 就有 BM25 式排序（配 GIN 索引，0.7 见过） 想省掉内存倒排表（5.2.2）时的替代路
Elasticsearch / OpenSearch 分布式检索引擎，BM25 是默认评分 中大型生产的 BM25 标配；运维成本是代价
BM25F 字段加权版：标题命中比正文命中值钱，按字段分别算 tf 再合成 标题前缀（3.2.3）是它的"穷人版"——把标题塞进同一段文本
覆盖度评分项（ts_rank_cd / Lucene） 考虑"命中几种不同的词" LexicalReranker 的 cover/density（7.2.2）就是它的朴素版
查询扩展（RM3 等） 用首轮命中的高频词扩写查询再检索 multi_query（第 8 节）的"不调 LLM 的统计版亲戚"

选型一句话：数据已经在 Postgres 里且规模中等 → 先试 tsvector + pgvector 同库 Hybrid（少养一套基础设施）；规模大了或分词要求高 → 再上专用引擎。 5.2.1 的分词器纪律在任何实现里都成立：换实现 = 换了分词 = 换了实验条件， 金标要重新对齐。
