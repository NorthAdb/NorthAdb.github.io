框架对照与选型总结

第 12 节约 40 分钟本节自测

LlamaIndex 术语映射 Demo；选型卡片；LLM Wiki 的后续学习入口；v4：Node、Retriever、Ragas 等框架名词在首次出现处展开。

本节任务：用 LlamaIndex 校对自己的概念命名，然后收束成选型卡片与 后续路线。读完的检验标准：手写的每一块都能在框架里找到位置。

课程地图上的位置：主线 C 的收口。上一节 11 结构化扫盲； 下一节 13 评测进阶（v2 加厚篇开始）。

12.1 为什么要看框架

自己手写一遍之后看框架，看的是设计决策而不是 API 用法： "这个概念它叫什么？拆在哪一层？和我拼的位置一样吗？" （计划书阶段 8 的原话：用框架校对自己的概念命名和模块切分。）

12.2 术语映射表（手写 → LlamaIndex）

LlamaIndex 是一套把"加载、切分、索引、检索、生成"串起来的 Python 框架。 表里的类名先有个着落，再看和手写代码差在哪。

  • Document 是入库前的一篇原文，相当于 RawDoc。Node 是切完之后的检索单元， 相当于 Chunk，并且自带指向父节点和子节点的链接。Parent-Child 因此可以不另建 rg_parents，父子关系就挂在 Node 上。
  • Splitter（切分器） 负责把 Document 切成 Node。SentenceSplitter 尽量在句子边界 上滑窗；TokenTextSplitter 按 token 数滑窗。滑窗就是第 3 节的 overlap： 下一块从上一块末尾往前重复一段，避免一句话正好被切在边界上。
  • Postprocessor（后处理器） 挂在检索之后、生成之前。重排、按元数据过滤， 都属于这一层。SentenceTransformerRerank 是其中的重排器。 本课程把标题前缀直接写进 embed_text；框架里常在命中之后再用元数据把上下文贴回去。
  • Retriever 是"给定问题，返回一批 Node"的接口。向量检索和 BM25 各是一个 Retriever。
  • QueryFusionRetriever 把多个 Retriever 的结果合成一份。 mode="reciprocal_rerank" 就是第 6 节的 RRF：按名次的倒数相加，不比较原始分数。 num_queries 表示它还会把原问题改写成几条，每条各检索一次再融合。 num_queries=2 就是原问题再加 1 条改写，相当于第 8 节 multi-query 的缩小版。
  • ResponseSynthesizer 把 Node 填进 Prompt 再调用 LLM。本课程把这件事拆成了 context_builder 和 llm。PromptHelper 管 token 预算，决定塞得下几块。
  • docstore 是框架在内存里按 id 存放 Node 原文的那一层。BM25 从这里读文本， 不读向量。VectorStoreIndex 是向量索引对象，as_retriever 把它变成一个 Retriever。 PGVectorStore 把这一层接到 PostgreSQL + pgvector。本节 Demo 没有用它。
本课程的模块 LlamaIndex 里叫 差异点
RawDoc / Chunk Document / Node Node 带 parent/child 关系（天然支持 PC）
chunker.fixed_chunks（chunker.py:96） SentenceSplitter / TokenTextSplitter 同为"段落优先滑窗"
chunker 标题前缀（chunker.py:106） MetadataPostprocessor / embed_model 包一层 框架里叫"上下文增强"
embedder（embedder.py:31） BaseEmbedding 同为双塔，接口几乎一一对应
vector_store（vector_store.py:30） VectorStoreIndex + PGVectorStore HNSW 参数：ours=手工 SQL，框架=参数传入
bm25（bm25.py:54） BM25Retriever（llama-index-retrievers-bm25） 内部同样是 BM25Okapi
hybrid.rrf_fuse（hybrid.py:22） QueryFusionRetriever 默认就是 RRF，num_queries 即多路改写
reranker（reranker.py:22） NodePostprocessor（如 SentenceTransformerRerank） 框架把精排抽象成"后处理器"
context_builder（context_builder.py:27） ResponseSynthesizer + PromptHelper 预算/装填被合并进"合成器"
evaluate.py（evaluate.py:135） 无内建（社区 Ragas 项目） 评测框架不做，要自己接——本课程的立场

看到没有：你手写的每一块都能在框架里找到位置——这就是"能看懂"的完成标准。

12.3 框架 Demo 的代码走读（scripts/demo_llamaindex.py，110 行）

python -m scripts.demo_llamaindex        # 首次会调 embedding API 建内存索引

Demo 分四步，每步对应我们手写的一个部件：

# 1) 接入模型（:37-51）：OpenAILike 接 DeepSeek、OpenAIEmbedding 接硅基流动
llm = OpenAILike(model=config.LLM_MODEL,
                 api_base=f"{config.DEEPSEEK_BASE_URL}/v1", ...)
embed = OpenAIEmbedding(model_name=config.EMBED_MODEL,
                        api_base=config.SILICONFLOW_BASE_URL,
                        embed_batch_size=24)   # :48 与我们 _BATCH=24 一致

# 2) 同一批语料进内存索引（:54-62）：SimpleDirectoryReader 读 data/corpus
index = VectorStoreIndex.from_documents(docs)

# 3) 框架版 Hybrid（:65-76）
vector_ret = index.as_retriever(similarity_top_k=10)
bm25_ret = BM25Retriever.from_defaults(docstore=index.docstore, similarity_top_k=10)
fusion = QueryFusionRetriever([vector_ret, bm25_ret],
                              num_queries=2,               # 原始 + 1 改写：multi-query lite
                              mode="reciprocal_rerank")    # 即 RRF

# 4) 对比提问（:80-97）：同一问题并行跑框架版与手写版（:86 手写 Hybrid），
#    Top-3 并排打印 + 框架生成回答

OpenAILike 和 OpenAIEmbedding 说的是调用形状：请求按 OpenAI 那套 HTTP 接口来写。 模型可以仍是 DeepSeek 或硅基流动，api_base 把地址指到对应的服务。 SimpleDirectoryReader 按目录读文件，变成一串 Document，相当于本课程的 loader.load_main()。

观察任务：同一个问题，框架版的命中块与本课程版一致吗？ （大方向应一致；个别名次差异来自分词器与 chunk 边界的微小不同—— 这正是"换实现 = 换了实验条件，金标要重新对齐"的实例。）

注意 Demo 的索引在进程内存里，每次运行重建，进程结束就没了。 它没有接课程的 pgvector 表，只做概念对照。真要落库，用 llama-index-vector-stores-postgres 包里的 PGVectorStore，那已经超出本节的目标。

12.4 选型卡片（结业工具）

问题类型                          → 该加哪一层
─────────────────────────────────────────────────────
局部语义事实                      → Vector RAG
有符号/编号/型号/术语             → + BM25 + RRF（Hybrid）
候选够，但 Top-K 不准             → + Rerank
用户口语与文档术语不一致          → + Query Rewrite / Multi-Query
检索对了答案仍胡编/丢引用         → 改 Prompt 约束 + 引用 + 拒答（不是换模型！）
小块才能命中、大块才够回答        → + Parent-Child
脏数据/错章/索引不一致            → 清洗 + 元数据 + checksum（不是换检索器！）
检索不可靠、需要"刹车"           → + CRAG（第 16 节；KB 已内置可开关）
章节长文档的层级/全局摘要题       → 考虑 RAPTOR
实体关系/多跳/全局主题            → 考虑 GraphRAG / LightRAG
证据已在 Context 仍答不好         → 最后才考虑换更大 LLM

配套的诊断顺序（第 10 节的 8 步清单）+ 这张卡片 = 计划书定义的"能诊断与选型"。 第 17 节的 KB 系统就是把这张卡片的默认配置做成产品：Hybrid+Rerank 常开、 CRAG 可选、拒答双层。

[!IMPORTANT] 计划书的核心原则，作为结业赠言： 不要以"部署成功"为完成标准，而以"能解释每个检索结果为什么出现、 换一种方案为什么会改变结果"为标准。 本课程的每个数字都来自你本机的真实运行——它们可以被你随时重跑、质疑、推翻。 这就是工程学习与背概念的区别。

12.7 延伸：评测框架对照（Ragas / TruLens / DeepEval）

第 13 节手写了 judge，再看社区评测框架，就是"手写 vs 框架"的评测版。

  • Ragas 实现的是第 13 节那三个分数：Faithfulness、Answer Relevance、 Context Relevance。社区把这三个分数叫 RAG triad，中文材料里也会写成"RAG 三元组"。 它和第 11、14 节图上的三元组（主体、关系、客体）不是同一个词。
  • TruLens 把每次调用的输入、检索到的块、模型输出记成一条 trace，再在界面上打分。 本课程的 Trace 面板是同一想法的手写版。
  • DeepEval 把"分数低于阈值"写成 pytest 风格的断言。pytest 是 Python 的测试运行器， 收集 test_ 开头的函数并执行；断言失败，这次改动就被拦下来。 和第 13 节用单测守住 Recall/MRR 是同一纪律，对象从硬指标换成了裁判分数。

选型判断与 12.1 相同：手写一遍再看框架，看的是它们怎么处理裁判 Prompt 的版本、结果缓存和抽样。概念已经在第 13 节。框架替代不了 13.4 的三条纪律， 也替代不了 13.5 里用金标算出来的硬指标。
