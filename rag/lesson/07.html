Reranker：召回与精排的分工

第 07 节约 30 分钟本节自测

Cross-Encoder vs 双塔；rerank 救不了没召回的题；v2：ColBERT 晚交互、LLM 重排光谱；v3：reranker 训练数据与 hard negatives。

本节任务：能说清双塔与 Cross-Encoder 的成本/精度交换，知道 rerank 分数 为什么是全课程"最可信的相关性信号"（第 13 节 judge、第 16 节 CRAG、KB 的 拒答阈值都建在它上面）。

课程地图上的位置：Layer 2 最后一站。上一节 06 RRF；下一节 08 查询改写与装填。输入是融合后的候选（≤30 个 Hit），输出是 重排后的同一些 Hit（score 换成了 rerank 相关性分）。

7.1 双塔 vs 交叉编码器

双塔（第 4 节）        Query → [Enc] → v_q ┐
                      Doc   → [Enc] → v_d ┴→ cos(v_q, v_d)   ← 独立编码，可离线
Cross-Encoder（本节）  [CLS] Query [SEP] Doc → [Enc] → score  ← 拼一起进模型

Cross-Encoder 让 Query 的每个 token 与 Doc 的每个 token 在注意力层直接交互， 所以相关性判断准得多。代价：每个 (Query, Doc) 对都要过一次模型—— 离线预计算不可能了，只能用在"候选已经很少"的精排阶段。

Retriever（双塔/BM25）→ 高 Recall：从全库捞出 30 个候选，宁可错杀不可放过
Reranker（Cross-Enc） → 高 Precision：30 → 5，把真正相关的顶到前排

两个词对照着记：Recall（召回率）＝该拿回来的有没有都拿回来； Precision（精确率）＝拿回来的里面有多少真是对的。检索层（第 4-6 节） 追求 Recall，精排（本节）追求 Precision——分工不同，不冲突。

7.2 代码走读（playground/retrieve/reranker.py，107 行）

7.2.1 在线版：SiliconFlowReranker（reranker.py:22-53）

class SiliconFlowReranker:
    name = config.RERANK_MODEL                    # :22 "BAAI/bge-reranker-v2-m3"

    def rerank(self, query, candidates, top_k=config.TOP_K):
        if not candidates:
            return []                              # :34 空候选直接返回
        docs = [c.content for c in candidates]     # :36 只送正文
        r = self._client.post(_SILICONFLOW_RERANK_URL,     # :38 /v1/rerank
              json={"model": self.name, "query": query,
                    "documents": docs, "top_k": top_k})
        results = r.json()["results"]              # :42 [{index, relevance_score}]
        for r_i, item in enumerate(results):
            h = candidates[item["index"]]          # :44 按 index 找回原 Hit
            out.append(Hit(..., score=float(item["relevance_score"]),
                           source="rerank", rank_in_stage=r_i))

要点：

  • 一次 HTTP 调用带 query + 30 个候选，返回每条的相关性分数——注意与 embedding API 的区别：它是 (query, doc) 对级别的打分，所以候选多时贵；
  • 返回的 Hit 保留原文档信息、只换分数与名次（:46-52），source="rerank" 让下游（装填、展示、评估器）能区分这列分数的语义；
  • rerank 分数是未经校准的相关性概率：强相关常见 0.9+，完全不相关接近 0—— 这个"两极分化"的形态正是它当评估器的资本（见 7.4 与第 16 节）。

7.2.2 降级版：LexicalReranker（reranker.py:56-89）

def rerank(self, query, candidates, top_k=config.TOP_K):
    qtok = set(tokenize(query))                    # :67 复用第 5 节的分词器
    for h in candidates:
        dtok = tokenize(h.content)
        cover   = len(qtok & set(dtok)) / max(len(qtok), 1)   # :75 覆盖率：query 词命中比例
        density = len(qtok & set(dtok)) / len(set(dtok))      # :76 密度：块内命中占比
        scored.append((0.7 * cover + 0.3 * density, h))       # :77 固定权重合成

与 BM25 的区别在于它是"Query 对单个候选的匹配度"，不再考虑 IDF 全局统计—— 作为离线降级够用，也直观展示 rerank 位置该干什么。注意 :77 的 0.7/0.3 是 拍脑袋定的：这正好说明降级路径的定位是"保可用"，不是"保最优"。

探活与选择在 get_reranker()（reranker.py:92-106）：用一条真实调用探活 （构造一个 probe Hit 打一次 rerank API），失败则降级并打警告。

7.4 实验 1 的诚实结论

来自 python -m scripts.run_eval 第 1 组（exp1_retrievers，文档级指标）：

方案 MRR@5 noise@5 评测总耗时（23 题）
Hybrid(RRF) 0.928 0.557 ~0.1s
Hybrid+Rerank 0.928 0.557 ~13.3s

在文档级指标上 rerank 没有改变数字——为什么？两个原因：

  1. 语料只有 16 篇，RRF 的 Top-1 已经基本正确，没有"排错了"可修；
  2. 文档级 MRR 天然饱和（第 10 节会讲指标设计）。

但这不是"rerank 没用"的证据。看一次真实的逐题对比（flat500x80， 问题："SSE4.2 新增的字符串处理指令集缩写是什么？"）：

RRF 融合后：                     Rerank 后：
1. sse      0.0328               1. sse          0.9985  ← SSE4.2 权威段
2. sse      0.0323               2. sse          0.9808  ← 实用记忆点
3. sse      0.0313               3. cpu-faq      0.9790  ← Q2（相关但间接）
4. cpu-faq  0.0313  ← FAQ 提前    4. simd-compare 0.5500
5. sse      0.0303               5. sse          0.4606

RRF 把 cpu-faq 的 FAQ 段顶到第 4（它词面密度高），Cross-Encoder 则把 真正定义 STTNI 的段落抬到第 1，并给出 0.9985 这种"几乎肯定相关"的分数。 排序质量肉眼可见地变好，只是本题恰好没有因此改变命中文档。

什么时候 rerank 是刚需：候选池更杂（多来源、脏数据）、语料上万块、 Top-K 名额昂贵（K 小、上下文预算紧）。计划书说得很对：Reranker 救不了 "金标根本没进候选"——那是召回/切分/清洗的问题，加 rerank 只是烧钱。

7.5 重排分数作为评估器（贯穿后面三节课的伏笔）

rerank 分数的三个下游，理解了它们就理解了"精排不只是排序"：

下游 位置 用法
拒答评估器 第 16 节 demo_crag.py:20（LOW_SCORE = 0.35） top1 < 0.35 → 触发纠正/拒答
KB 拒答阈值 kb/config.py:25（KB_LOW_SCORE_REFUSAL=0.35）+ kb/chat.py 拒答判定 阈值实测证据：可回答题 top1 多在 0.9+，含糊题 0.1-0.3，分界清晰
上下文压缩 第 7 节加厚 低分块先压缩再装填，省预算

7.6 成本账

每题多 ~0.5s（30 候选一次 API 调用）
本课程 23 道可回答题 × 1 次 rerank ≈ 13s（实验 1 的 +Rerank 行）
生产：QPS × 0.5s × 单价——所以很多系统先跑 RRF，只在低置信度时才 rerank

7.7 注意事项

  • rerank API 有单请求文档数上限：候选太多要分批打分再合并（本课程 30 候选 一次过，OK；几百候选先粗筛）；
  • rerank 分数跨查询不可比（每题的分数分布不同），只能用于题内排序与阈值；
  • 排序 ≠ 召回：rerank 只能在"已召回的候选"里重排。指标没变先查是不是 没召回（第 10 节诊断清单第 4 步），别急着调 rerank。

7.8 加厚（v2）：重排器的完整光谱

对标 all-in-rag 第四章"检索进阶：重排序"。双塔 vs Cross-Encoder 之外， 完整的重排光谱还有三档：

方案 Query-Doc 交互 成本 适用
双塔嵌入（第 4 节） 无（独立编码） 最低（可离线） 全库召回
ColBERT / 晚交互 token 级（每个 token 存多向量，MaxSim 匹配） 中（多倍存储，检索快） 要双塔的速度 + 更细的匹配度
Cross-Encoder（本节主力） 全交互 高（每候选一次前向） 候选 ≤ 50 的精排
LLM 重排 全交互（Prompt 里让 LLM 列表比较/打分） 最高 候选极少 + 需要理由时（可解释！）

两个工程提醒：

  1. LLM 重排是"可解释的重排"：让 LLM 输出"每条相关度 + 一句理由"，缺点是慢、 贵、位置偏差（偏爱排在前面的）——只适合 ≤10 条的最终裁决；
  2. Context Compression（上下文压缩）是重排的姊妹：检索后用小模型/LLM 把每块 压成只与问题相关的句子再进 Context。我们的 noise@5 ≈ 0.55 说明有一半内容 是凑数的——压缩的收益空间实测存在，最省钱的实现是第 13 节的 judge Prompt 顺手标出无关块。

7.9 动手练习

  1. Playground 问"SSE4.2 新增的字符串处理指令集缩写是什么"，勾选/取消 Rerank， 对比两份 Top-5 名单与分数形态（余弦/RRF 的分数挤在一起，rerank 分数拉开差距）；
  2. 勾选 Rerank 后看耗时条——哪一步涨了？
  3. 用 7.3 的终端示例亲手打一次 rerank API，观察"强相关 vs 无关"的分数差距 ——这就是 7.5 所有下游应用的物理基础；
  4. 思考：如果你只有 1000 块语料、Top-K=10，值得为 rerank 付 0.5s/题吗？ 什么时候答案会变成"值得"？

7.10 加厚（v3）：Reranker 是怎么练出来的——hard negatives

bge-reranker 这类 Cross-Encoder 不是"设计"出来的，是在成对的标注数据上微调 出来的。训练数据长这样：(查询, 正例文档, 负例文档)——正例是真回答了问题的块， 负例是"看起来相关但不回答"的块。数据的灵魂在负例的选法：

  • 随机负例：从语料里随便抽个不相关块——太容易了。模型只学会"词面不同 = 负例"，这种题不需要精排能力；
  • hard negatives（难负例）：挑BM25/Dense 排得很靠前、但并不回答问题的块 当负例。查询"AVX-512"时，"AVX"的块就是天然难负例：词面几乎一样，答案完全 不同——模型必须学会看语义细节才能排除它，这正是精排的本职。

与课程的两处连接：

  1. 金标的 near_confusion 题型（第 1 节 1.5）就是给检索系统的"难负例考卷"—— 第 5 节实验里 BM25 在这类题上翻车（recall 0.75），正因为它只会词面；
  2. 训练流水线是本课程管线的倒影：先用粗检索（第 4-6 节）从海量数据里捞出 "高分但不正确"的候选当难负例，再训练精排模型学会排除它们——粗排与精排 的分工，在训练数据生成阶段就已注定。这也解释了 7.1 的"宁可错杀不可放过"： 粗排的错误形态（捞多了）恰好是精排训练数据的采集器。
