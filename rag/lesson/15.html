查询构造与结构化数据：NL→过滤器、Text2SQL 思路、表格文本化

第 15 节约 40 分钟本节自测

NL→元数据过滤器（白名单校验/安全退化）；Text2SQL 三条铁律；表格文本化三层方案；v4：DML/DDL、schema、EXPLAIN 在首次出现处展开。

本节任务：掌握"让 LLM 生成查询而不是生成答案"的完整方法链： 自然语言→元数据过滤器（动手）、Text2SQL 三条铁律（认知）、表格文本化三层方案（设计）。 上一节 14 极简 GraphRAG；下一节 16 高级范式。

课程地图上的位置：v2 加厚篇第三站。它把第 9 节的 meta_filter（手工指定） 升级成"LLM 自动生成"，与第 14 节的图召回一起构成"查询理解层"的两只手。

15.1 查询构造：过滤是检索的一部分，LLM 是过滤器生成器

NL（natural language，自然语言）就是用户写下的那句话。 查询构造把这句话翻译成程序能执行的结构，翻译的结果是过滤器或 SQL，不是答案。

用户问题 ──LLM──→ {"doc_ids": ["avx512"]}   ← 严格 JSON，白名单校验
                        ↓
        检索：过滤发生在向量检索之内（SQL WHERE），演示代码里先做成检索后筛选

白名单（第 9 节 9.7）是事先定死的合法值集合。这里的合法值是语料里真实存在的 doc_id。 不在名单上的字符串会被丢掉。

scripts/demo_query_construction.py（74 行）的三段代码就是全部：

15.1.1 Prompt：把选择空间塞给 LLM（demo_query_construction.py:25-32）

FILTER_PROMPT = """你是查询构造器。把用户问题翻译成检索过滤条件（JSON），规则：
- 只在问题明确指向某些主题/文档时才填 doc_ids；泛化问题输出 {{"doc_ids": []}}
- doc_ids 只能从列表里选：{docs}
- 输出严格 JSON，不要解释。

问题：{question}

过滤条件："""

第二条规则是把白名单写进 Prompt：模型从第一眼就只看见合法的 doc_id。 校验仍然要做。Prompt 是提示，代码里的名单才是闸门。两道都便宜，漏一道， 编造的 doc_id 就会进检索。

15.1.2 校验：不信任，要验证（demo_query_construction.py:35-44）

def construct_filter(question: str) -> dict:
    out = get_llm().chat(FILTER_PROMPT.format(...), max_tokens=120)
    m = re.search(r"\{.*\}", out, re.S)              # :38 容错截取（同 judge._parse_json）
    try:
        f = json.loads(m.group(0)) if m else {}
    except json.JSONDecodeError:
        f = {}                                       # :42 解析失败 = 空过滤器
    valid = [d for d in f.get("doc_ids", []) if d in DOC_LIST]   # :43 白名单校验！
    return {"doc_ids": valid}

:43 这一行是全节的题眼：LLM 输出进入程序之前，必须过校验层。 就算 Prompt 里已经给了白名单，代码仍然再验一遍——两道闸都便宜，漏一道都贵。

15.1.3 应用：过滤作为检索的前置（demo_query_construction.py:47-61）

plain = dense_search(qv, 5, "flat500x80", {"corpus": "main"})
filtered = plain if not flt["doc_ids"] \
    else [h for h in plain if h.doc_id in set(flt["doc_ids"])][:5]

注意这里的过滤是检索后筛选（演示用，从 plain 里筛），而第 9 节的 meta_filter 是检索中过滤（SQL WHERE）。生产实现应该走后者—— Demo 选择前者是为了让你能并排打印"无过滤 vs 过滤"的对照。这个差别 务必分清（见 15.5 注意事项第 2 条）。

15.2 三道题实测

python -m scripts.demo_query_construction
问题 LLM 构造的过滤器 无过滤 Top-5 过滤后 Top-5
AVX-512 的掩码寄存器有几个？ ["avx512"] avx512×4, simd-overview avx512×4
缓存和分支预测分别在哪个环节起作用？ ["cache-basics","branch-prediction"] perf-methodology 混入 ×2 两篇正主 + branch
CPU 性能优化的主要手段？ []（空） 5 篇合理 等于没过滤（安全退化）

三个设计要点：

  1. 白名单校验：LLM 输出的 doc_id 必须存在于语料列表，否则丢弃—— 结构化输出的第一条军规：不信任，要校验；
  2. 空过滤器 = 安全退化：泛化问题构造不出过滤，就退回全局检索， 不为了"一定要滤一点"而硬造一个范围。:53-54 是 Python 的条件表达式 a if 条件 else b：有 doc_ids 就筛，名单为空就用原来的 plain；
  3. 过滤提升的是候选集纯度：第 3 行那种全局题，过滤没有额外信息。 所以要先路由（第 14 节 14.6），判断这题需要不需要过滤。

15.3 Text2SQL：同一个思想的重量级形态

Text2SQL 是让模型把问题翻译成 SQL。和过滤器生成是同一件事， 目标语言从 JSON 换成了 SQL（all-in-rag 第 4 章第 3 节的讲法）：

问题："上季度销售额最高的产品是什么？"
  ↓ LLM
SELECT product, SUM(amount) FROM orders WHERE quarter='Q3' GROUP BY product ORDER BY 1 LIMIT 1;

例子里的 SQL 词，和本课程检索用到的 WHERE / LIMIT 属于同一门语言： SUM 是求和，GROUP BY 是按某一列分组之后再聚合，ORDER BY 1 是按第 1 列排序。

生产上的三条铁律（本课程没有实现 Text2SQL，但这三个词会反复出现）：

  • 只读。生成的 SQL 先过一层检查，再交给一个只有读权限的数据库账号。 DML（Data Manipulation Language，数据操作语句）会改行：INSERT、UPDATE、DELETE。 DDL（Data Definition Language，数据定义语句）会改表：CREATE、DROP、ALTER。 模型若吐出 DROP TABLE，照单执行就能删表。检查层拒绝这些关键字； 只读角色是数据库账号的权限，这个账号只能 SELECT。检查层漏了，数据库自己仍会拒绝写入。
  • 白名单 schema。这里的 schema 指有哪些表、哪些列、列是什么类型。 Prompt 里只描述允许查询的那几张表和几行示例，不把全库的表名交给模型。 它和第 9 节 jsonb 那种"自由字段"不是一个词，也不是 15.6 的 JSON Schema （一份机器可读的说明书，规定 JSON 必须有哪些键、值是什么类型）。
  • 先 EXPLAIN 再执行。EXPLAIN 让数据库打印执行计划：会不会全表扫描、估出多少行， 并不真正跑这条查询（第 9 节 9.1.3 用它看 GIN 有没有被用上）。 计划看起来会扫全表，就不要执行。

对应本课程：meta_filter 的 JSON 是一份很小的查询。 construct_filter 的 :43 白名单，相当于 SQL 里只允许出现的表名和列名。 三条铁律里，"只读"对 JSON 过滤器天然成立，因为这份 JSON 表达不了 DELETE； "白名单"已经做了；"EXPLAIN"对应把构造出的过滤器先打印出来，人看过再检索。

15.4 结构化数据进知识库：表格 → 文本化

问题（笔记第 32 节）："把每一行当一个 chunk"是错误思路。可落地的三层方案：

① 行文本化：每行渲染成一句自然语言（"客户 A 于 2025 购买 P1，金额 100"）
   → 可被语义检索，但丢失聚合视角
② 段落/主题聚合：按某列分组渲染（"P1 在 2025 共售出 N 件…"）
   → 第 2 节"100 个案例→统计摘要"思想的最小实现
③ 摘要节点：整表/分组的统计结论单独成块（如"72% 工单发生在高并发"）
   → 检索"总体情况"类问题时命中

我们的架构已经支持：表格文本化后的块照常走 rg_chunks + strategy 版本化； 摘要节点给个独立 strategy（如 table_summary），用 meta_filter 控制走哪层—— 这就是 all-in-rag 3.5"结构化索引（多表格递归检索）"的手工版。

顺带一提：KB 系统（第 17 节）的 docx 解析（kb/parser.py 的 _parse_docx） 已经把表格按行拼成 a | b | c 文本抽出来了——那是行文本化的现成实现， 只是渲染成了 Markdown 表格语法而非自然语言句。

15.5 注意事项

  • 白名单 DOC_LIST（:20-23）是硬编码的语料清单：换语料必须同步改—— 生产上应该从 rg_documents 查出来再填进 Prompt；
  • 演示版是"检索后筛选"，生产版应该是"检索中过滤"（SQL WHERE / meta_filter）： 两者在 HNSW 下的行为不同（先过滤再近邻搜索可能候选不足，见第 9 节 9.1 的坑）；
  • LLM 偶尔会编造白名单外的 doc_id（即使 Prompt 说了只能从列表选）—— 这不是 Prompt 写得不好，是 LLM 的本性，所以 :43 的校验不能省；
  • Text2SQL 的"先 EXPLAIN"在过滤器场景的等价物：把构造出的过滤器打印给用户 确认，而不是默默生效——尤其是过滤结果为空时（空结果 ≠ 没有答案， 可能是过滤器太严）。

15.6 格式化生成的三个段位（本课程全部出现过）

① 输出严格 JSON     → 三元组抽取（第 14 节）、过滤器生成（本节）
② 输出带约束的自然语言 → 引用 [n] + 拒答规则（第 8 节系统 Prompt）
③ 输出可执行查询     → Text2SQL（本节，只读铁律）

共同点：模型的输出进入程序之前，要过一层校验。 JSON 用 json.loads 加上白名单；若要更严，可以用 JSON Schema 规定键和类型 （15.3 已和数据库 schema 区分开）。SQL 则做只读检查。 第 12 节说过评测框架不替你做评测接线；校验同样不在框架里，它是你自己的代码。

15.7 动手练习

  1. 跑 python -m scripts.demo_query_construction，自己出 3 道题看过滤器生成的 边界情况（故意写错文档名、混合两个主题、只用代词）；
  2. 把 FILTER_PROMPT 的白名单（:27）砍半，看 LLM 会不会"编造"列表外的 doc_id（会被 :43 校验拦下——这就是为什么校验不能省）；
  3. 把 run() 的过滤改成走 meta_filter={"corpus":"main", "doc_ids":[...]} 的 真检索中过滤——注意 doc_ids 不是 rg_chunks.meta 的字段，你要么把它 写进 meta（重建索引），要么在 SQL 外层包一层（想一想为什么 KB 的 dense_search 没有做 doc 级过滤，以及加一个有多难）；
  4. 思考：第 9 节的 meta_filter + 本节的过滤器生成 + 第 14 节的路由， 三者拼起来是什么？（答：一个"文本到过滤器"的完整查询理解层。）
