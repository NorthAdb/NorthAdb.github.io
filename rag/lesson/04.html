4.1 双编码器：为什么文档向量可以离线算

Query ──→ Encoder ──→ Query Vector ─┐
                                    ├─→ 余弦相似度 → 排序
Doc   ──→ Encoder ──→ Doc Vector ───┘

Query 和 Document 分别编码成同一个空间里的向量，因此：

  • 文档向量可以入库时算一次，查询时只编码 Query（本课程 620 块只算了 620 次）；
  • 这就是"双塔"架构，是它能撑住大规模召回的原因（对比第 7 节的 Cross-Encoder： 那里 Query-Doc 必须成对进模型，离线预计算不可能）。

4.2.2 降级版：HashingEmbedder（embedder.py:99-128）

词袋特征哈希投影——每个 token 哈希到 1024 维，带符号累加后归一化（:119-125）：

def embed_one(self, text):
    v = [0.0] * self.dim
    for tok in self._tokens(text):                 # jieba 中文分词（:110-117）：
                                                   # 把句子切成一个个词，下一节 BM25 的主角
        h = int(hashlib.md5(tok.encode()).hexdigest(), 16)
        v[h % self.dim] += 1.0 if (h >> 64) & 1 else -1.0   # 符号减少碰撞打架
    norm = math.sqrt(sum(x * x for x in v)) or 1.0
    return [x / norm for x in v]                   # 归一化 → 余弦有意义

它是真实的（弱）检索器：同词必同向量，所以词面匹配有效；但完全不懂语义， "向量搜索"匹配不上"语义搜索"这种改写。课程用它可以演示： 没有语义的 Dense 检索 = 只剩下词面功夫，基本退化成另一种 BM25。 探活与选择逻辑在 get_embedder()（:142-151）：ALLOW_FAKE_EMBEDDING=False 时 探活失败直接抛错（:145-147，不许降级的场合），否则打印降级警告继续跑。

4.2.3 检索侧：dense_search（playground/retrieve/vector_store.py:30-64）

一条 SQL 看懂全部：

SELECT doc_id, chunk_index, content, section_path, parent_id,
       1 - (embedding <=> %s::vector) AS sim        -- 余弦距离 → 相似度
FROM   rg_chunks
WHERE  strategy = %s AND embedding IS NOT NULL      -- 索引版本隔离
  AND  meta @> %s::jsonb                            -- 元数据过滤（第 9 节）
ORDER  BY embedding <=> %s::vector                  -- 走 HNSW 索引
LIMIT  %s
  • <=> 是 pgvector 的余弦距离算子，1 - 距离 = 相似度（:38）；
  • HNSW（分层可导航小世界图）：pgvector 的默认向量索引，查询 O(log N)。 建索引参数 m=16, ef_construction=200（scripts/init_db.py:53-55）， 查询参数 hnsw.ef_search（默认 40）——这三个参数到底是什么、查询是怎么 沿着图走的，4.2.5 逐层拆解；为什么根本需要它（ANN 问题）见 4.2.4；
  • 查询向量以 %s::vector 传字符串化的 Python list（vector_store.py:45 的 str(list(query_vec))）——pgvector 的 psycopg 适配器也接受向量对象，两种写法都行；
  • 小语料其实顺序扫描也够快，但生产数据量起步百万块，HNSW 是标配认知 ——为什么"够快"和"必须快"的分界在哪，往下看。

4.2.4 先补一个词：ANN——为什么要"近似"

上面 SQL 的 ORDER BY embedding <=> ... LIMIT k，理想实现叫 KNN（K 近邻）： 拿查询向量与库里每一个向量都算一遍余弦，排序取前 K。625 块 × 1024 维是毫秒级 的小算术；但换成一百万块，就是每次查询 10 亿次乘加——延迟和 CPU 都不可接受。

**ANN（Approximate Nearest Neighbor，近似最近邻）**是这个难题的工程答案： 放弃"保证找出的 K 个恰好是全库最相似的 K 个"，接受极小的漏找概率， 换几个数量级的加速。衡量任何 ANN 方案都用三把尺子：

尺子 含义 4.5 实验怎么量
召回率 ANN 的 Top-K 与精确解的重合度 recall@10（对照顺序扫描）
延迟 单次查询耗时 平均延迟（ms）
内存 / 构建成本 索引多大、建多久 ——（本实验语料太小，不显著）

三把尺子互相牵制：把召回调满，延迟或内存通常就要付账。注意"近似"不是将就—— 在召回 0.99+ 的前提下快百倍，是生产的标准选择；反过来，几千块以内顺序扫描 精确、零调参、零内存，根本不需要 ANN。这条分界线就是 4.5 实验要亲手验证的。

4.2.5 HNSW 逐层拆解（m / ef_construction / ef_search 到底是什么）

HNSW（Hierarchical Navigable Small World，分层可导航小世界图）名字唬人， 直觉版一句话：给向量建一张多层地图——上层公路稀疏、跨度大；底层街道稠密、 跨度小。查询从顶层先大幅接近目标，再逐层下降精细搜索。

两个直觉来源：

  • 跳表（skip list）：查字典不从头翻，先看目录锁定章节，再翻章节内细目—— HNSW 就是它的图版本，越往上节点越少（随机抽样决定谁"升层"）、边越长；
  • 小世界网络：社交网络里任何两个人只隔少量中间人。图检索吃的就是这个性质： 沿边跳几下就能到目标附近。
第 2 层（极稀疏，长边）：    A ─────────────── E        ← 粗定位，几步跨全库
                          /
第 1 层（中等）：      A ── B ──── E ── G
                        /
第 0 层（全部向量，短边）：A - B - C - D - E - F - G   ← 最终的精细搜索层

一次查询的走法（ef_search 就在这一步登场）：

  1. 从顶层入口出发，贪心走向"离查询更近的邻居"，本层只做粗定位；
  2. 降到下一层，以上一层的落点为起点继续贪心；
  3. 到达第 0 层后，维护一个长度为 ef_search 的候选队列：反复考察队里最近 的点的邻居，更近就入队、装不下就淘汰最远的—— ef_search 就是"搜索时手里握着多少个候选"。太小：正确邻居没机会被 扩展到，漏找；太大：考察的人多，更准但更慢。这就是 4.5 实验里那个旋钮， pgvector 默认 40（且必须 ≥ top_k，否则候选不够数）。

三个参数各管一段（前两个写死在建索引语句里，改了要重建；第三个随时可调）：

参数 用在何时 含义 本课程的值
m 建索引 每个节点最多连几条边（"人脉上限"）：越大图越密越准，内存与构建时间越高 m=16（init_db.py:54）
ef_construction 建索引 建图时每个节点的候选队列宽度：越大建得越慢、图质量越好 ef_construction=200（init_db.py:55）
hnsw.ef_search 查询 查询时的候选队列宽度：越大越准越慢 默认 40，会话级 SET 可调

记忆口诀：m 管"路修多密"，ef_construction 管"修路时多仔细"，ef_search 管 "赶路时多仔细"。4.5 的实验把第三个从 10 拧到 400，亲手量"更准了多少、慢了多少"。

4.2.6 ANN 算法谱系：HNSW 的亲戚们

HNSW 不是唯一选项。按"用什么结构组织向量"分四大家族，各认识一位代表：

算法 一句话原理 强项 弱项 谁在用
IVFFlat（pgvector 自带） 先把全库聚成 nlist 个桶，查询只扫最近的 nprobe 个桶 建得快、内存省、零图维护 桶边界向量易漏（要调 nprobe），数据倾斜召回不稳 pgvector / Faiss，中小库
IVF-PQ（乘积量化） IVF 之上再把向量压成"子段量化码" 内存降到几十分之一，亿级可放内存 有损压缩伤召回，要配 Rerank 救 Faiss，超大规模
LSH（局部敏感哈希） 特殊哈希让相似向量大概率撞同桶 理论简洁、支持流式插入 召回/延迟均衡差，实践中少见 教学与老系统
Annoy 多棵随机投影树并行投票 静态数据简单可靠 只读（增删要重建）、内存偏高 Spotify
ScaNN 各向异性量化 + 高度优化的扫描 速度/召回的 Pareto 前沿 工程复杂 Google
DiskANN / Vamana 图方法的单层亲戚，索引可放 SSD 十亿级单机、内存占用小 查询走 IO，延迟受磁盘限制 微软，云厂商超大库

HNSW 在谱系里的位置：图方法这一支（NSW → HNSW → DiskANN）的中坚—— "分层"解决了早期 NSW 在高维下绕远路的问题，是当前向量数据库（pgvector、 Qdrant、Milvus、Elasticsearch）的默认主角。

两个工程常识收尾：① Faiss 不是又一个算法，而是 Meta 出品的 ANN 工具箱 （上面大半算法的实现都在里面），学完本节再看它的文档，目录就是一张 ANN 谱系表； ② 最后一页永远是顺序扫描——精确、零调参、零内存，几千块以下的最优解 （4.5 的对照组就是它）。"规模决定方案"，别为了听起来高级而上索引。

4.3 余弦相似度直觉

两个向量的夹角越小，余弦越大。Embedding 模型把"语义相近"训练成"方向相近"：

"CPU 的缓存为什么分多级"  → [0.021, -0.037, ...]  ┐
                                                ├ 夹角小 ≈ 相似
"为什么要设计多级缓存"    → [0.019, -0.035, ...]  ┘
"AVX-512 寄存器宽度"     → [-0.044, 0.012, ...]   ← 方向完全不同

注意相似度的相对性：Top-K 是"最相似的 K 个"，不代表"绝对相关"—— 语料里没有答案时，它会照样把"最不坏"的 K 个递给你（第 8 节的拒答为什么要 放在生成层、第 16 节 CRAG 为什么用 rerank 分数而不是 cosine 做评估器，根源都在这）。

4.5 实验：ef_search 基准（exp8，v2 加厚）

4.2.5 讲过：ef_search 是查询时的候选队列宽度，"更准 vs 更慢"的旋钮。这个实验 把旋钮从 10 拧到 400，用数据回答"值不值"。scripts/bench_hnsw.py:21 的 brute_top10() 先算顺序扫描的精确 Top-10当对照组，再让 hnsw_top10() （:33）在不同 SET hnsw.ef_search 下对比 ANN 近似误差：

ef_search recall@10（vs 顺序扫描） 平均延迟
10 / 20 / 40 / 80 / 200 / 400 全部 1.000 1.65 ~ 1.91 ms

诚实结论：625 块的小语料上，HNSW 各档都拿到了 100% 召回、延迟也没差别—— ANN 的取舍在这个规模根本观察不到。这本身就是重要认知：

几千块以下：顺序扫描（精确、零调参）完全够用，别急着上 HNSW
十万块以上：HNSW 开始显著省 IO；ef_search 才成为真正的旋钮
生产建议：  按 p95 延迟预算选 ef，用 exp8 的脚本在自己的数据量上重测——
            别人的基准数字不能移植
            （p95：把所有请求的延迟排序，取第 95 百分位的那个值——
              排除最慢 5% 的离群后，"绝大多数用户真实感受到的延迟"）

4.6 注意事项

  • hnsw.ef_search 是会话级参数：连接池里每次取连接要重新 SET （本课程单连接长连接所以没踩，生产必知）；
  • 过滤 + HNSW 的次序坑：HNSW 先取 ef_search 个候选再过滤，条件严时 结果会缺——pgvector 0.8 的 hnsw.iterative_scan = relaxed_order 为此而生 （第 9 节还会再提）；IVFFlat（另一种向量索引：先把向量聚类分桶、查询只搜 最近的几个桶）是替代方案：建得快、内存省，但要 ANALYZE（刷新统计信息）+ 调 probes（每次查询探几个桶，通常 10+），数据倾斜时召回不稳。 小库用扫描，中库用 HNSW，超大规模再评估 IVFFlat；
  • 库的 LC_CTYPE 必须是 UTF-8 locale，否则 pg_trgm 对中文完全失效——不报错， 只是默默返回垃圾（D:\PostgreSQL\README.md 第 7 节记录的真实大坑； 本课程不依赖 trgm，但"环境参数要留档"的习惯从这里来）；
  • 换 Embedding 模型 = 全部向量作废（维度和语义空间都变了）：必须新 strategy 重建，且不能与旧向量混排比较。

4.7 多模态嵌入：一句话框架（v2 加厚）

文本嵌入把句子变成向量，多模态嵌入把图片/音频也映射进（近似的）同一语义空间： CLIP 类模型让"落日照片"与"傍晚的海边"向量相近。RAG 里的三个用法：

  1. 图文互检：以文搜图、以图搜文（向量库照旧，只是向量来源多了一个编码器）；
  2. PDF 里的图表：整页截图 → 多模态嵌入 → 命中后用多模态 LLM 读图作答 （RAG-Anything/M3RAG 的路线；MinerU 解析出的 image_tags 是它的素材）；
  3. 表格：优先"表格文本化"（第 15 节），嵌入只是兜底。

本课程不实现（语料是纯文本），但硅基流动的模型生态里有多模态嵌入与视觉模型—— 升级路径是现成的。

4.8 动手练习
