查询改写与 Context 装填

第 08 节约 35 分钟本节自测

Rewrite / Multi-Query / HyDE；token 预算、Lost in the Middle、引用与拒答；v3：改写家族全景与装填预算算账。

本节任务：掌握检索前（改写）与检索后（装填）两个"分数之外的杠杆"， 理解 build_context 的预算/去重/排序/引用四件事，以及拒答为什么必须放在 生成层用 Prompt 约束。

课程地图上的位置：Layer 3 的主体。上一节 07 Rerank；下一节 09 知识库工程。本节横跨流水线的两头：改写在检索之前， 装填与生成在检索之后。

8.1 查询侧：改的是查询，不是结果

三个工具，风险各不相同（playground/retrieve/query_rewrite.py，全文 51 行）：

方法 做什么 救什么题 风险
Rewrite（:15） LLM 把口语改写成文档术语 表述与文档差得远 改写引入错误术语
Multi-Query（:26） 拆成 3 个角度分别检索，结果 RRF 合并 一题多问、覆盖面窄 候选膨胀、慢 3 倍
HyDE（:38） 先让 LLM 写"假设答案"，拿假设答案做向量检索 语义鸿沟大 幻觉答案带偏检索

（幻觉：模型一本正经地编造不存在的内容——LLM 时代最著名的副作用。 本课程的拒答约束（8.4）与第 13 节的 Faithfulness 评审，防的都是它。）

8.1.1 代码走读：三个函数

rewrite_query（query_rewrite.py:15-23）——一句澄清式改写：

def rewrite_query(query: str) -> str:
    llm = get_llm()
    prompt = ("把用户问题改写成适合知识库检索的查询：补全省略的主语，"
              "把口语换成文档常用术语，保留原意，不要回答问题，只输出改写后的查询本身。\n"
              f"用户问题：{query}\n改写后的查询：")
    out = llm.chat(prompt, max_tokens=120).strip()
    return out or query                     # :23 LLM 返回空串 → 退回原查询

multi_query（:26-35）——多角度拆解，注意保底设计：

def multi_query(query: str, n: int = 3):
    ...
    lines = [ln.strip(" -0123456789.\t") for ln in llm.chat(prompt).splitlines()]
    out = [ln for ln in lines if ln]
    return ([query] + out)[: n + 1]     # :35 原始 query 永远排第一参与检索！

:35 是全文件的点睛之笔：改写是增益，不是替代——LLM 返回的每一行都 strip 掉列表编号（" -0123456789.\t"），但无论如何，原始查询都在列表头部。 改写失败时至少退回原路，这正是它比 Rewrite 稳的原因。

hyde_query（:38-50）的 Prompt 值得读一遍："写一段技术性回答，不需要准确， 只需要像文档里的答案"——HyDE 要的就是文档的词汇分布，不是事实。 代价与收益都源于此：词汇对了召回大涨，事实错了也会把检索带偏。

8.1.2 编排层如何用它们（rag.py:119-129）

queries = [question]
if o.rewrite == "rewrite":
    t.rewritten = query_rewrite.rewrite_query(question); queries = [t.rewritten]
elif o.rewrite == "multi_query":
    queries = query_rewrite.multi_query(question, 3)
    t.multi_queries = queries[1:]              # Trace 里只记"改写出的"，原始的不重复记
elif o.rewrite == "hyde":
    t.rewritten = query_rewrite.hyde_query(question); queries = [t.rewritten]
# 之后 :133-144 对每个 query 各跑一遍多路召回，:165-167 用 rrf_fuse 把多组结果再合并

8.2 实验 4 结果

来自 python -m scripts.run_eval 第 4 组（exp4_rewrite）：

方案 Recall@5 MRR@5 评测总耗时（23 题）
不改写 1.00 0.928 ~0.1s
Rewrite 单查询 1.00 0.935 ~24.6s
Multi-Query 多路 1.00 0.884 ~32.8s

读表：

  • Recall 已经饱和：三种设置都是 1.00——这套金标在 16 篇语料上"捞没捞到" 不是瓶颈，改写的作用只能体现在名次（MRR）上；
  • Rewrite 略升（+0.007）：口语被改写成文档术语后部分题的名次提前了， 但幅度不到一道题的分量；
  • Multi-Query 略降（-0.044）且最慢：多角度查询扩大了候选覆盖面，但也引入 偏离原始意图的检索词，部分正确块被挤出 Top-1——RRF 融合（第 6 节）能缓解 稀释，消不掉。代价之外还有 3 次 embedding + 1 次 LLM 调用；
  • 三个读数合起来才是本节的真正结论：改写是双刃剑，收益与损失都必须实测。 在这套小语料上该不该开改写？判断标准不是"有没有用"，而是"这点提升值不值 250 倍的耗时"。召回不满（Recall < 1）时 Multi-Query 才有翻身机会—— v1 口径（20 题时代）它就曾把 Recall 从 0.95 补满到 1.00；换口径结论就变， 这正是第 1 节 1.7 强调"注明口径"的原因；
  • HyDE 本课程只作对照（Playground 可选），不作默认——幻觉答案带偏检索的 案例在长尾语料上很常见。

8.3 生成侧：Context 装填的四件事（context_builder.py:27-70）

检索到的块不能 "".join 了事。build_context 显式做四件事，与代码段一一对应：

def build_context(hits, budget_chars=config.CONTEXT_CHAR_BUDGET,   # :26 3200 字符
                  order="score", max_blocks=config.CONTEXT_MAX_BLOCKS):   # 默认 6 块
    # 1) 去重（:29-35）：多路召回天然重复，同 chunk_id 只留一次
    # 2) 预算（:37-43）：按分数从高到低收，len(kept) >= max_blocks 或
    #    used + len(h.content) > budget_chars 即停；没进来的进 dropped（可观测！）
    # 3) 排序（:45-54）：score | ends | doc 三种策略
    # 4) 引用（:57-69）：[i] 编号进正文 + citations 列表（doc_id/section/chunk_id/score）

三个装填策略的差别（:46-54）：

order 行为 治什么
score 分高在前 默认；最朴素
ends 最强的两块放头尾，其余居中 Lost in the Middle：LLM 对长 Context 中间注意力弱
doc 同文档证据相邻 阅读连贯；适合多文档对照题

截断策略：超预算丢谁？本实现"分数低的先丢"（:37-43 按分数排序后收满即停）， 而不是截断中间——因为低分块更可能是噪声。代价是"低分但必要"的块会被丢 （全局总结题的关键块可能分数不高），dropped 列表就是为了让你能发现这种情况。

8.4 引用与拒答（prompt.py + llm.py）

系统提示只有三条硬约束（playground/generate/prompt.py:4-8）：

1. 只根据提供的资料回答；资料里没有的，直接说"资料中没有相关信息"，不要编造。
2. 引用证据时在句末标注编号，如 [1][2]。
3. 资料互相矛盾时指出来并说明各自出处。

用户侧 Prompt 的拼装在 prompt.py:11-20 的 build_user_prompt：资料块 （带 [i] 编号与出处头）+ 引用规则 + 问题。LLM 客户端在 llm.py:32-53 （chat：3 次重试 + 递增退避）与 llm.py:56-88（chat_stream：SSE 流式—— SSE（Server-Sent Events）是服务器向浏览器单向持续推送文本的轻量协议， 浏览器里表现为"逐字上屏"，/kb 的打字机效果就是它）。答案落地后，rag.py:207 用特征词（"资料中没有"等）判定 trace.refusal——这也是一个"启发式 + 可观测"的例子。

实验 6（真实 LLM 生成）的结果：

方案 拒答正确 拒答率
Dense 基线 5/5 1.00
Hybrid+Rerank 完整版 5/5 1.00

五道不可回答题（v1 口径；v2 扩到 7 道）全部正确拒答，回答形如： "资料中没有相关信息……[1][2] 仅涉及 SSE~AVX-512"。看完整回答见 exp6 报告。

[!IMPORTANT] 拒答是 RAG 能力的一部分，不是模型胆小。 检索层的 Top-K 永远会返回 "最不坏"的 K 个（相似度是相对的，第 4 节 4.3），能不能承认"这些证据不够"， 必须在生成层用 Prompt 约束 + 评测集里放不可回答题来保证。KB 系统还叠加了 第二道闸门：rerank 分数过低时不调用 LLM 直接拒答（kb/chat.py 的 stream_answer），省掉一次注定失败的开发。

8.5 如何运行

# 改写三件套的终端实测（会调 LLM，注意耗时）
python -c "
from playground.retrieve.query_rewrite import rewrite_query, multi_query, hyde_query
q = '公司服务器为啥要搞多级缓存？'
print('rewrite:', rewrite_query(q))
print('multi:', multi_query(q))
print('hyde:', hyde_query(q)[:100])
"

# 装填四件事的终端实测（不调 LLM）
python -c "
from playground.rag import RAGPipeline, PipelineOptions
t = RAGPipeline(PipelineOptions(retriever='hybrid', generate=False)).retrieve('AVX-512 的掩码寄存器')
from playground.generate.context_builder import build_context
ctx = build_context(t.fused, order='ends')
print('used:', len(ctx.used), 'dropped:', len(ctx.dropped))
print(ctx.text[:200])
"

# 完整问答（含引用与拒答）
python -c "
from playground.rag import RAGPipeline, PipelineOptions
print(RAGPipeline(PipelineOptions()).answer('AVX-512 的掩码寄存器有几个？').answer)
"

8.6 注意事项

  • 改写三件套都依赖 LLM：LLM 降级时 get_llm() 返回 EchoLLM， 改写质量不可信——生产上应在降级时自动关闭改写（condense：KB 系统里 "把'它和 BM25 有什么区别'这类依赖上下文的追问，改写成不依赖历史的独立 检索词"的机制，和本节改写同思想、第 17 节正式讲；kb/chat.py:160 的 condense_question 先查 llm.is_real 就是它的降级保护）；
  • 预算单位是字符不是 token（context_builder.py:26）。token 是 LLM 计长/计费的最小文字单位，约等于一个词或半个词：中文约 1 字 ≈ 1 token， 英文约 4 字符 ≈ 1 token——换英文语料要重新标定 CONTEXT_CHAR_BUDGET；
  • dropped 不是垃圾，是诊断信号：某题答案引用了编号 [3]，但 [3] 的块在 dropped 里出现过，说明预算太紧或块太长；
  • 拒答特征词表（rag.py:23-26）是启发式的：换 Prompt 措辞要同步维护它， 否则 trace.refusal 失真。

8.7 动手练习

  1. Playground 问"公司里多少人会用 AVX-512？"（知识库没有此信息，但词面相关）， 开/关"强制引用标注"对比回答——无引用约束时编造倾向是否变大？
  2. 找一道多块证据的题（如 q19 全局题），切换 score vs ends 装填， 对比答案里引用编号的分布；
  3. 用 8.5 的第二个命令把 order 依次换成 score/ends/doc，对着 ctx.text 说出三种顺序各自适合什么题；
  4. 思考：为什么"分数低的先丢"比"截断中间"更安全？什么情况下后者反而对？ （提示：当"必要信息恰好都在分数中部"时，ends 与截中间是同一件事的两面。）

8.8 加厚（v3）：改写家族全景与装填预算的算账方法

改写家族全景（讲过的 + 两个邻居）

方法 改什么 救什么题 成本 本课程位置
Rewrite 一句话改写成文档术语 口语 vs 术语的鸿沟 1 次 LLM 8.1
Multi-Query 拆 3 个角度并行检索 一题多问、覆盖面窄 1 次 LLM + 3 路检索 8.1
HyDE 先写假设答案再拿它检索 语义鸿沟极大 1 次 LLM 8.1
Step-Back 先抽象一层问原理，再问细节 细节题缺背景 1 次 LLM 未实现，思路同族
子问题分解 多跳问题拆成 2-3 个独立子问题 要拼接 A→B→C 的题 N 次 LLM+检索 第 14 节图召回是它的"结构化亲戚"
查询路由 不改写，只判断该走哪条路 检索器/路径选型 1 次轻量判断 14.6

共同纪律：改写都在"增益 vs 失真"之间赌，必须过金标（8.2 是示范）；且都要 有保底——原始查询永远参与检索（multi_query 的 :35）。

装填预算怎么算账

CONTEXT_CHAR_BUDGET=3200 不是拍脑袋，是一笔账：默认 top_k=5 × 平均块 500 字 ≈ 2500 字符正文 + 引用编号与出处头的开销 ≈ 3200。改任何一项都按这个式子重算：

预算 ≈ top_k × 平均块长 + 头尾开销（编号/出处/指令）

两个推论：① 换了切分尺寸（第 3 节），预算要跟着动——900 字大块配 3200 预算 只装得下 3 块；② 换英文语料按 4 字符/token 换算（8.6），同样 3200 字符的英文 信息量大约只有中文的 1/4，预算要放大或块数要下调。
