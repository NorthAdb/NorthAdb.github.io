切分 Chunking：检索单元的设计

第 03 节约 30 分钟本节自测

固定长度/段落/标题三种切法；200/500/900 消融；标题前缀的 context-aware 思想；v3：切分策略谱系（fixed→结构→语义→agentic）。

本节任务：理解"检索单元"是 RAG 里你自己设计的第一个数据结构，掌握 段落优先滑窗（滑窗：固定大小、一路切下去的切法；"段落优先"指尽量在 段落边界落刀，3.2.2 展开）+ 标题前缀这对最小组合——后者是"一行代码换回 语义（文字背后的意思）完整性"的全课性价比之王。

课程地图上的位置：Layer 1 第二课。上一节 02 清洗；下一节 04 Embedding。切分的输入是第 2 节清洗后的 RawDoc.text， 输出是 Chunk 对象列表——"块"从此成为全课程的通用货币（第 1 节 1.3 的 Hit 就是它的检索期形态）。

3.1 为什么切分是个真问题

最朴素的切法是"每 500 字切一次"，但它会切出：

"它在这种情况下性能更好。"      ← 单独看毫无意义的块

这句话的主语（PostgreSQL 的 MVCC / AVX 的降频）在被切掉的上文里。 Embedding 模型对一个无主语的句子算出的向量，自然匹配不上任何正经问题。

更好的做法是让块自带上下文：标题、章节、父级主题。这就是 Context-aware Retrieval 的核心——回到最底层，修补块本身的可检索性，而不是往上游堆更炫的 检索算法。

3.2 代码走读（playground/ingest/chunker.py，全文 144 行）

三个公开函数，对应三种切法（chunker.py:38,96,120）：

heading_sections(text)    # :38  先按 Markdown 标题层级切成小节（= 父块候选）
fixed_chunks(...)         # :96  固定长度滑窗：段落优先 → 句子 → 硬切，带 overlap
parent_child_chunks(...)  # :120 小节内再切 200 字子块（第 10 节的主角）

3.2.1 标题树：heading_sections（chunker.py:38-66）

_H_RE = re.compile(r"^(#{1,4})\s+(.*)$")            # :35 只认 1-4 级标题

def heading_sections(text):
    stack: list[tuple[int, str]] = []   # [(级别, 标题)]，:41
    buf: list[str] = []
    for line in text.splitlines():
        m = _H_RE.match(line)
        if m:
            flush()                     # 遇到新标题：上一小节收工
            level = len(m.group(1))
            while stack and stack[-1][0] >= level:
                stack.pop()             # :59 弹出所有 ≥ 当前级别的祖先
            stack.append((level, title))
            buf.append(line)            # 标题行本身归入小节正文（:62）
        else:
            buf.append(line)
    flush()

维护一个标题栈，section_path 就是栈里从底到顶的拼接（chunker.py:49 的 " > ".join）——所以一块的 section_path 长这样：H1标题 > 二级标题 > 三级标题。 这个字段后面三处要用：第 3.2.3 的标题前缀、Playground 的命中展示、 rg_parents 的父块定位。

3.2.2 滑窗：_split_by_paragraph（chunker.py:69-93）

def _split_by_paragraph(body, size, overlap):
    paras = [p.strip() for p in re.split(r"\n\s*\n", body) if p.strip()]   # :71 段落边界
    ...
    while len(p) > size:                     # :77 单段超长 → 按句子切
        cut = p.rfind("。", 0, size)         # :78 在 size 内找最后一个句号
        cut = cut if cut > size // 2 else size   # 句号太靠前就硬切（避免碎片）
    ...
    if cur and len(cur) + len(p) + 1 > size:     # :87 装不下 → 收工当前块
        pieces.append(cur)
        cur = cur[-overlap:] if overlap > 0 else ""   # :89 overlap 的实现：
        #                                            带着上一块尾巴开新块

三个细节值得注意：

  1. 段落优先：永远先试段落边界（空行分割），只有单段超长才按句子切， 最后才硬切。语义边界 > 字符边界；
  2. 句号回退有下限（:79）：cut > size // 2 保证句子切不会切出超短碎片；
  3. overlap 的实现（:89）：新块以上一块的末尾 overlap 个字符开头—— 缓解"关键句正好跨边界被劈开"。代价是内容重复（Top-K 里两块都有这句话）， 所以 overlap 不是越大越好（第 8 节装填层的去重会再见到它）。

3.2.3 标题前缀：embed_text ≠ content（chunker.py:100-114）

这是本节最重要的 10 行：

for sec in heading_sections(text):
    pieces = _split_by_paragraph(sec.content, size, overlap)
    for piece in pieces:
        title = sec.section_path.split(" > ")[-1]        # :105 最后一级标题
        embed_text = f"{title}：{piece}" if title != "（无标题）" else piece
        chunks.append(Chunk(doc_id=doc_id, chunk_index=idx,
                            content=piece,        # 交给 LLM 的正文：原文
                            embed_text=embed_text,     # 被向量化的：带标题
                            section_path=sec.section_path))

同一个块存两份文本：embed_text（向量化用）带标题前缀，content（装进 Context 用）保持原文。效果："它在这种情况下性能更好"变成 "降频争议：它在这种情况下性能更好"——Embedding 的语义表示立刻完整。 这就是 Context-aware Chunk 的最小实现：一行代码，零成本。 入库时两列分别写到 rg_chunks.embed_text / rg_chunks.content （playground/ingest/ingest.py:113-120），检索 SQL 取的是 content，向量比的是 embed_text。

3.2.4 数据类：Section 与 Chunk（chunker.py:19-33）

Section（小节 = 父块候选）只有 section_path + content 两个字段； Chunk 多了 doc_id、chunk_index、embed_text、parent_id。 chunk_index 是"块在文档内的序号"，与 doc_id、strategy 一起构成 chunk_id（第 1 节见过的三段式）——这意味着同一文档的不同索引版本天然可区分。

3.4 实验 3：切分大小消融

完整报告见 exp3_chunking。这个实验同样来自 第 1 节的 python -m scripts.run_eval（第 3 组）：四种切分参数各自建一套索引 （flat200x0 / flat350x60 / flat500x80 / flat900x120），在同一批金标题上 对比。表格里的"块数"是每套索引切出来的块总量（可用 Playground 首页的索引表核对）：

方案 块数 Recall@5 MRR@5 noise@5
小块 200 135 1.00 0.884 0.571
中块 350 101 1.00 0.899 0.600
中块 500（默认） 98 1.00 0.928 0.557
大块 900 97 1.00 0.928 0.543

（口径：30 题金标中的 23 道可回答题；Hybrid(RRF) 检索；指标含义见第 1 节 1.5 指标速查。）

怎么读这张表：

  • 文档级 Recall@5 三个尺寸全部饱和（1.00）——16 篇文档的小语料上，正确答案 所在的文档几乎总能挤进前 5。这不是"切分不重要"，而是文档级指标在这个数据 规模上已经失去区分度（第 10 节会正式讨论"指标要配数据规模"）；
  • 区分度落在 MRR 上：小块 200 最低（0.884）——块数多，同一文档被切成很多 主题单一的小块，"把正确文档顶到第一名"的力量被分散；500 与 900 并列最高 （0.928）；
  • noise@5 随块变大而下降（0.571 → 0.543）：大块信息全，就算一块"不直答"， 也更容易捎带相关内容，凑数比例自然低——但大块也有代价：单块塞多个主题， Embedding（把块文字变成向量去匹配，第 4 节）被稀释（v1 口径 20 题时代的同款 实验曾出现"小块 Recall 最高"的形态，换到 30 题口径后 Recall 全部饱和—— 结论要跟着口径走，见第 1 节 1.7）；
  • 中块 500 在 MRR 与 noise 上都是第一梯队，块数还少——这就是它当默认值的理由。 但别过度解读：0.928 vs 0.884 的差距在 23 道题上只有一两道题的差别， 没有万能尺寸，只有"对这批数据 + 这批问题"的实测最优。

另一个重要观察：同一篇文档的多个块会一起霸占 Top-K（本语料只有 16 篇， 一篇 5 个块命中就占满 5 个名额，挤掉其他文档的视角）。解法有两个： 装填时按文档去重/聚合（第 8 节），或者直接上 Parent-Child + auto-merging（第 10 节）。

3.5 注意事项

  • 改 config.CHUNK_SIZE 默认值 = 破坏实验可比性。想试别的尺寸，加新 strategy（scripts/build_index.py:18 的 main 里加一行 build_index(..., chunk_size=..., overlap=...)）， 旧索引原封不动；
  • chunker._H_RE 只认 1-4 级标题（:35）——五级以下的深度标题会被当正文； heading_sections 也只认 Markdown 的 # 语法，纯文本（如 MinerU 的 txt 产物） 没有标题层级，整篇就是一个"（无标题）"小节——这就是为什么 PDF 要先过 MinerU 拿到带层级的 full.md（第 2 节 2.8）；
  • 标题前缀会略微改变向量语义——它让块更"像标题描述的那个话题"。 如果你的查询习惯是引用原文句式（抄一段原文来搜），前缀反而引入噪声， 消融方法同第 2 节。

3.6 动手练习

  1. Playground 问"AVX2 与 AVX-512 在整数运算上的差别"，分别用 flat200x0 和 flat900x120，看 Dense 命中的块内容有什么不同；
  2. 用 3.3 的命令把一篇文档的块全部打出来，找出一个"如果没有标题前缀就无法 检索"的块——对照 embed_text 和 content 的差异；
  3. 思考题：为什么 embed_text 与 content 要分开存？如果 Prompt（发给大模型的 指令文本，第 8 节正式讲）里也想带标题，应该怎么改？（提示：改 context_builder.build_context 的装填格式，但要重算 token 预算——预算按字符算的，context_builder.py:26。）

3.7 加厚（v3）：切分策略谱系——从免费到昂贵

本节实现了两种切法（固定滑窗、标题小节 + 滑窗）。完整的方法谱系按成本排一条线， 越往下越"聪明"、也越贵：

策略 做法 成本 适用
固定长度滑窗（本课程 flat） 每 N 字符一落刀，段落/句子优先 几乎为零 通用基线，永远先跑它
递归分隔（LangChain 默认） 按"段落→句子→词"逐级找可用的分隔符 低 通用；思想与 3.2.2 相同，回退链更全
结构感知 按 Markdown 标题 / HTML 标签 / 代码 AST 切 低 有清晰结构的文档（3.2.1 的 heading_sections 就是它）
语义切分 相邻句各算 embedding，在相似度突变处落刀 中（每句一次嵌入） 主题跳跃多的长文（新闻合集、会议纪要）
LLM 切分（agentic） 让 LLM 判断"这几段是不是同一件事"并划界 高（每段一次调用） 极珍贵的语料；通常不值得
Late Chunking 先整篇过嵌入、再按 token 池化切块 低 需要块间上下文的场景（长上下文嵌入模型）

三条选型纪律（与第 1 节 1.5 的"先金标后改进"同源）：

  1. 从最便宜的开始：固定滑窗 + 标题前缀（3.2.3）解决大多数问题；
  2. 升级要有证据：语义切分贵 N 倍嵌入成本，只有在金标上量出提升才值得—— 方法就是本节 3.4 的消融，把"滑窗"换成"语义切分"再建一个 strategy 对比；
  3. 单位要统一：本课程按字符切，多数框架按 token 切——英文语料上 500 字符 ≈ 125 token，直接移植参数会切出完全不同大小的块（换算表见 8.6）。
