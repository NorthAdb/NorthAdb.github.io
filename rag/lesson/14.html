极简 GraphRAG：三元组抽取与多跳检索

第 14 节约 45 分钟本节自测

152 条三元组的抽取→邻接表→一跳扩展→图引导检索；“谁主导 Zen”决定性对比；查询路由；v4：三元组、邻接表、一跳在首次出现处展开。

本节任务：亲手跑通"三元组抽取 → 邻接表 → 实体一跳 → 图引导检索"全链路 （scripts/toy_graph.py，140 行），并用"谁主导 Zen"一题亲眼看到图检索 赢过纯向量的现场。上一节 13 评测进阶；下一节 15 查询构造。

课程地图上的位置：v2 加厚篇第二站，把第 11 节的扫盲落到 140 行可运行代码。 计划书授权的上限："用 LLM 抽少量三元组，存邻接表，手写实体→一跳邻居→检索"—— 目的：理解图检索的查询形态，不是复现社区检测。

14.1 四步流水线

先把这条流水线里的四个词定下来。后面的代码只是它们的一种写法。

三元组是一条原子事实，拆成三格：主体（subject，键 s）、关系（relation，键 r）、 客体（object，键 o）。"吉姆·凯勒是 A4 的主架构师"收成 {"s": "吉姆·凯勒", "r": "主架构师", "o": "A4"}。 它是图上的一条边。和第 13 节那三个评测分数同名不同物。

邻接表是一个字典：键是实体，值是"从这里出发能走到的边"的列表。 问"和 AMD 直接相连的有谁"就是查 adj["AMD"]，不用把 152 条三元组扫一遍。

无向：同一条边从两端都能查到。代码把一条三元组同时挂进 adj[s] 和 adj[o] （:66-67）。有向图只挂一端。"A 创立 B"若无向，从 B 也能走回 A； 有些关系（"A 继承 B"）倒着走是错的，14.7 会再提。

一跳：从问题里认出的实体出发，只沿边走一步，收集邻居和这条边所在的文档。 多跳是到了邻居再继续走。本玩具只做一跳。问题里已经写着中间那个实体时， 一跳就够到达答案；中间实体没出现在问题里，一跳到不了。

① 抽取：LLM 从每篇短文抽三元组（结构化输出）
      {"s": "吉姆·凯勒", "r": "主架构师", "o": "A4", "doc": "apple-silicon"}
② 存储：实体 → [边] 的邻接表（triples.json，无向：s/o 两端都可走）
③ 图召回：问题里识别实体 → 取一跳邻居 → 邻居的来源文档
④ 生成：只在"实体来源文档"里检索 + 带引用回答

①就是格式化生成（第 15 节会分成三个段位）：模型不回答问题， 只产出程序下一步能执行的 JSON。doc 记下这条边是从哪篇短文抽出来的，后面才能回到原文。

14.2 代码走读（scripts/toy_graph.py）

14.2.1 抽取 Prompt 与容错（toy_graph.py:27-59）

EXTRACT_PROMPT = """从下面的短文中抽取实体关系三元组。要求：
- 只抽文中明确陈述的关系；每条格式 {{"s": 主体, "r": 关系(2-6字), "o": 客体}}
- 实体用文中原名（公司/人名/架构/指令集）
- 输出 JSON 数组，不要解释：

短文（doc_id={doc_id}）：
{text}

三元组："""                                   # :27-35

def extract_triples(force=False):             # :39
    if TRIPLES_PATH.exists() and not force:   # :40 抽取结果落盘，重跑不花钱
        return json.loads(...)
    for d in load_graph():
        text = d.text[:1800]                  # :46 短文足够；控制 token
        out = llm.chat(EXTRACT_PROMPT.format(doc_id=d.doc_id, text=text), max_tokens=800)
        m = re.search(r"\[.*\]", out, re.S)   # :48 截取第一个 JSON 数组（容错）
        for t in json.loads(m.group(0)):
            if all(k in t for k in ("s", "r", "o")):    # :53 字段校验（不信任 LLM）
                t["doc"] = t.get("doc", d.doc_id)
                triples.append(t)

Prompt 里的三条军规对应三个真实风险：

  • "只抽明确陈述的关系"——只要文中写了的边。模型若用自己的世界知识补一条， 这条边没有 doc 可以回去核对；
  • "实体用文中原名"——命名要一致，图才能并到一起。一边抽成 "Intel"、一边抽成 "英特尔"，邻接表里就是两个谁也不连谁的点，叫孤岛；
  • 模板里的 {{"s": ...}} 双花括号是 .format() 的转义（第 13 节 13.2.1）。 写成单花括号时，Python 会把它当成占位符，立刻 KeyError。

14.2.2 邻接表与图召回（toy_graph.py:63-89）

def build_adjacency(triples):                 # :63
    for t in triples:
        adj.setdefault(t["s"], []).append(t)
        adj.setdefault(t["o"], []).append(t)  # :67 无向：s/o 两端都能走

def find_entities(question, adj):             # :72
    return [e for e in adj if e in question]  # :73 实体识别 = 子串匹配（玩具的诚实之处）

def graph_recall(question, adj, max_docs=6):  # :76
    ents = find_entities(question, adj)
    for e in ents:
        for t in adj.get(e, []):
            edges.append(f"{t['s']} --{t['r']}--> {t['o']}  [{t['doc']}]")   # :82
            if t["doc"] not in docs:
                docs.append(t["doc"])         # :84-85 邻居的来源文档 = 图召回结果
            other = t["o"] if t["s"] == e else t["s"]
            edges.append(f"    一跳邻居：{other}")                    # :87-88
    return docs[:max_docs], edges[:12]

:73 的识别方式是子串匹配：实体名作为连续的一串字，出现在问题里就算认出。 没有模糊匹配，也没有同义词。"Intel" 和 "英特尔" 对不上就是漏检。 图路能走到哪里，上限先被这一步卡住。生产系统通常另做一次 LLM 调用， 先从问题里抽出关键词再去对实体（LightRAG 的做法，见 docs/01）。

14.3 如何运行

# 首次：抽取 152 条三元组、131 个实体（调 LLM，约 1 分钟），存 data/graph_corpus/triples.json
python -m scripts.toy_graph

# 只查询（不重新抽取）
python -m scripts.toy_graph --query "GlobalFoundries 和 AMD 是什么关系？"

# 强制重新抽取（改了 EXTRACT_PROMPT 之后）
python -m scripts.toy_graph --force

14.4 真实运行结果

三道问题的对比（图引导 = 只在实体来源文档内检索）：

问题 纯向量 Top-3 图引导 Top-3 结果
吉姆·凯勒和苹果公司怎么连起来的？ apple-silicon, zen, jim-keller 同 都对；但图路给出了证据链：凯勒 --主架构师--> A4 [apple-silicon]
桑德斯和摩尔有什么共同经历？ jerry-sanders, gordon-moore, andy-grove 同 答对，且模型主动指出资料内部表述矛盾（第 8 节引用纪律的回报）
AMD 的 Zen 架构是谁主导的？ zen, zen, zen ❌ jim-keller ✅ 决定性对比："谁主导"匹配不到答案所在文档；图路沿 AMD→Zen→凯勒 的边直接锁定

第三行就是图检索的价值现场：问题与答案所在的文档，在词面和语义上都离得远， 关系图却把它们连着。代码并没有沿边走两步。问题里已经出现 "Zen"， find_entities 把它认成起点，一跳邻居就是凯勒。叙述里的 "AMD → Zen → 凯勒" 是图上的故事；查询实际用到的是其中已经写在问题里的那一站。

12 篇文档时纯向量也常常够用。图的增益要等答案分散、关系链更长、 而且中间实体没有写在问题里的语料上才会拉开。那时候一跳不够，才需要多跳。

14.5 与 LightRAG 的对照（配合 docs/01 笔记阅读）

我们的玩具 LightRAG
抽取 s/r/o 三元组 实体带名字、类型、描述；关系带关键词和描述。抽取有速率限制，实体名会做规范化
图层 邻接表，只走一跳 实体层回答局部问题（local），关系层回答更全局的问题（global）。两个词的定义在第 11 节 11.3
查询 实体名的子串匹配 LLM 先抽查询关键词，再对实体和关系，然后融合
缺什么 没有把同一实体的不同说法合并，没有多跳，没有社区 没有社区摘要。这是它比 GraphRAG 轻的那一刀（第 11 节 11.4）

14.6 查询路由：先判断"这题该走哪条路"

查询路由是在检索之前先选路：这道题交给 BM25、向量，还是图。 all-in-rag 第九章的"智能查询路由"在本课程里就是三层心智模型的调度。

问题含明确符号/型号        → BM25 为主
语义改写/局部事实          → 向量为主 + Hybrid
"谁/什么关系/怎么连起来"   → 图路优先（本节）
全局总结/主题归纳          → 树/摘要层（RAPTOR，本课程外）

最简单的路由器是实体词典加规则：词典就是邻接表的键，问题里出现了这些名字， 就走图。复杂一点则让 LLM 做分类。路由器要可观测：每道题记下走了哪条路、为什么。 Playground 的 Trace 就是让人先充当这个路由器，看清每一路的行为，再决定要不要自动化。

14.7 注意事项

  • triples.json 是抽取结果的缓存：改了 EXTRACT_PROMPT 必须加 --force， 否则永远在用旧图（toy_graph.py:40-41 的短路逻辑）；
  • 邻接表无向（:67）对本语料正确（"凯勒主导 Zen"="Zen 被凯勒主导"），但 有方向语义的关系（"A 继承 B"）无向会引出错误的一跳——扩展前先想清楚；
  • 抽取的 text[:1800]（:46）截断对短文安全，对长文档会静默丢失后半篇的 关系——生产实现要按节分批抽取再合并；
  • 三元组丢失上下文："凯勒 --主架构师--> A4"没有时间线（他后来去了 Intel）—— 图路给出证据链后，仍要回到原文档核对（:82 的 [doc] 溯源就是为了这一步）。

14.8 动手练习

  1. python -m scripts.toy_graph --query "GlobalFoundries 和 AMD 是什么关系？"， 追踪边是怎么把两篇文档连起来的；
  2. 给 EXTRACT_PROMPT（toy_graph.py:27）加一条"跳过年份/地点类实体"， --force 重新抽取，对比三元组数量与查询质量变化；
  3. 把 graph_recall 的 max_docs 从 6 调到 2，看"谁主导 Zen"还能不能答对 ——体会过滤宽严的取舍；
  4. 思考：若语料换成 16 篇 CPU 章节手册，这个玩具图会变成什么样？ （答案：实体是指令/寄存器，关系浅——计划书预言过"手册语料不适合图方法"。）
