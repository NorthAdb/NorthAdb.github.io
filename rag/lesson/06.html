Hybrid 融合：RRF 与量纲绑架

第 06 节约 30 分钟本节自测

手写 RRF；错误示范：直接加权分数；归一化加权的折中；为什么默认选 RRF；v3：RRF 出处、加权变体与边界。

本节任务：能用"量纲绑架"解释为什么不能直接加权两路分数，能手算一个 RRF 融合例子，并记住本课最重要的实验结论之一：错误的融合可以比任何单路都差。

课程地图上的位置：Layer 2 第三站。上一节 05 BM25；下一节 07 Rerank。融合的两路输入就是前两节的 dense_search 与 bm25_search 产出的 Hit 列表。

6.1 融合的难题：两把不同的尺子

Dense 的分数：余弦相似度，取值 [0, 1]      （本课程实测集中在 0.4~0.7）
BM25 的分数：无界非负，实测常见 2~30+     （取决于 IDF 与词频）

直接 α·cos + (1-α)·bm25 会发生什么？BM25 量纲大几个数量级， α=0.5 的"五五开"实际是 BM25 说了算——排序几乎等于 BM25 单路。 这叫量纲绑架。

6.2 代码走读（playground/retrieve/hybrid.py，96 行）

文件顶部注释（hybrid.py:1-11）就点明三个函数的关系：rrf_fuse 正确默认、 raw_weighted_fuse 错误示范、norm_weighted_fuse 可工作的折中。

6.2.1 RRF 本体（hybrid.py:22-57）

def rrf_fuse(lists: list[list[Hit]], k: int = config.RRF_K, top_k: int = 10):
    """多路排名融合。lists: [dense_hits, bm25_hits, ...]"""
    fused: dict[str, dict] = {}
    for lst in lists:                          # :25 逐路遍历
        for rank, h in enumerate(lst):         # :26 名次从 0 开始
            if kid not in fused:
                fused[kid] = {"hit": h, "score": 0.0, "ranks": []}
            fused[kid]["score"] += 1.0 / (k + rank + 1)   # :29 RRF 核心一行
            fused[kid]["ranks"].append(rank + 1)          # :30 记录名次（可观测）
    out = sorted(fused.items(), key=lambda kv: kv[1]["score"], reverse=True)[:top_k]

核心只有 :29 一行：score += 1/(k + rank + 1)。其余都是记账。 meta={"ranks": [...]}（:50）把每路名次塞回 Hit——Playground 的"融合名次" 一栏展示的就是它。

走一遍数字（k=60）：

块 X：Dense 第 1、BM25 第 3   → 1/61 + 1/63 = 0.0323   ← 双路都认
块 Y：Dense 第 2、BM25 缺席   → 1/62 + 0    = 0.0161
块 Z：Dense 缺席、BM25 第 1   → 0 + 1/61    = 0.0164

X 两路都靠前所以登顶；Y 和 Z 都只有一路票，票值相近。RRF 不关心分数差多少， 只关心"几个检索器都把它排在了前面"——这就是它对量纲免疫的原因。 k=60 的作用：压平头部差距。k 越大，第 1 名和第 5 名的分差越小，融合越"温和"。

几个都叫 K 的量不要混（动手练习只拧第一颗）：

名字 在哪 是什么
RRF_K / rrf_fuse 的 k config.py → hybrid.py:21 融合公式 1/(k+名次) 里的平滑常数：越大头部越平
CANDIDATE_K / rrf_fuse 的 top_k config.py → rag.py 传入 每路召回或融合后取几条 Hit（本课 30），与公式无关
ef_search 第 4 节 HNSW 向量图上探多宽，融合根本不读它

ef_search 必须 ≥ 向量路的 top_k（口袋不能比最终要的条数还小），那是 HNSW 的约束， 和 RRF_K 无关。生产 Postgres 里稀疏一路也可以用 tsvector 代替本课的内存 BM25 （第 5 节已写），本节只负责两路名单怎么合成。

:25 的 for lst in lists 说明它天生支持任意多路——第 8 节 multi_query 把 3 组查询的融合结果再并进来（rag.py:165-167），用的就是同一个函数。

6.2.2 错误示范：raw_weighted_fuse（hybrid.py:60-78）

def raw_weighted_fuse(dense, bm25, alpha=0.5, top_k=10):
    pool = {}
    for h in dense:
        pool[_key(h)] = {"hit": h, "s": alpha * h.score}          # 0~0.5
    for h in bm25:
        e = pool.setdefault(_key(h), {"hit": h, "s": 0.0})
        e["s"] += (1 - alpha) * h.score                           # 动辄 10~25

代码本身没有 bug——它错在思想上：两个不可通约的量纲按字面加权。 tests/test_core.py 里有用例断言"junk 块必然登顶"（造一个 BM25 高分但内容 无关的块），把这个错误固化成可运行的证明。

6.2.3 折中：norm_weighted_fuse（hybrid.py:81-96）

def norm(lst):                       # min-max 归一化到 [0,1]
    lo, hi = min(h.score ...), max(h.score ...)
    if hi - lo <= 0:                 # 单元素/全并列：没有分布信息，给满权重
        return {chunk_id: 1.0 for ...}      # :89-90 除零保护（单测抓出的真 bug）

归一化后加权确实救回来了，但仍有两处要警惕：min-max 对离群值敏感 （一个 30 分的异常块会把其他所有块压到接近 0）；α 要调。所以课程结论： 默认选 RRF，norm 加权作为"必须保留分数信息"时的折中。

6.3 如何运行

# 手算验证：三条 Hit 的 RRF 分（对照 6.2.1 的数字）
python -c "
from playground.retrieve.vector_store import Hit
from playground.retrieve.hybrid import rrf_fuse
def h(i, d): return Hit(doc_id=d, chunk_id=f'{d}::{i}', strategy='s', chunk_index=i, content='c', section_path='', score=0)
fused = rrf_fuse([[h(0,'x'), h(1,'y')], [h(0,'z'), h(1,'x')]], top_k=3)
for f in fused: print(f.doc_id, f.score, f.meta['ranks'])
"

# 单测（含量纲绑架的可复现证明）
python -m pytest tests/test_core.py -q -k fuse

6.4 实验 1 的核心证据（MRR@5）

来自 python -m scripts.run_eval 第 1 组（exp1_retrievers），五个方案同一批金标题：

方案 MRR@5 noise@5 相对 RRF
Dense 0.880 0.571 —
BM25 0.808 0.614 —
Hybrid(RRF) 0.928 0.557 基线，全场最优
Hybrid(直接加权-错) 0.822 0.600 -0.106，甚至不如 Dense 单路
Hybrid(归一化加权) 0.884 0.543 可用，但需调 α/β

读表：

  1. 错误加权（0.822）被 BM25 的高分牵着走，名次退化成"接近 BM25 单路"，比 Dense 单路（0.880）还低——这就是"不能直接加分数"的实测证据：一个实现上 没有任何 bug 的函数，因为思想错了，成绩比两路单打都差；
  2. 归一化加权（各自 min-max 后再加权）确实救回来了，但仍需调 α、对离群值敏感；
  3. RRF 零参数、零调参、稳超两路中较弱者。

去 Playground 选 Hybrid（直接加权——错误示范），随便问一题， 对比 Dense 命中和 BM25 命中的分数：你会直观看到"BM25 的 25 分 vs 余弦的 0.6 分" 根本不在一个世界。

6.5 融合 ≠ Rerank（提前划清边界）

查询改写（第 8 节）改的是"查询"——输入之前
RRF 融合（本节）    改的是"多路结果的合并"——粗排
Reranker（第 7 节） 改的是"候选项的顺序"——精排

很多资料把它们混着讲，导致初学者以为"加了 RRF 就不用 Rerank"或反之。 它们是流水线上不同位置的三个部件，本课程全程分开评测。

6.6 注意事项

  • 各路召回的 top_k 要一致：rag.py:138-143 两路都用 config.CANDIDATE_K=30。 若一路召回 10 一路召回 100，RRF 的名次分布不对称，排名靠后的路被系统性压制；
  • RRF 的分数只在本查询内有意义：1/(60+rank) 的绝对值没有语义，不能跨查询 比较（"这题 RRF 0.0323 > 那题 0.0289"不说明任何问题）；
  • 融合发生在两个 Hit 列表之间，与数据库无关——想加第三路（比如图检索）， 构造出 Hit 列表直接丢给 rrf_fuse 即可（第 14 节的图召回就是这么接的思路）。

6.7 动手练习

  1. Playground 同一问题分别用 RRF / 直接加权 / 归一化加权，对比"融合后候选" 的第一名是谁（直接加权下第一名几乎总是 BM25 的第一名）；
  2. 把 rrf_fuse 的 k（config.RRF_K，默认 60）临时改成 5 和 200（记得改回来）， 观察融合后头部名次变化——改的是上一小节表里的第一颗 K，不是 top_k；
  3. 用 6.3 的终端示例把 z 块换成三路（再加一路只有 y 的列表），验证 rrf_fuse 不需要任何修改就能融合三路。

6.8 加厚（v3）：RRF 的出处、变体与边界

  • 出处：RRF 来自 Cormack 等人 2009 年的实验研究，论文标题就叫"Reciprocal Rank Fusion outperforms Condorcet and individual rank learning methods"—— 结论是这个"不像算法的算法"在多路融合上稳赢更复杂的学习方法。k=60 就是 论文的经验值：压平头部名次差距，让第 1 名不至于一家独大（6.2.1 的手算）；

  • 变体：加权 RRF：给不同路配权重（每路 1/(k+rank) 再乘 w 后相加， 如 w_dense=0.7, w_bm25=0.3）——pgvector 0.8 与 Qdrant 的混合检索都支持。 何时值得加权？实测某一路系统性更强时。代价是要调参，且权重有"对这批 金标过拟合"的风险——先跑 6.4 的 RRF 基线，再决定要不要引入这个自由度。

    加权 RRF 和 6.2.3 的归一化加权最容易混：一个给名次加权，一个给分数加权。 本课 hybrid.py 没有实现加权 RRF，只有普通 RRF / 裸加权 / 归一加权。

    加权 RRF 归一化加权（hybrid_norm）
    加权对象 Rank：w / (k+名次) Score：先 min-max 再 α·Dense+(1-α)·BM25
    用不用原始分数 不用 用（只是先拉到 [0,1]）
    在决定什么 "谁的排名更值得信" "谁的分数更值得信" 
    加权 RRF：     Rank → 1/(k+rank) → × 路权重 → 相加
归一化加权：   Raw score → min-max → × α → 相加

    四条路怎么记（前三条对应 retriever=hybrid / hybrid_raw / hybrid_norm）：

    方法 看什么 优点 主要问题
    RRF（默认） Rank 稳定、不受量纲影响 丢失原始分数差距
    裸加权 原始 Score 实现最简单 量纲绑架
    归一化加权 归一化 Score 解决量纲，仍保留分差 要调 α、离群值敏感
    加权 RRF Rank + 路权重 保留 RRF 稳定性，同时偏向强路 要调 w、可能过拟合 
    实际路线：Dense + BM25 → 先普通 RRF 当基线
          → 看 6.4 / Playground 哪一路系统性更强
          → 必要时再试加权 RRF（给排名加权），不要一上来调 α

  • 融合时机的两个流派：本课程是"先融合多路候选、再统一精排"（rag.py 的 顺序：召回 → 融合 → 精排）；另一派"各路先各自精排、再融合名次"——后者 贵 N 倍（每路都要过一次 reranker），通常只在各路异构（向量 + 图 + SQL） 时才值得；

  • 边界：RRF 假设"各路质量相近"。若一路明显强（某语料上 BM25 几乎全对）， RRF 会把弱路的噪声票也计入——这时加权、甚至退回单路，都是诚实选项。 融合不是信仰，是可实测的工程选择，6.4 的五方案对比表就是证据。
