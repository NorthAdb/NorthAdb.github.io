评测进阶：LLM-as-judge 与指标保护

第 13 节约 40 分钟本节自测

RAG 评估三元组（Faithfulness/AR/CR）实测；judge 的三条纪律；单测守住指标回归；v4：声明、回归、冒烟测试与裁判偏差在首次出现处展开。

本节任务：掌握生成侧的自动评测（RAG 评估三元组）与"指标保护"的 单测纪律——从此你的每次重构都有安全网。上一节 12 框架对照； 下一节 14 极简 GraphRAG。

课程地图上的位置：v2 加厚篇第一站。第 10 节解决"检索层好不好测" （Recall/MRR 有金标），本节解决"生成侧怎么自动评"（答案没有标准答案， 只有好坏程度）。

13.1 RAG 评估三元组

这里的三元组是三个分数，不是第 14 节图上的"主体、关系、客体"。 三个分数各看生成链路的一段：

Context Relevance   送进 LLM 的证据与问题相关吗？   → 低分先查检索层
Faithfulness        答案的每个声明有 Context 支撑吗？ → 低分 = 幻觉风险
Answer Relevance    答案真的在回答问题吗？          → 低分 = 答非所问/拒答失败

声明是答案里可以单独判断对错的一句话。Faithfulness 逐句问：这句话能在资料里找到依据吗。 幻觉（第 8 节）是模型写出资料里没有的内容。Faithfulness 低，就是这种句子变多了。

后面行文里的缩写：CR = Context Relevance，F = Faithfulness，AR = Answer Relevance。

三层心智模型直接对上：CR 查 Layer 2（检索），F 查 Layer 3 的生成约束，AR 看整次回答有没有对准问题。 三者可以各自变坏。检索好、答案却编造，是 F 低而 CR 高。证据够、却答非所问，是 AR 低而 CR 高。 所以三个都要测。合成一个总分之后，看不出坏在哪一层。

13.2 代码走读（playground/eval/judge.py，122 行）

13.2.1 三个裁判 Prompt（judge.py:19-45）

每个 Prompt 都是同构的五段式：角色设定（"你是严格的评审"）→ 输入材料 → 分档定义（"完全支撑=5，大部分=4，明显无依据=2，多数无依据=1"）→ 只输出 JSON 的格式约束 → 变量插值。Faithfulness 的完整版（judge.py:19-28）：

FAITHFULNESS_PROMPT = """你是严格的评审。根据【资料】判断【回答】是否完全由资料支撑。

资料：
{context}

回答：
{answer}

规则：找出回答中"资料不能支撑的声明"。完全支撑=5，大部分支撑=4，
有明显无依据声明=2，多数内容无依据=1。
只输出 JSON：{{"score": 1-5, "unsupported": ["无支撑声明1", "..."]}}"""

两个细节：

  • {{"score": ...}} 双花括号是 .format() 的转义。str.format 把单花括号里的名字当成占位符， 到时候用参数替换。JSON 示例本身也有花括号，若不写成 {{ }}，Python 会去找一个叫 "score" 的参数，找不到就抛 KeyError（按键取值失败）。第 14 节的抽取 Prompt 是同一写法。
  • Faithfulness 额外要 "unsupported" 列表：裁判必须列出它认为没有依据的那些声明。 人工抽检时对着这份清单核对，而不是只看一个 1 到 5 的数字。

13.2.2 容错解析与单题评审（judge.py:48-85）

def _parse_json(text):                          # :48
    m = re.search(r"\{.*\}", text, re.S)        # :50 从 LLM 输出里截第一个 {...}
    try:
        return json.loads(m.group(0)) if m else {}
    except json.JSONDecodeError:
        return {}                                # 解析失败 = 返回空，不炸流程

re.S 是正则的 DOTALL 标志：让 . 也能匹配换行。模型吐出的 JSON 经常跨行， 没有这个标志，\{.*\} 会在第一行就停，括号对不齐。 json.loads 把 JSON 文本变成 Python 的字典或列表。文本不合法时抛 JSONDecodeError， 这里接住并返回空字典，后面的聚合把它当成"这项没有分数"。

           "context_relevance": None, "unsupported": []}

:48-56 的 _parse_json 就是"格式化生成必须过校验层"（第 15 节的共同结论） 的评测版。:62 分数初值是 None 而不是 0。None 表示这项没评出来； 0 会变成一个极差的分数。聚合时 :104-106 的 avg 只统计真正的数字， 没评上的项不拉低平均。

13.2.3 抽样与聚合（judge.py:88-115）

judge_schemes 对每个方案抽 10 道可回答题 + 5 道不可回答题（:91-92）， 完整链路跑一遍（:98 的 RAGPipeline_answer 包装了 Pipeline.answer， :118-121）再逐条评审。抽样是只评一部分题：每题 3 次裁判调用， 15 题 × 2 方案大约 90 次 DeepSeek 调用，约 3 分钟。 样本小，绝对分数会抖，所以 13.4 只拿来比较两个方案谁高谁低。

13.3 如何运行

python -m scripts.run_judge      # 约 3 分钟，结果进 experiments/exp7_judge.md + .json

运行器 scripts/run_judge.py:16 的 main() 固定对比两个方案 （Dense 基线 vs Hybrid+Rerank 完整版）。想换方案：改 main 里的 schemes 字典即可，judge 本身不感知方案。

13.4 实验 7 结果（本机真实运行）

方案 Faithfulness Answer Relevance Context Relevance
Dense 基线 5.00 3.53 2.47
Hybrid+Rerank 完整版 4.87 3.60 2.87

三个诚实的读数（这份报告最有价值的部分是"怎么解读"）：

  1. Faithfulness ≈ 5：引用+拒答约束（第 8 节）在起作用——答案基本没有 无支撑声明；
  2. Context Relevance 只有 2.5-2.9：裁判被问"证据里相关部分占比"，而我们 每题送 5-6 块、往往只有 1-2 块直答——与第 10 节 noise@5≈0.55 完全互相 印证。两个独立方法指向同一个事实：Top-K 有一半名额是"凑数的"，这正是 Rerank 与压缩（第 7 节 7.8）的价值空间；
  3. Answer Relevance 3.5-3.6 偏低：人工抽查发现主要是裁判对拒答不友好—— 不可回答题的正确回答"资料中没有相关信息"被判"没有回答问题"。 教训：judge Prompt 要把"正确拒答"定义为满分情形，或者对不可回答题 单独评审"是否正确拒绝"。

[!IMPORTANT] LLM 裁判的三条纪律：① 只做方案间相对比较，绝对分数无意义；② 必须配合 人工抽检校准；③ 不能替代金标硬指标——Recall/MRR 是从金标算出来的， judge 分数是"另一个 LLM 的观感"。

13.5 指标保护：34 个单测守住回归

回归指一次改动把原先正确的行为又弄坏了。评测可以重跑，但人不会每次改完 tokenize 都记得再跑全套金标。单测把"这个函数现在必须仍然算出这个数"写死， 回归会在 pytest 亮红时被看见。pytest 是测试运行器，收集 test_ 开头的函数并执行。

tests/ 现在三个文件：

tests/test_core.py       纯函数测试（不碰数据库/网络）
  · chunker：标题路径、embed_text 标题前缀、Parent-Child 关联
  · cleaner：页眉页脚过滤、样板句移除
  · bm25.tokenize：SSE4.2 / AVX-512 / VPGATHERDD 必须整体成词（符号题命脉）
  · rrf_fuse：手算分值断言（1/61+1/62）
  · raw_weighted_fuse：量纲绑架的可复现证明（断言 junk 必然登顶）
  · 评测指标：Recall/MRR/noise 的手算校验
tests/test_db_smoke.py   rag_test 库冒烟：建表→假向量入库→Dense/BM25 检索→清理
tests/test_kb.py         KB 系统：解析器 / doc_id 命名 / 拒答 / 会话级联
                         / CRAG 纯函数 / 粘贴建文档生命周期

冒烟测试不证明每个边界都对，只证明这条链路通电了能跑通：建表、写入、检索、清理。 库没启动或 SQL 写错，它会比金标评测更早失败。

运行：

python -m pytest tests/ -q        # → 34 passed
python -m pytest tests/test_core.py -q -k fuse   # 只跑融合相关的保护用例

它们的由来也是教学素材：第一次运行就抓出 3 个问题——norm_weighted_fuse 单元素列表除零的真 bug（hybrid.py:89-90 的保护就是那时加的）、RRF 输出 round(·,5) 的舍入断言、标题小节的行为理解偏差。测试的价值在第一次运行就兑现了。

[!NOTE] 测试库隔离的坑（真实踩过）：test_db_smoke.py 用环境变量切 rag_test 库， 但 pytest 按文件名顺序收集时 test_core.py 可能先 import 过 config—— 环境变量就晚了。正确做法是 import 后直接改 config.DB_DSN 属性。 连接是懒建立的：get_conn 第一次被调用才真正去连数据库 （playground/db.py:17-21）。改属性发生在这次调用之前，连上的就是测试库。 若 import 的那一刻就已经连上，再改环境变量也来不及。这个修复写进了两个测试文件头注。

13.6 动手练习

  1. 把 judge 的三个 Prompt 里的"严格"改成"宽松"，看分数漂移多少——体会裁判偏差；
  2. 故意在 bm25.tokenize 里把 avx-512 按连字符拆开，跑 pytest 看哪个用例拦截它；
  3. 给不可回答题写一个专用 judge Prompt（满分=正确拒答），重跑对比 AR 分数 （13.4 第 3 条的落地）。

13.7 加厚（v3）：LLM 裁判的已知偏差与对策

LLM 当裁判有一组被反复记录的系统性偏差——认识它们，才知道 13.4 那三条纪律 为什么长那样：

偏差 表现 对策
位置偏差 两份答案并排比较时，偏爱写在前面的那份 成对评测：交换左右顺序再评一次，两次分数取平均
长度偏差 偏爱更长、面面俱到的回答 Prompt 写明"简洁且准确优于冗长"，再抽样核对
自负偏差 偏爱和自己同一家族模型的文风 裁判模型与被评模型用不同来源
严格度漂移 同一份 Prompt，这一批打得松、下一批打得紧 temperature=0（第 0 节：采样随机度；0 表示尽量不随机）；对比的方案放在同一次批里跑完
拒答不友好 正确拒答被判成"没回答问题" 把"正确拒答"写进满分定义（13.4 第 3 条的根因）

对照 13.4 的实测：AR 3.5-3.6 偏低的主因就是最后一行；Faithfulness 拿到 5.0 则受益于"unsupported 清单"——要求裁判给出可检查的依据，是压制所有偏差的 通用手段（有依据的分数才能被人工抽检纠正）。

judge 的定位因此更清楚：它是便宜、可扩展的相对比较器，不是真理—— 金标硬指标（第 10 节）+ LLM 裁判 + 人工抽检，三角组合才是完整评测。
