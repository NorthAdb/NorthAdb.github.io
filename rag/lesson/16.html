高级范式案例：Self-RAG / CRAG / Agentic RAG

第 16 节约 40 分钟本节自测

三个范式三句话；CRAG 纠正循环可运行版（rerank 分数当评估器）；控制流地图；v4：控制流、微调 token、空带与标定在首次出现处展开。

本节任务：给三个范式各自一个 30 秒电梯陈述，并把 CRAG 做成可运行的 极简版亲手跑一遍。读完你应该能在"检索不可靠"的场景里一眼认出该上哪层 控制流。上一节 15 查询构造；下一节 17 个人知识库。

课程地图上的位置：v2 加厚篇收尾。所有范式共同点：在单次流水线外面 加了一层控制流——这正是前面 15 节"无条件流水线"之后的自然一步。

16.1 三个范式，三句话

范式在这里指一种控制流的形状，不是又一个检索算法。 控制流是"下一步做哪件事，取决于上一步的结果"。 第 1 到 15 节的流水线是固定顺序：改写、检索、融合、生成，每一步都会发生。 本节的三个名字都在这条直线外面加了判断。

范式 一句话 解决什么
Self-RAG 模型自己决定要不要检索、检索结果能不能用、要不要重写 把"何时检索"放进生成过程
CRAG 先给检索质量打分，不合格就纠正：再检索、换问法，或拒答 检索经常不可靠时，给系统一个刹车
Agentic RAG 检索是 Agent 手里的一个工具，多步"检索、判断、再检索、综合" 一次 Top-K 装不下的多跳问题

Self-RAG 的原版要微调：改模型的参数，让它学会在生成中途吐出几个特殊 token。 ISREL 表示"刚检索到的这段和问题相关吗"，ISSUP 表示"这段能不能支撑我正要写的这句话"。 token 在这里是模型词表里的一个符号，不是第 5 节分词得到的词。 本课程没有微调。用 Prompt 让模型先评价证据再回答，是它的近似； 第 8 节的系统约束加上第 13 节的 Faithfulness，是生成结束之后再评的版本。

CRAG（Corrective RAG，纠正式 RAG）把判断放在检索之后：证据差就不要直接拿去生成。

Agent 在这里指一个循环：模型说"调用某个工具、参数是这些"，程序真的去执行， 把结果送回，模型再决定下一步。工具就是它能调用的函数，例如 retrieve(query)。 回边是这个循环里从"判断"回到"再检索"的那一条，相对的是一条直线走到生成就结束。 多跳（第 11 节：沿关系走多步）常常要这种回边，因为第一轮检索还看不到链的下一站。

三者的差别是判断放在哪：Self-RAG 放在生成模型里面，CRAG 放在一次检索之后， Agentic 放在整个循环外面，可以转许多圈。

16.2 CRAG 极简版：代码走读（scripts/demo_crag.py，92 行）

问题 → 第一轮检索（Hybrid+Rerank）
         ↓
   rerank 分数 ≥ 0.35？──是──→ 直接生成
         ↓否
   纠正动作：multi-query 重检索（本地版"扩大搜索"）
         ↓
   分数回升？──是──→ 用纠正后的证据生成
         ↓否
   拒答（CRAG 原版是回退到 Web 搜索；本地知识库场景=承认不知道）

四个函数，每个都有行号可查：

LOW_SCORE = 0.35                        # :20 评估阈值（rerank 分数）

def retrieve_and_score(question, rewrite):        # :28 一轮检索+评估
    opts = PipelineOptions(retriever="hybrid", use_rerank=True,
                           rewrite="multi_query" if rewrite else "none")
    t = RAGPipeline(opts).retrieve(question)      # :31 复用第 1-10 节的全部积木
    ctx = build_context(t.reranked)               # :32 复用第 8 节装填
    return t, ctx, t.reranked[0].score if t.reranked else 0.0   # :33 top1 分 = 评估器

def crag_answer(question):                        # :44 三段控制流
    # ---- 第一轮（:48-54）
    t1, ctx1, s1 = retrieve_and_score(question, rewrite=False)
    if s1 >= LOW_SCORE:
        trace["decision"] = f"top={s1:.2f} ≥ {LOW_SCORE} → 证据可信，直接生成"
        trace["answer"] = answer_with_context(question, ctx1.text)
        return trace
    # ---- 纠正轮（:57-67）
    mqs = query_rewrite.multi_query(question, 3)  # :57 第 8 节的 multi_query 当"扩大搜索"
    t2, ctx2, s2 = retrieve_and_score(question, rewrite=True)
    if s2 >= LOW_SCORE and s2 > s1:               # :64 两个条件：够好 且 比第一轮好
        trace["decision"] = f"纠正有效：{s1:.2f} → {s2:.2f}"
        ...
    # ---- 仍不可信：拒答（:70-74）
    trace["decision"] = "纠正后仍低 → 证据不足，拒答"
    trace["answer"] = "资料中没有相关信息，无法回答这个问题。"

评估器就是给"这批证据够不够好"打一个数的部件。 本节用第 7 节 reranker 的第一名分数，没有另训一个模型。 :64 的 s2 > s1 要求纠正之后必须比第一轮更高。 只要求"过了 0.35"时，第二轮可能更吵、却刚刚过线，这叫负纠正：动作做了，证据更差。

trace["steps"] 把每轮的分数、命中文档、决策全部记录（:49-50, 58-62）—— 控制流越复杂，可观测越重要（本节 16.5 的地图就是这个思想）。

16.3 本机真实运行

python -m scripts.demo_crag       # 3 道题，每题 1-2 轮检索（会调 LLM）

Q: AVX2 新增了哪些招牌特性？      第一轮 top=0.994 → 直接生成 ✅
Q: 为什么需要多级缓存？           第一轮 top=0.909 → 直接生成 ✅
Q: Intel 18A 工艺的量产时间？     第一轮 top=0.00 → 触发纠正
    multi-query: ['Intel 18A 工艺 量产时间', 'Intel 18A 制程 何时大规模生产', ...]
    纠正后 top=0.00 → 仍低 → 拒答："资料中没有相关信息，无法回答这个问题。" ✅

三个观察：

  1. 评估器为什么用 rerank 分，不用余弦相似度。 余弦相似度是第 4 节的那个分数： 没有真答案时，库里"最不坏"的一块仍然会得到 0.5 上下。reranker 对"真不相关" 会给到 0.00 附近，刹车才踩得下去。
  2. 纠正要有次数上限。 论文里的 CRAG 循环一两轮就停。本实现固定最多两轮， 否则每一轮都是一次召回加一次精排，费用随圈数涨。
  3. 扩大搜索在只有本地库时，就是 multi-query 或换一个检索器。 原版 CRAG 不合格时会去调 Web 搜索。本地知识库没有外网可搜，最后一档是拒答。

阈值 0.35 来自分数的分布，不是一个通用常数。第 7 节里，可回答题的 top1 大多在 0.9 以上， 完全不相关在 0.0 几。中间一大段几乎没有样本，这段空隙叫空带。 阈值放在空带里，两侧的题不容易被切错。换一个 reranker，分布会搬地方， 0.35 就要重做标定：拿金标里的可回答题跑一遍，看 top1 实际落在哪，再把阈值放进新的空带。 KB 用的是同一个数（kb/config.py:25），并用真实查询对过这个分布。

16.4 Self-RAG 与 Agentic RAG：本节只扫到能对上零件

16.1 已经定义过微调和那两个 token。这里只补"为什么不在本课程把论文复现出来"：

  • Self-RAG 的原版要训练出那些特殊 token。用 Prompt 近似的部分，第 8 节和第 13 节已经有了。 再复现训练，学到的仍是"生成过程中插入判断"，零件不会变多。
  • Agentic RAG 的最小形态，是一个会调用 retrieve(query, filter) 的循环。 PipelineOptions 就是这个工具的参数表：检索器、是否重排、strategy、meta_filter 都在上面。 要新学的是何时停：循环上限、费用预算、同一查询不要重复。 LangGraph、LlamaIndex Workflows 这些框架把循环画成一张图，节点是步骤，边是"接下来去哪"。 图上的概念没有超出 16.5 的那张控制流地图。

16.5 与既有课程的连接（本课程的"控制流地图"）

第 6 节  RRF 融合          = 无控制流的合并
第 8 节  查询改写          = 固定的一次前置变换
第 14 节 查询路由          = 单次分派
本节    CRAG              = 检索后的一次条件分支
        Agentic           = 完整循环（分支 + 回边）

控制流越复杂，可观测性越重要——本课程坚持每步 Trace，就是为了在加控制流时 还能看清每一步为什么发生。

16.6 如何运行

# CRAG 三道题演示（会调 LLM；改 LOW_SCORE 后重跑看决策变化）
python -m scripts.demo_crag

# 终端里把阈值当旋钮：0.8（宁可多纠正）vs 0.2（几乎不纠正）
python -c "
import scripts.demo_crag as dc
dc.LOW_SCORE = 0.8
print(dc.crag_answer('为什么需要多级缓存？')['decision'])
"

产品化落地：KB 的聊天已内置同款循环（kb/chat.py:85 的 retrieve_kb， crag=True 时启用），每轮步骤落库并在前端"检索过程"面板展示—— /kb 页勾选"检索纠错 (CRAG)"即可体验，无需跑命令。

16.7 注意事项

  • CRAG 的纠正动作不一定提升质量：multi-query 换了检索词，也可能把噪声 检索进来——:64 的 s2 > s1 就是防"负纠正"的，删掉它试试会发生什么；
  • 评估器的阈值要按当前 reranker 重新标定（16.3）：换模型之后，0.35 可能整段偏高或偏低。 做法是拿金标可回答题看一遍 top1 的分布，再把阈值放进空带；
  • Self-RAG/Agentic 的"要不要检索"决策在闲聊场景比知识库场景更重要—— 知识库几乎每题都该检索，所以本课程没有实现它；做通用助手时再加；
  • 每次纠正都是成倍的成本（再一轮召回+精排，可能再加一次 LLM 改写）—— 上限、预算、超时三样至少要在代码里出现一样。

16.8 动手练习

  1. 跑 python -m scripts.demo_crag，把 :20 的阈值调成 0.8 和 0.2，看三道题 的决策各变成什么（体会阈值=召回与风险的旋钮）；
  2. 把纠正动作从 multi-query 换成"Parent-Child 重检索"（:57 改成调用 parent_child_search），观察纠正成功率变化；
  3. 对比两个 CRAG 实现：本节的 demo_crag.py（纠正 = multi-query 重检索） 与 kb/chat.py::retrieve_kb 的 CRAG（纠正 = LLM 扩展查询 + 合并候选重精排） ——列出两处纠正动作的差异与各自的适用场景；
  4. 设计题：给我们的 Playground 加"Agentic 模式"，工具列表 [retrieve_dense, retrieve_bm25, retrieve_graph(第14节), reject]， 循环上限 3 次——先在纸上画控制流，再决定要不要写代码。
