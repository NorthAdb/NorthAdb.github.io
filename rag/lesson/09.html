知识库工程：元数据、去重与增量更新

第 09 节约 45 分钟本节自测

元数据过滤、strategy 版本、checksum 与增量更新；v3：字段设计清单；v4：jsonb、GIN、@>、upsert、事务在首次出现处展开。

本节任务：视角从"检索算法"切换到"知识库是一套需要维护的系统"—— 掌握元数据过滤、strategy 版本管理、checksum 一致性检测这三件生产必备， 并理解为什么 KB 系统（第 17 节）的入库设计几乎逐条来自本节。 jsonb、GIN、@>、upsert、事务这些词，在本节第一次出现时展开讲完。

课程地图上的位置：Layer 1 的工程收口。上一节 08 改写与装填； 下一节 10 Parent-Child 与评测。

9.1 元数据过滤：检索的一部分，不是附属字段

**元数据（metadata，本课程列名 meta）**是贴在数据上的标签，描述"这条记录是什么"， 本身不是被检索的正文。一篇切片的正文在 content 里；"它来自哪套语料、哪篇文档、 哪一节"这类标签才是元数据。过滤要回答的是："这次只准在哪些标签里找？"

本课程把块上的标签收进 rg_chunks.meta（建表 scripts/init_db.py:48）。 文档表 rg_documents 上也有同名列（:24），职责不同：文档那列记整篇的属性， 块那列跟每一刀切片走，检索 SQL 滤的是块。

9.1.1 jsonb：存进 PostgreSQL 的 JSON

JSON（JavaScript Object Notation）是一种文本格式，用来写结构化数据。 一个对象用花括号，里面是 "键": 值，值可以是字符串、数字、布尔、空、 再套一层对象或数组。本课程写进块上的典型样子：

{"corpus": "main"}

键是 corpus（语料标签），值是字符串 "main"。多加字段就是多一对： {"corpus": "main", "lang": "zh"}。

PostgreSQL 有两种列类型都能装这段文本：

类型 库里实际怎么存 适合做什么
json 原样保留你输入的文本（空格、键的顺序都在） 要一字不差地存档、再原样吐出
jsonb 入库时就解析成二进制结构：重复键合并、键会重排、去掉无意义空白 要按键查询、要建索引——本课程用的就是它

b 是 binary。付出的代价是写入时多一次解析，换来的是读和过滤不用每次重新解析文本。 NOT NULL DEFAULT '{}'（init_db.py:48）的意思是：这一列不许是空值（NULL， "什么都没有"），没写的时候数据库填一个空对象 {}。空对象是合法的 jsonb， 和 NULL 不是一回事——前者是"有一个对象，里面零个键"。

jsonb 不保证键的书写顺序。别把"第一个键是 corpus"写进任何逻辑，要按键名取。

9.1.2 @>：包含，以及 :: 类型转换

检索 SQL 里的过滤子句（playground/retrieve/vector_store.py:40-41）：

AND meta @> %s::jsonb

三个符号拆开：

%s 是占位符。 本课程用 psycopg 连数据库。SQL 文本里写 %s，真正的值 由驱动另路送进去（vector_store.py:45 把 Python 字典 json.dumps 成字符串再传入）。 这叫参数化查询：值不会被拼进 SQL 字符串。过滤条件来自调用方时， 就靠这个避免把用户输入变成 SQL。

::jsonb 是类型转换（cast）。 PostgreSQL 用 值::类型 把左边转成右边的类型。 占位符传进来的是文本，::jsonb 告诉数据库"按 jsonb 来理解这段文本"。 转换失败（不是合法 JSON）会直接报错，不会静默当成普通字符串比较。

@> 是包含操作符（containment）。 左边 @> 右边 为真，当且仅当右边出现的 每一个键值，左边都有，且值相等。左边可以多出别的键。

{"corpus":"main","lang":"zh"}  @>  {"corpus":"main"}     → 真（多出来的 lang 不影响）
{"corpus":"main"}              @>  {"corpus":"main","lang":"zh"}  → 假（右边要求的 lang 左边没有）
{"corpus":"dirty"}             @>  {"corpus":"main"}     → 假（键在，值不同）

所以 meta @> '{"corpus":"main"}' 问的是：这块的标签里是否含有 corpus=main。 整列还可以带着别的键。以后往 meta 里加 lang，旧的 corpus 过滤仍然成立—— 这是 9.5 第一条注意事项的来源。

同一家族里，本节会碰到、以后也躲不开的几个操作符：

写法 含义 例子
@> 左边包含右边 上面三行
<@ 左边被右边包含，即 @> 的反向 '{"a":1}'::jsonb <@ '{"a":1,"b":2}' 为真
? 左边这个对象有没有某个键（不看值） meta ? 'corpus'
-> 按键取出子值，结果仍是 jsonb meta->'corpus' 得到 "main"（带 JSON 引号的 jsonb 字符串）
->> 按键取出子值，结果变成普通 text meta->>'corpus' 得到 main，可以拿去和别的文本列比较

本课程的检索只用 @>。选它是因为"多个条件同时满足"可以自然地写成一个对象： {"corpus":"main","lang":"zh"} 表示两键都要匹配。

可以不碰表、只验证操作符。预期打印一行 (True, False, False)：

python -c "
from playground.db import q
print(q('''
SELECT
  '{\"corpus\":\"main\",\"lang\":\"zh\"}'::jsonb @> '{\"corpus\":\"main\"}'::jsonb,
  '{\"corpus\":\"main\"}'::jsonb @> '{\"corpus\":\"main\",\"lang\":\"zh\"}'::jsonb,
  '{\"corpus\":\"dirty\"}'::jsonb @> '{\"corpus\":\"main\"}'::jsonb
'''))
"

9.1.3 GIN 索引：给"里面含不含这个标签"用的

**索引（index）**是数据库另存的一份查找结构。没有它，WHERE 得把表逐行读完 （顺序扫描，sequential scan）再决定留谁；有它，先在索引里定位，再回表取那几行。 索引让读变快，代价是多占磁盘，并且每次写入都要连带维护。

rg_chunks 上有三份索引（init_db.py:53-58），服务的问题完全不同：

索引 建在哪 类型 回答的问题
rg_chunks_hnsw embedding HNSW（第 4 节的向量近邻图） 哪个向量离查询最近
rg_chunks_strategy_idx strategy B-tree strategy = 'flat500x80' 这类等值
rg_chunks_doc_idx (doc_id, strategy) B-tree 某文档在某版本下的块
rg_chunks_meta_gin meta GIN meta 里是否包含给定的键值

B-tree（平衡树，balanced tree）是 PostgreSQL 不写 USING 时的默认索引。 它把标量值排好序，等值（=）和范围（<、>）都走它。strategy 是普通文本， 一个块一个值，B-tree 正合适。CREATE INDEX ... ON rg_chunks (strategy) （:56）没有写 USING，所以就是 B-tree。

GIN（Generalized Inverted Index，通用倒排索引）解决的是另一种列： 一个格子里装着很多元素。jsonb 的一个对象有多个键值，数组有多个成员， 全文检索的 tsvector（第 5 节 5.9 提过）有多个词。B-tree 只能把"整格"当成 一个整体来排序，回答不了"这格里面有没有 corpus=main"。

倒排的直觉就是书后面的索引：正文是"页 → 页上有哪些词"，索引翻过来做成 "词 → 哪些页出现过它"。查一个词，直接拿到页码列表，不用逐页翻。 GIN 对 jsonb 做的是同一件事：把对象拆成若干条"路径 + 值"，每条指向拥有它的那些行。 @> 就是拿你给的键值去这份倒排表里取交集。

建索引那一行（init_db.py:58）：

CREATE INDEX IF NOT EXISTS rg_chunks_meta_gin
    ON rg_chunks USING gin (meta jsonb_path_ops);

USING gin 指定索引方法。括号里的 jsonb_path_ops 是操作符类 （operator class）：同一套 GIN，可以按不同规则拆 jsonb，决定"倒排表里 每一条到底记什么、以及哪些操作符能用上这份索引"。两个常用选择：

操作符类 倒排表里记什么 能加速的操作符 体积
jsonb_ops（不写时的默认） 每个键、每个值分开记 @>，以及"键在不在"的 ? 较大
jsonb_path_ops（本课程） 整条"路径→值"合成一条记录 只有 @> 明显更小

本课程检索只写 @>，所以用 jsonb_path_ops：索引更小，包含查询更贴这个操作符。 代价要记住——以后如果写成 meta ? 'owner'（只问有没有这个键）， 这份索引帮不上，得另建一个 jsonb_ops 的 GIN，或改写成带值的 @>。

还有一句实话：索引建了，不代表每一条 SQL 都会用它。优化器（planner，数据库里 决定"这条 SQL 怎么执行"的组件）会估代价。本课程几百块的表上，它经常觉得 顺序扫描更便宜，GIN 先闲着。块数到了十万、百万，@> 才会稳定地走 rg_chunks_meta_gin。第 4 节练习里那句"候选集极小时 GIN 反而多余"，说的就是这件事。 想看它实际选了哪条路，在 SQL 前加 EXPLAIN（只打印计划，不执行业务逻辑）。

9.1.4 过滤参数怎么流进来

**语料（corpus）**是一批用途相同的文档，外加一个来源标签。本课程有 main（主语料）、dirty（脏数据对照）、graph（图谱短文）、mineru、kb。 它们的块可以住在同一张 rg_chunks 里，靠 meta 里的 corpus 隔开， 检索时互不可见。

dense_search 的形参 meta_filter（vector_store.py:31-33）是一个字典， 例如 {"corpus": "graph"}。函数里做了两件容易看漏的事：

flt = (meta_filter or {}).copy()
flt.setdefault("corpus", "main")
  • copy() 复制出一份新字典。后面要改的是这份副本，调用者手里的原字典保持原样， 同一份过滤条件还能传给下一次检索。
  • setdefault(键, 默认值) 是字典方法：键已经存在就保持原值，不存在才写入。 于是调用方没提 corpus 时，补上 "main"；调用方明确给了 "graph" 时，不会被盖掉。 corpus 过滤默认是开的。 这就是各语料互不干扰的机制。

调用入口在 PipelineOptions（playground/rag.py:41 的 meta_filter 字段， :38 的 corpus 字段）。retrieve() 里（rag.py:138-139）的规则是： meta_filter 为 None 时，Dense 用 {"corpus": o.corpus}；你传了字典，Dense 就用你这份， 里面可以同时有多个键。

两条路径的入口并不相同。Dense 读 meta_filter；BM25 的参数是单独的 corpus 字符串 （rag.py:144 把 o.corpus 传进 bm25_search）。只改 meta_filter、不改 corpus 时， Dense 去了 graph，BM25 仍停在默认的 main，Hybrid 会把两套语料的命中揉在一起。 要"只搜图谱"，两个都指向 graph：

from playground.rag import RAGPipeline, PipelineOptions
t = RAGPipeline(PipelineOptions(
    retriever="hybrid",
    corpus="graph",                     # BM25 用这个字符串
    meta_filter={"corpus": "graph"},   # Dense 用这份 jsonb 过滤
)).answer("Intel 和 AMD 是怎么产生联系的？")
print(t.final_hits[0].doc_id)

还有一处默认值叠在更里面：dense_search 对拿到的字典执行 setdefault("corpus", "main")。你传了 meta_filter={"lang": "zh"} 这种不含 corpus 的字典时， Dense 仍会补上 corpus=main，补的是字面量 "main"，不会去读 PipelineOptions.corpus。

BM25（第 5 节的词面打分）一侧同一条纪律：_build 的 WHERE 里同样是 meta @>（bm25.py:44）。它和向量检索的差别在缓存。

lru_cache 来自 Python 标准库 functools（bm25.py:38）。它以装饰器的形式写在函数上方： 装饰器是包住函数的一层额外行为，函数本身的代码不用改。这里额外做的事是按参数记住返回值。 同样的参数再来，直接交回上次的结果， 不再查库、不再重建内存里的倒排表。maxsize=8 表示最多留 8 份。 LRU（Least Recently Used，最近最少使用）是满了以后的淘汰规则：丢掉最久没被问到的那份。 这里的参数是 (strategy, corpus)，所以"换一套索引版本或换一个语料"会另算一份， "同一套再搜一次"则命中缓存。

缓存的另一面：库里的块已经更新，内存里的 BM25 还是旧的。KB 入库和删除之后 会调用 cache_clear() 清掉它（kb/store.py:173-176）。课程实验如果绕过这条路径 直接改表，BM25 会继续搜旧结果，直到进程重启或手动 cache_clear()。

9.1.5 为什么过滤必须写在 SQL 的 WHERE 里

WHERE 是 SQL 里写筛选条件的子句。LIMIT 是"最多返回几行"。 Top-K 就是只要排在最前面的 K 条，本课程用 LIMIT 表达。

问"AVX 和 AVX-512 在掩码上的区别"时，如果范围先限定在文档 avx 与 avx512， 近义干扰会直接消失。本课程写进 SQL 的是 meta @>：候选集在打分之前就按标签缩小。 doc_id 也可以同样写进 WHERE，时机相同——都在排序取 Top-K 之前。

两条路要分开：

检索中过滤：WHERE meta @> ...     没通过的行不进入排序，也不进入返回结果
检索后丢弃：先取出 Top-K，再在 Python 里 if 掉标签不对的

检索后丢弃的问题是：名额已经按"未过滤的全库"发出去了。10 个名额里 8 个属于别的语料， 你扔掉它们，手里只剩 2 条，而本语料里本来排第 11 的那条永远没有机会。 过滤写进 WHERE 之后，LIMIT 数的就是过滤之后的名额。

权限标签同理，9.7 会再讲：先查出来再扔掉，不该看的内容已经进了日志和缓存。

9.1.6 HNSW 先取近邻、再过滤

HNSW 是第 4 节的向量索引：一张多层近邻图，查询沿着边跳，不用和全库每个向量都算一遍。 ef_search 是查询时手里握着的候选个数（默认 40，第 4 节 4.2.5）。 和元数据过滤叠在一起时，pgvector 的实际次序是：

1. 在 HNSW 上先找出大约 ef_search 个最近的向量
2. 再对这批候选套 WHERE（strategy、meta @>）
3. 剩下的才按 LIMIT 返回

过滤很严时，40 个近邻里可能只有 2 个 corpus=graph。你要 10 条，它只交回 2 条。 库里并不是没有，是图搜索在凑满 ef_search 之后就停了，后面那些"稍远但标签合格"的块 没被看到。

pgvector 0.8 为此加了 hnsw.iterative_scan（迭代扫描）：一轮过滤之后数量不够， 就继续沿图往下找，直到够数或到达上限。它是会话级参数，和 ef_search 一样要 SET：

取值 行为
off 默认。搜完一轮就停，条件严时结果会缺
strict_order 继续找，返回顺序仍严格按距离
relaxed_order 继续找，允许结果顺序不严格按距离，换更快的扫描

relaxed_order 就是本课程环境说明里点名的那个值（D:\PostgreSQL\README.md 第 9 节； 第 4 节 4.6 也提过）。本课程语料小，ef_search 覆盖得住，坑不显现； 生产上过滤一严就必须知道有这个开关。

9.2 索引版本管理：strategy 是第一公民

9.2.1 strategy：一套索引的名字

**strategy（索引版本）**是一个普通文本列（init_db.py:40），给"同一批文档、 某一种清洗 + 切分 + 向量化方法"起的名字。文档还是那些文档，切法一变， 块的边界和向量都变了，所以必须另存一套，不能覆盖旧的——否则第 3 节的消融 无法并排比较。

命名规则在 playground/ingest/ingest.py:56-57： strategy = f"flat{chunk_size}x{overlap}"，例如 flat500x80 表示固定长度、 块大小 500、重叠 80。Parent-Child 版本手动传 pc_child200；脏语料是 dirty500x80。 目前库里共存 9 个版本（Playground 首页表格实时可见）。

它是约定，不是数据库约束。列类型只是 text，你写成 test1 也能插入。 约束（constraint）是数据库强制的规则，违反就拒绝写入；约定只活在人和代码的默契里。 乱起名能跑，但"看名字就知道切分参数"这条约定就破了。

同一条检索 SQL 里，strategy = %s 走 B-tree（9.1.3），meta @> 走 GIN。 两道门都过，行才进候选。

9.2.2 build_index() 的四步，以及每步的词

写入顺序在 ingest.py:84-127。

第 1 步，删掉该 strategy 的全部旧块（:84-86）：

exec(f"DELETE FROM {config.TABLE_PREFIX}_chunks WHERE strategy = %s", (strategy,))

这一步是为了清除孤儿向量。这里的"孤儿"指：源文本已经换了切法或换了内容， 旧的块行还留在表里，它的 embedding 仍会被 HNSW 和 BM25 搜到。 典型来源是文档变短了。旧版有 chunk_index = 0..12，新版只剩 0..8。 若只插入新行、不先删除，9 到 12 这四块没有对应的新正文，却继续参与检索。 半新半旧比"全部是旧的"更危险——金标对不上时，你分不清是模型退步了还是索引脏了。

第 2 步，upsert 文档（:88 调用 _write_documents，:18-30）。

upsert 是 update + insert 的合成说法：有这条就更新，没有就插入。 PostgreSQL 没有一个叫 UPSERT 的关键字，写法是 INSERT ... ON CONFLICT DO UPDATE：

INSERT INTO rg_documents (doc_id, source, title, checksum, corpus, meta)
VALUES (%s, %s, %s, %s, %s, %s)
ON CONFLICT (doc_id) DO UPDATE
   SET source = EXCLUDED.source, title = EXCLUDED.title,
       checksum = EXCLUDED.checksum, ...
  • **主键（PRIMARY KEY）**是能唯一指出一行的列。doc_id 是文档表的主键 （init_db.py:19），两行不许同号。
  • ON CONFLICT (doc_id) 说的是：如果即将插入的 doc_id 和已有行冲突 （主键不允许重复），不要报错中止，改走后面的更新。
  • EXCLUDED 是 PostgreSQL 给"这次没插进去的那行"起的表名。 EXCLUDED.checksum 就是你 VALUES 里准备写入的新指纹；等号左边的 checksum 是表里已有的那列。

**checksum（校验和）**在这里是内容指纹：由全文算出来的一小段固定长度字符串， 用来发现"源文件改了，索引还是旧的"。计算在 loader.py:40：

hashlib.sha256(text.encode("utf-8")).hexdigest()[:16]

**哈希（hash）**把任意长度的字节变成固定长度的指纹。改一个字，指纹整个换掉 （这种"输入微变、输出全变"叫雪崩）。它是单向的：从指纹推不回原文， 也不是加密——没有密钥，谁都可以对同一段文本算出同一个值。

SHA-256 是一种哈希算法，输出 256 位，写成十六进制是 64 个字符。 hexdigest()[:16] 只留前 16 个字符（64 位）。对"文件有没有被改过"这件事， 16 个十六进制字符在个人知识库的规模上足够：两篇不同文档碰巧得到同一指纹的概率 可以忽略。它用来发现意外修改和漏重建。hexdigest() 就是把那 256 位印成十六进制字符串。

指纹变了，ON CONFLICT 那条更新会把 updated_at 刷成 now() （ingest.py:27）。now() 是数据库函数，取当前时间。于是"源文件变了" 可以事后查出来，而不必重读磁盘。KB 的"同名重传、checksum 相同就跳过" （kb/ingest.py:53-58）是同一思想：指纹没变就不要重新向量化，省掉一次嵌入 API。

第 3 步，Parent-Child 才写父块（:89-99），并修正 section_path（:100-107）。

Parent-Child（第 10 节的正式内容，这里先混个脸熟）：短的子块用来被搜到， 命中后再取出它所属的整节长文本送给模型。父块存在 rg_parents， parent_id 形如 doc_id::sec3。只有 strategy 名字以 pc_child 开头时， ingest.py:70 才会走上这条分支；flat500x80 没有父块。

section_path 是标题链，例如 CPU 概述 > 缓存（第 3 节切分时生成）。 它存在块上，供命中列表显示"这段话出自哪一节"。父块插入时先写了空字符串， 随后用一条 UPDATE ... FROM 从子块把标题链抄回去。

第 4 步，插入新块和向量（:109-127）。冲突处理这次是 DO NOTHING：

ON CONFLICT (doc_id, strategy, chunk_index) DO NOTHING

UNIQUE (doc_id, strategy, chunk_index)（init_db.py:50）是一条唯一约束： 这三列的组合不许出现第二行。于是"同一文档、同一索引版本、同一个序号"只有一块。 chunk_id（第 3 节见过）就是这三列用 :: 拼出来的字符串，例如 avx::flat500x80::3。

DO NOTHING 和上面的 DO UPDATE 是同一语法的另一支：撞上唯一约束时跳过这一行， 不更新、不报错。在第 1 步已经把该 strategy 删干净的前提下，正常运行不该发生冲突。 DO NOTHING 不会改写已存在的旧块，所以去孤儿仍然靠第 1 步的 DELETE； 省略删除的话，变短文档多出来的旧序号会原样留下。

对应的删除工具是 drop_strategy()（ingest.py:141-144）：按名字一次删净一个版本的块。 不要手动 DELETE 掉其中一部分块。 删一半再插一半，就是上面说的半新半旧。

块通过**外键（foreign key）**指向文档：chunks.doc_id REFERENCES rg_documents(doc_id) （init_db.py:39）。外键要求这一列的值必须在被引用的表里真实存在， 禁止出现"块指向一篇已经没有的文档"。后面的 ON DELETE CASCADE（级联删除） 表示：文档行被删时，数据库自动删掉引用它的块和父块，不留悬空指针。 KB 的 delete_document 先按 doc_id 删块、再删文档，最后清 BM25 缓存 （kb/store.py:106-108）。就算只删文档行，级联也会把块带走。

9.3 增量更新 vs 全量整理

增量更新：只处理变化了的那几篇（本章的 upsert；别的文档不动）
          快、便宜，适合日常吸收新文件
全量整理：定期把全库再走一遍（去重、冲突检测、换切分参数后整套重建）
          慢、贵，能看见"长期堆出来的冗余和互相矛盾"

增量的单位是"变化的文档"。一篇文档改了一个段落， 本课程的做法仍是按 doc_id 重切、重嵌入这一篇的全部分块——切分边界会连带移动。 overlap（第 3 节）是相邻块互相重叠的那一段字；只换中间一块，前后块带着的重叠 会对不上新正文。 全量的单位是"一套 strategy 或整个库"：所有文档重新清洗、重新切、重新嵌入。

现实系统两者一起用：日常增量 + 定期全量。本课程的 build_index 在语义上 是"按 strategy 全量重建"（先删该版本的全部块，再整批插入）。语料只有几十篇， 这比逐篇判断谁变了更简单，也更不容易留下孤儿。

十万文档就不能每次都这样：一次重建的嵌入费用和时间都线性涨。 KB 的 reindex_document（kb/ingest.py:106-115）是按篇增量的雏形—— 只读那一篇的磁盘原件，只替换那一篇在 KB strategy 下的块 （kb/store.py:70-75 的 DELETE 带了 doc_id 和 strategy 两个条件）。 别的文档的向量不动。

9.4 去重的三个层次（与第 2 节呼应）

同一段话出现两次，检索会把它当成两份证据。去重要分清发生在哪一层：

层次 时机 方法 已实现于
文本级 清洗时 相邻的、内容相同的行只留一行；样板句删掉 cleaner.py:43-52
文档级 清洗时 整篇 checksum 相同的文档只留第一篇 cleaner.py:63-71
块级 装填时 同一个 chunk_id 只留一条 context_builder.py:27-33

文本级处理的是"同一篇内部，页眉页脚被复制粘贴了很多次"。 文档级处理的是"两个文件正文完全一样"（指纹相同，cleaner.py:67 直接跳过）。 块级发生在检索之后、送给模型之前：Dense 和 BM25 两路都命中了同一块时， chunk_id 相同，装填只占一个名额。

装填层没有按父块去重。同一个父节下的两个不同子块，chunk_id 不同， 两段都会留下。把"多个子块收成一节"是第 10 节 expand_to_parents 的工作， 不要把它记成 context_builder 已经做了。

实验 2 里"avx.md 复制了 avx2 的段落"，伤害是这样走的：

  • token：分词之后的一个词（第 5 节）。重复段落让同一个 token 在语料里多出现一次。
  • 文档频率：有多少块含有这个 token。重复把这个数抬高了。
  • IDF（逆文档频率，第 5 节）：越少见的词越有区分度。文档频率被抬高之后， IDF 变小，这个词在 BM25 里变得"没那么稀奇"，真正相关的那一块排名下滑。
  • Top-K 名额：两块内容一样，却占掉两个席位，别的文档被挤出去。

装填层按 chunk_id 去重能挡住"同一块从两路检索来了两次"，挡不住"两篇文档里 各有一块，文本相同但 chunk_id 不同"。后者只有入库前的文档级、文本级去重能去掉。 所以说：装填层能止血，入库层才治本。

9.5 注意事项

  • @> 是包含（9.1.2）。meta @> '{"corpus":"main"}' 不要求 meta 只有这一个键。 加新字段不会让旧过滤失效。反过来，过滤对象里多写一个块上没有的键，一行都匹配不上。

  • strategy 是约定不是约束（9.2.1）。数据库不检查名字是否符合 flat{尺寸}x{重叠}。

  • build_index 的先删后插不是一个事务。

    事务（transaction）是一组 SQL，要么全部生效，要么全部取消。 开始到结束之间，别人看不到半成品；中途失败则回到开始之前的样子。 这种"不可只做一半"的性质叫原子性。写法是 BEGIN … 若干语句 … COMMIT （提交，正式生效）；失败则 ROLLBACK（回滚，全部撤销）。

    本课程的连接是自动提交：playground/db.py:20 的 autocommit=True。 每一条 exec() 执行完就立刻永久生效，没有包在同一个 BEGIN/COMMIT 里。 因此第 1 步的 DELETE 一旦返回，旧块就已经没了。若接下来嵌入 API 超时、 进程被杀掉，这个 strategy 会停在"旧的已删、新的没写完"。 生产上要把删和插放进同一个事务，失败就回滚，旧索引还在； 或者像 KB 那样把删除范围收成一篇文档（kb/store.py:70-92）—— 失败时坏掉的是一篇，不是整套版本。KB 这条路径同样是自动提交， 它缩小的是爆炸半径，并没有变成事务。

  • checksum 只在读文件入库时重算（loader.py:40）。你改了 data/corpus/ 里的 Markdown，网站不会盯着磁盘。下一次 build_index 或 KB 的重新入库才会比较指纹。 指纹相同就跳过的逻辑，也只在那次运行里发生。

9.6 动手练习

  1. 用 9.1.4 的代码块跑一次"只检索图谱语料"（corpus 和 meta_filter 都是 graph）， 再跑一次两者都改回 main，对比 Top-5 的 doc_id。 然后跑 9.1.2 的小脚本，确认打印出来的是一行 (True, False, False)—— 这就是"加字段不会破坏旧过滤"的依据。
  2. 手动模拟增量更新：往 data/corpus/ 加一篇短文，只重建 flat500x80 （python -c "from playground.ingest.ingest import build_index; build_index(corpus='main', strategy='flat500x80')"）， 确认旧文档的 chunk_index 还在，新文档出现在同一 strategy 下。 做完记得：这次是按 strategy 全量重建（9.3），不是只嵌入了新文件。
  3. 思考：如果一篇文档改了标题但正文没变，checksum 会变吗？该重建吗？ （答：会变——checksum 算的是全文，标题在全文里。要不要重建取决于标题是否进入 embed_text。本课程会把当前小节标题加到被向量化的文本前面（chunker.py:106）， 所以该重建。这就是"清洗或切分规则变了，索引版本也要变"的一个具体例子： 正文没变，送去嵌入的字符串变了，旧向量已经对不上新的 embed_text。）

9.7 加厚（v3）：元数据字段设计清单

meta 是 jsonb 自由字段（9.1.1）：建表时不必为每个标签加一列，写入什么键都可以。 自由不等于随便。生产知识库的常用字段按用途分三类——为过滤、展示、权限而设：

字段 用途 谁在消费
corpus（本课程已用） 隔离不同来源的语料 检索过滤（9.1 的 meta @>）
doc_id / chunk_index（已是正式列） 定位与溯源 引用卡"查看原文"（第 17 节）
source_type 只要某一种来源：md、pdf、网页、聊天记录 检索过滤
title / section_path（已用） 命中展示与引用出处 Playground 命中列表、citation
created_at / updated_at "只要最近一年"这类时间范围 检索过滤（条件严时回到 9.1.6 的 HNSW 坑）
version / doc_status 只检索生效版本；草稿、作废不进结果 检索过滤
permissions / owner 谁可以看见这条 检索过滤，必须写在 SQL 的 WHERE 里
lang 多语言分流 检索过滤，以及选哪一种分词器（第 5 节）

三条设计纪律：

  1. 值要规范化。 日期用同一种写法；状态用枚举——事先定好的有限个值， 例如 draft / active / retired，不要有人写"生效"、有人写"已发布"。 代码里用白名单把非法值挡在写入之前：不在名单上的直接拒绝 （第 15 节把同一思想用在"模型生成的过滤条件"上）。 自由文本进了 meta，@> 要求值逐字相等，多一个空格就匹配不上。
  2. 权限是安全边界。 多租户指同一个库里住着多个互相不能看见对方数据的使用者 （租户）。permissions 或 owner 必须出现在 SQL 的 WHERE 里（9.1.5）。 先检索再在界面上隐藏，内容已经进了日志、BM25 的 lru_cache 和可能的调试输出。
  3. 字段要节制。 每加一个键，以后所有写入路径都有义务填对它。 先问"将来哪条查询会按它过滤？"答不上来就不要加。 展示用的标题更适合放正式列（本课程的 title、section_path 就是列，不是 meta 里的键）， 因为它们几乎每条命中都要读，不需要走 GIN 的包含查询。
