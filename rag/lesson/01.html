RAG 全景复习：三层心智模型

第 01 节约 20 分钟本节自测

知识工程 / 检索工程 / 上下文工程；为什么 RAG 不是“向量数据库技术”；v3：长上下文之辩等三个高频质疑。

本节任务：建立一张"三层地图"，让此后每节课的每个模块都能挂到你脑中的固定位置—— 以后遇到 RAG 问题，第一反应应该是"这是哪一层的问题"，而不是"换哪个模型"。

课程地图上的位置：上一节 00 导览；下一节 02 清洗（三层中的 Layer 1 从这里开始）。

1.1 一句话定义

RAG = 在生成之前，把外部知识检索进 Context，再让 LLM 基于增强后的上下文回答。

普通 LLM 应用的知识固化在参数里（训练即定局），RAG 的知识在外部（可增删改查）， 模型参数一个都不动。这是它与几个近亲的本质区别：

Fine-tuning  → 知识"学进去"（改参数，成本高，适合改行为/风格）
RAG          → 知识"拿给模型看"（改外部库，成本低，适合改事实/文档）
Tool Calling → 能力"调用起来"（API/计算器/搜索）
Memory       → 信息"存下来以后再找"（对话历史、偏好）

判断口径：要改"模型知道什么"用 RAG；要改"模型怎么说话"才考虑 Fine-tuning。

1.2 三层心智模型（现代 RAG 的骨架）

┌─────────────────────────────────────────────────────────┐
│ Layer 1  Knowledge Engineering      知识怎么组织？        │
│          清洗 / 解析 / Chunk / 摘要 / 实体关系 / 增量更新    │
├─────────────────────────────────────────────────────────┤
│ Layer 2  Retrieval Engineering      需要时怎么找到？       │
│          Dense + BM25 + RRF + Rerank + Metadata Filter    │
├─────────────────────────────────────────────────────────┤
│ Layer 3  Context / Agent Engineering 找到后怎么用好？      │
│          预算装填 / 排序 / 引用 / 拒答 / 查询改写 / Agent    │
└─────────────────────────────────────────────────────────┘
                    全部串起来 → Eval（评测不是装饰，是地基）

把课程内容挂上去：

层 课程 常见病症（用来反查层）
Layer 1 第 2（清洗）、3（切分）、9（元数据/版本）、11（树/图） 检索回来的块本身是脏的、碎的、错的章
Layer 2 第 4（向量）、5（BM25）、6（融合）、7（精排） 该命中的没进候选，或进了但排名靠后
Layer 3 第 8（改写/装填/引用/拒答）、16（控制流范式） 候选都对，答案却跑偏、编造、丢引用
Eval 第 10、13 节 ——它不解决问题，它告诉你哪层有问题

诊断问题时先定位是哪一层出的问题，不要一上来就换模型。第 10 节会把这张表 细化成 8 步排障清单。

1.3 本课程的流水线（每一站对应的代码与行号）

下面是数据从磁盘到答案的完整路径，右侧是首次出现的课程。每一站的输入输出 都是同一种形状——这一点是全课最重要的设计：

data/corpus/*.md
   ↓ loader.py:27        load_dir()：1 篇 = 1 个 Document（doc_id = 文件名）   ← 第 2 节
   ↓ cleaner.py:30       clean_text()：页眉页脚 / 样板句 / 断行                ← 第 2 节
   ↓ chunker.py:96       fixed_chunks()：小节 → chunk（500 字 + 标题前缀）     ← 第 3 节
   ↓ embedder.py:59      embed_batch()：BGE-M3 → 1024 维（带磁盘缓存）        ← 第 4 节
   ↓ vector_store.py:30  dense_search()：pgvector HNSW，余弦 Top-K（取最相似的 K 条） ← 第 4 节
   ↓ bm25.py:54          bm25_search()：jieba + BM25Okapi 稀疏一路             ← 第 5 节
   ↓ hybrid.py:22        rrf_fuse()：只用名次融合两路                          ← 第 6 节
   ↓ reranker.py:32      SiliconFlowReranker.rerank()：Cross-Encoder 精排      ← 第 7 节
   ↓ query_rewrite.py:15 三种改写（rewrite / multi_query / HyDE）              ← 第 8 节
   ↓ context_builder.py:27 build_context()：预算 / 去重 / 排序 / 引用编号      ← 第 8 节
   ↓ llm.py:32           DeepSeekLLM.chat()：带引用回答，资料不足要拒答        ← 第 8 节
   ↓ evaluate.py:135     run_eval()：Recall@K / MRR / 噪声率 / 拒答率          ← 第 10 节

[!NOTE] 关于行号 行号对应当前仓库快照，日后代码改动会有 ±几行的漂移——以函数名为准，行号只是 帮你快速定位。查最新位置：grep -n "def dense_search" playground/retrieve/vector_store.py。

为什么形状统一这么重要？看 playground/retrieve/vector_store.py:14-27 的 Hit 数据类（Python 的 @dataclass：只声明字段、自动生成构造函数的"结构体"） ——它就是流水线的"通货"：

@dataclass
class Hit:
    doc_id: str          # 来自哪篇文档
    chunk_id: str        # doc_id::strategy::chunk_index，全局唯一
    strategy: str        # 哪个索引版本
    chunk_index: int
    content: str         # 块正文（送给 LLM 的就是它）
    section_path: str    # "H1 > H2 > H3"，第 3 节的主角
    score: float         # 各阶段语义不同：相似度/BM25 分/RRF 分/rerank 分
    source: str = ""     # dense / bm25 / fused / rerank ...（可观测的钥匙）
    parent_id: str | None = None    # 第 10 节 Parent-Child 用
    rank_in_stage: int = 0
    meta: dict = field(default_factory=dict)

因为每层都吃 Hit 吐 Hit，才可能做到两件事：① 任何一层可以单独替换或 消融——消融（ablation）指"固定其他部分、只动一个部件，量出这个部件值多少分"， 本课程所有"XX 消融实验"（第 2 节清洗消融、第 3 节切分消融）都是这个套路 （第 6 节换融合方式、第 7 节开关精排，上层代码一行不改）；② Playground 能把 每层中间结果原样画出来。可观测不是加了日志，而是类型设计的红利。

1.4 编排者：rag.py 如何把积木装起来

playground/rag.py 是所有积木的装配车间，值得现在就通读一遍（全文 213 行）：

  • PipelineOptions（rag.py:30-71）：一个纯配置对象。检索器选哪路 （retriever）、开不开精排（use_rerank）、用哪种改写（rewrite）、 哪个索引版本（strategy）……第 2-10 节的所有"实验方案"，本质上就是 这组开关的不同取值组合。describe()（rag.py:44）把配置变成人话标签， 实验报告里的方案名都来自它。
  • RAGPipeline.retrieve()（rag.py:111-183）：改写 → 多路召回 → 融合 → （Parent-Child）→ 精排，五步与上面流水线一一对应（召回：从全库把可能 相关的候选捞出来；融合：把多路结果合并成一个名单，第 6 节）。
  • RAGPipeline.answer()（rag.py:186-209）：在 retrieve 之上追加 Context 装填 + LLM 生成，产出 Trace 数据类（rag.py:87-103）—— Playground 右侧整面板画的都是它。

1.5 为什么评测要先于优化

计划书里最重要的一条原则：先金标，后改进。没有固定测试集时，你改了检索器、 换切块大小、加了 rerank，全靠"感觉好像好一点"来判断——人的感觉在 A/B 对比里 （同一批题跑两套配置、只看数字差异）极不可靠。所以本课程第 1 件事就是冻住金标集 （data/eval/questions.json， 30 题 = 23 可回答 + 7 不可回答；v1 冻的是 25 题，v2 加厚时增补并重新全量跑过）：

  • 23 道可回答题按题型分 7 类：fact 6、symbol 3、semantic 5、 near_confusion 4、multi_doc 1、cross_chapter 2、global 2—— 题型字段存在 Question.type（evaluate.py:21-36），实验报告按它分题型统计；
  • 7 道不可回答题：问 AVX10、NEON、Intel 18A、RISC-V RVV、3D V-Cache、 APX、CXL——语料里故意没有这些内容，考察系统敢不敢说"不知道"。

[!TIP] 不可回答题是初学者最容易漏的。一个只会"一本正经编答案"的 RAG， 检索做得再好也是负资产。第 10 节会给"拒答率"一个正式的指标定义。

金标怎么写的？看一题实例（文件就是 JSON 格式——形如 {"键": "值"} 的通用 结构化数据写法；evaluate.py:30 的 from_dict 就是读它）：

{ "question": "SSE4.2 新增的字符串处理指令集缩写是什么？",
  "type": "symbol", "gold_doc": "sse", "keywords": ["STTNI"] }

三个字段各喂一个指标：gold_doc 喂 Recall/MRR（文档级），keywords 喂 kw_hit/noise（块级），type 喂分题型统计——第 10 节展开。

指标速查：从第 2 节起每张实验表都用它，先学会"读"

正式定义与代码实现在第 10 节，这里先用一个玩具例子把三个最重要的数字读明白。 设某题的正确答案在文档 avx512 里，检索系统返回的 Top-5 文档依次是： cache, avx512, sse, cpu-faq, avx：

指标 白话定义 本例的值
Recall@5 正确答案的文档进没进前 5 名（进了记 1，没进记 0） 1（avx512 排第 2）
MRR@5 排得有多靠前：按 1/名次给分（第 1 名 1 分、第 2 名 0.5 分、第 5 名 0.2 分，没进前 5 记 0），再对全部题目取平均 1/2 = 0.5
noise@5 前 5 名里"凑数的"占多少（越低越好，与上面两个相反） 4/5 = 0.8
  • Recall 管"捞没捞到"，MRR 管"捞到的排得靠不靠前"——两个必须都看： 只看 Recall 的话，把正确文档排第 5 的系统和排第 1 的系统得分完全一样；
  • kw_hit@K / noise@K 是块级指标（Top-K 个块里有没有真含答案关键词的块 / 凑数块占比）。16 篇文档的小语料上文档级指标很快饱和（正确文档几乎总能进前 5）， 区分方案好坏要靠块级指标和逐题对比（第 10 节细讲）；
  • 拒答率：对"资料里根本没有答案"的题，系统敢不敢说不知道——上面那 7 道 不可回答题考察的就是它（第 8 节的实现、第 10 节的定义）。

[!TIP] 读后面实验表的最小装备 每张实验表都这样读：先看 Recall（捞没捞到）→ 再看 MRR（排得靠不靠前）→ 最后看 noise（塞进来的有多少凑数的）。表头标注的"口径"指"基于哪套金标题 + 哪个索引版本"——两套口径的数字不能混着比（1.7 节细说）。

1.6 如何运行

本节不需要跑任何新东西——但建议你现在就把评测基线跑出来，后面每节课改完 都回来对比：

# 检索层快速评测（5 方案 × 30 题，秒级，只算检索不算生成）
python -m scripts.run_eval
#    输出 experiments/exp1_retrievers.md + .json

# 或者不跑命令，直接开网站点 /eval 页 → "运行快速评测"按钮
python -m course.app

run_eval.py:39 的 main() 固定跑 6 组实验（exp1 检索器对比、exp2 清洗、exp3 切分、 exp4 改写、exp5 Parent-Child、exp6 拒答），每组内部的方案组合见脚本注释—— 后面第 2-10 节实验表里的所有数字都来自这一个命令，想验证任何一张表， 重跑它即可。

1.7 注意事项

  • 金标两套口径：v1 实验（exp1-exp6 初版）基于 20 可回答题，MRR 数字如 0.917/0.887/0.779；v2 重跑（30 题）数字如 0.928/0.880/0.808。两套都真实， 课程引用时会注明口径；你自己的实验永远要写清"基于哪套题、哪个 strategy"。
  • 单测数字同理：v2 早期是 12 个，KB 加厚后 24 个，v3 修 patch 后 34 个（第 13 节讲怎么写）。
  • 结论顺序别搞反：先有金标（本节），再谈优化（第 2 节起）。

1.8 动手练习

  1. 打开 Playground，提问"AVX-512 的掩码寄存器有几个？"，对照 1.3 的流水线表， 数一数 Trace 经过了几层、每层对应哪个函数；
  2. 再问一道不可回答题"AMD 的 3D V-Cache 技术是怎么实现的？"，看它如何拒答 （真实回答见 exp6 报告：全部正确拒答）；
  3. 打开 data/eval/questions.json，按 type 数一遍——验证 23 + 7 = 30；
  4. 思考：如果把这 7 道不可回答题从测试集里删掉，你会错过什么能力？ （提示：检索指标一个都不会变——这正是它们容易被删的原因。）

1.9 加厚（v3）：三个高频质疑——把边界想清楚

质疑一："上下文窗口都百万 token 了，还要 RAG 吗？"

这是 2026 年最常被问的问题。答案：长上下文解决的是"装得下"，RAG 解决的是 "找得到、信得过"——两者互补而非替代：

维度 全量塞长上下文 RAG（检索后装填）
每次提问的成本 每问都要为全库 token 付费 只为命中的几块付费
延迟 长输入 prefill 慢 检索毫秒级 + 短上下文
新鲜度 改资料要重算重传 改库即生效（第 9 节增量更新）
权限与多租户 谁能看什么难控制 检索层先过滤（第 9 节）
溯源 模型只说"在上面某处" [n] 编号引用到块（第 8 节）
评测 出错难归因 金标 + 指标逐层定位（第 10 节）

工程上的合流做法：检索负责"选"，长窗口负责"装"——召回更多候选塞进长窗口 （把第 8 节的预算调大），取舍从"能不能装下"变成"塞多少性价比最高"。

质疑二："换个更强的模型，是不是就不用做检索工程了？"

模型变强改善的是"读懂资料、表达答案"（Layer 3 的后半段）；但该找哪几块、 找没找到、敢不敢拒答、能不能溯源——这些 Layer 1/2 的问题不随模型变强而消失。 第 10 节 8 步排障清单里，只有第 7 步之后才轮到"模型能力"背锅。

质疑三："RAG 的核心是不是向量数据库？"

1.2 开篇回答过：不是。向量检索只是 Layer 2 的一路（第 4 节），BM25（第 5 节） 与融合（第 6 节）同样是一等公民；而决定答案质量上限的经常是 Layer 1 的清洗 与切分——第 2 节的实验里，清洗不花一分钱 API 就把 BM25 救回 0.06 个 MRR。 把"RAG = 向量库"当心智模型，会让你在检索质量差时只想着换向量库，而真正该改 的是数据和切分。
