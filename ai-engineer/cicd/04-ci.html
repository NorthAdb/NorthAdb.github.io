4. 失败怎么读、怎么进 CI

动手 Demo：demos/04-ci
cd demos/04-ci && pytest tests/smoke -m smoke -v --junitxml=report-mr.xml

读本地失败（对接 CI 日志）

失败时重点看三块：

  1. 哪条用例：FAILED tests/smoke/test_x.py::test_y
  2. 断言对比：左右值分别是什么
  3. 栈顶业务帧：是代码 bug 还是测试环境/路径问题

常见非业务失败（CI 里也多）：

现象 可能原因
ModuleNotFoundError 依赖没装、PYTHONPATH/包结构不对
收集阶段 0 tests 路径错、命名不符合发现规则
本地绿 CI 红 环境差异、缺环境变量、Docker 与本机不一致

挂进 GitLab Job（概念，Day 2 展开）

mr_smoke:
  stage: test
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script:
    - pip install -r requirements.txt
    - pytest tests/smoke -m smoke -v --junitxml=report-mr.xml
  artifacts:
    when: always
    paths:
      - report-mr.xml
    reports:
      junit: report-mr.xml

gate1_critical:
  stage: test
  rules:
    - if: $CI_COMMIT_BRANCH == "main" && $CI_PIPELINE_SOURCE == "push"
  script:
    - pip install -r requirements.txt
    - pytest tests/gate1 -m gate1 -v --junitxml=report-gate1.xml

要点：

  • 不同 Job + 不同 rules + 不同 pytest 参数 = 多门禁
  • --junitxml=...：把结果留给 GitLab 展示 / artifacts 归档
  • pip install 可配合 cache 加速（Day 2 学 cache）

退出码（面试一句）

「pytest 有失败就返回非 0，GitLab 认为 Job failed，门禁不通过。」

和你岗位的关系

维护 CI 时你常做的事：

  • 改 Job 里的 pytest 命令（路径、-m、超时）
  • 根据日志判断是用例红了还是环境红了
  • 控制「重 case 不要误挂到 MR」——靠 rules + marker/目录

所以 pytest 是 CI 脚本里的业务执行器，不是可选项。
