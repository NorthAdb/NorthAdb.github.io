1. GitLab CI 核心组件

仓库事件（push / MR / tag / schedule） → GitLab 读 .gitlab-ci.yml → 按 rules 选出要跑的 Job → 派给空闲 Runner → Runner 用执行器跑 script → 回传日…

AI AI Agent 面试宝典 CI/CD 面试突击 阅读约 2 分钟
On this page

三角关系（心里有图）

组件 是什么 谁管
.gitlab-ci.yml 流水线配置（声明要跑什么） 仓库内，跟代码一起评审
GitLab（协调端） 收到事件、解析 yml、排队 Job GitLab Server
GitLab Runner 真正执行 Job 脚本的「工人」 运维 / 平台组注册 
仓库事件（push / MR / tag / schedule）
  → GitLab 读 .gitlab-ci.yml
  → 按 rules 选出要跑的 Job
  → 派给空闲 Runner
  → Runner 用执行器跑 script
  → 回传日志 / artifacts / 成功失败

.gitlab-ci.yml：代码即流水线

  • 放在仓库根目录（或项目设置里指定路径）
  • 改流水线 = 改代码，走 MR 评审，可追溯
  • 面试说法：「我们流水线配置和业务代码同仓管理，变更可审计。」

Runner 类型

类型 含义 场景
共享 Runner 多项目共用 小团队、通用构建
私有 Runner 绑定某项目/组 内网、特殊工具链、安全隔离

面试追问「为什么要私有 Runner」：

  • 需要访问内网制品库 / 编译服务器
  • 需要固定工具链（交叉编译、专用 SDK）
  • 安全：凭证不出共享池

Runner 和 Docker 什么区别？

Runner Docker
是什么 接活的工人进程（GitLab Runner） 怎么跑 Job 的一种方式 / 容器环境
干什么 向 GitLab 报到、领 Job、回报日志和结果 按 image: 起容器，在容器里执行 script
类比 工厂里的工人 工人进无尘车间干活（车间 = 容器）

关系（最常见）：

GitLab 派 Job
  → Runner（工人）接到
  → Runner 用 Docker 执行器起容器（image: xxx）
  → 容器里跑 pytest / 编译
  → 容器销毁，Runner 继续接下一个 Job
  • 一台机器上通常：装一个 Runner + 装 Docker Engine
  • Runner 也可以不用 Docker（Shell 执行器直接在宿主机跑）——环境易脏，生产少用
  • yml 里的 image: 是 Docker 镜像；tags: 是选哪个 Runner

口述：

「Runner 负责接任务；Docker 负责提供干净的执行环境。我们 Runner 配 Docker 执行器，每个 Job 起一个容器跑脚本。」

执行器（重点：Docker）

执行器 特点 面试怎么说
Shell 直接在 Runner 宿主机跑 简单，但环境易脏、难复现
Docker 每个 Job 起一个干净容器 统一环境、不污染宿主机、易封装工具链

Docker 执行器优势（大纲必背）

  1. 干净、统一的构建环境
  2. 方便封装各类编译工具链
  3. 不污染宿主机

和 Day 1 名词对齐

Day 1 名词 在 GitLab 里
Pipeline 一次触发产生的整条流水线
Stage yml 里 stages: 定义的阶段
Job yml 里一个命名块（如 mr_smoke:）
Step Job 的 script: 里每一行命令
Runner / Agent GitLab Runner
Artifact artifacts: 归档的文件
Webhook 仓库事件通知 GitLab 开 Pipeline（GitLab 常内建集成，不必手配）

易混

混淆 纠正
Runner = GitLab Server Runner 是工人；Server 是调度
有 yml 就会跑 还要有可用 Runner + rules 匹配
Docker 执行器 = 业务要上 K8s 只是 Job 运行方式，不等于部署平台
