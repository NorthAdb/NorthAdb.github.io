推荐阅读顺序

分四条轨道，可并行，但每条 internally 按序。

轨道 1：使用者（1–2 天）

  1. 什么是-Pi.md
  2. 本地跑起来.md
  3. 官方 docs/quickstart.md → usage.md
  4. 四种运行模式.md
  5. 会话与上下文.md
  6. 官方 providers.md（只看你用的厂商）

产出：能在真实项目里用 Pi 改代码。

轨道 2：扩展作者（3–7 天）

  1. 设计哲学.md + 刻意省略.md
  2. 扩展面总览.md
  3. 官方 skills.md → 自己写一个 skill
  4. 官方 extensions.md 前几章 + examples/extensions/* 三个例子
  5. 如何扩展而不改内核.md
  6. 官方 packages.md → 打一个本地包

产出：可安装的个人/团队工作流包。

轨道 3：嵌入与集成（1–2 周）

  1. Coding-Agent-栈.md
  2. examples/sdk/01 → 12
  3. 官方 sdk.md、rpc.md、json.md
  4. SDK与进程集成.md
  5. 读 core/agent-session.ts 的公开方法列表（略读实现）

产出：一个最小宿主（CLI 或脚本）驱动 Session。

轨道 4：运行时与内核（持续）

  1. 包地图与依赖.md
  2. packages/agent/README.md 全文
  3. Agent-运行时循环.md
  4. 源码 agent-loop.ts、agent.ts、types.ts
  5. packages/ai/README.md 前半 + 一个 provider 实现略读
  6. Harness北星.md，分清日常 JSONL 会话和 packages/durable
  7. 只有要做可恢复运行时，再读 packages/durable/README.md。不要找 packages/agent/docs/，那个目录已经不在

产出：能解释一次 tool call 从 TUI 到 provider 的完整路径。

阅读纪律

  • 文档 → 例子 → 源码，不要反着来
  • 每次只追一个问题（例如「steer 什么时候插入」）
  • 画序列图；对照真实 /debug 日志
  • 改代码前先写/跑最小测试（suite + faux）
