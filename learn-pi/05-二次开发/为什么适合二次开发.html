为什么适合二次开发

「适合二次开发」在这里指：以可维护的方式改行为、做产品、做分发，而不是靠长期脏 fork。

1. 扩展优先于改内核

官方明确目标：不 fork、不改 internals，也能适配工作流。
仓库用 examples 把「别人内置的功能」演示成扩展：subagent、plan-mode、permission、自定义 provider…

二次开发默认路径：

需求 → 找例子 → 写成 extension/skill → （可选）打成 package → 安装到环境

只有当扩展 API 表达不了时，才考虑 PR 上游或 fork 深改。

2. 清晰的包边界

pi-ai / pi-agent-core / pi-tui / pi-coding-agent 可独立依赖。

  • 只要统一 LLM？用 pi-ai
  • 只要循环不要 TUI？用 pi-agent-core
  • 只要终端组件？用 pi-tui
  • 只要 MCP 客户端？用 pi-mcp（独立成包，不依赖 Pi）
  • 只要"沙箱里跑 JS 调工具"？用 pi-codemode（唯一能力是调用注入的工具）
  • 要完整编码 Agent？用 pi-coding-agent

二次开发不必吞下整个 CLI。

3. 多种宿主形态

TUI / print / JSON / RPC / SDK —— 同一 Session 内核。
做 IDE 插件、Web 控制台、Slack 机器人（另见 pi-chat）、内部平台，都有落点。

4. 可换皮配置

piConfig.name / configDir / bin 支持 fork 换品牌与目录，而不必改遍源码。见 Fork与换皮.md。

5. 会话与运行时分离

会话日志可持久化；工具与扩展是恢复时重绑的依赖。
意味着你可以：

  • 换沙箱实现仍打开旧会话
  • 在评测里替换工具
  • 在企业环境注入审计工具而不改历史格式

6. 工程纪律利于长期维护

钉依赖、shrinkwrap、ignore-scripts、check 脚本、逐文件提交文化（本仓库 AGENTS）——二次开发团队不容易「依赖地狱里改 Agent」。

7. 文档 + 例子 + 自解释

  • docs 全
  • examples 多
  • 可让 Agent 读自家 docs 生成扩展

新人 onboarding 成本显著低于「只有源码没有扩展模型」的项目。

不适合的二次开发预期

  • 期望内核自带企业级 ACL / 审批流（要自建）
  • 期望 MCP 自动成为模型的可见工具（内置了，但默认 exposure: "codemode"，要改成 direct 或 deferred 才会进模型声明）
  • 期望不学 TypeScript 就能做深扩展

结论

Pi 适合二次开发，是因为把「产品差异点」放在扩展面与宿主面，把「稳定协议」放在 ai / agent / session。
你改的是自己的层；上游进化时，扩展 API 与会话格式是缓冲带。
