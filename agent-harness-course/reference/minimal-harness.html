从 0 手写 Minimal Pi-like Agent Harness

不看任何 Agent 的宣传页，从一个空白目录开始，写出九个组件的最小可用实现。本页是设计卷：给出需求、接口、数据结构、流程与测试标准；代码骨架只给到"接口级伪代码"，具体实现必须你自己写——写不下去时先回对应课程看 Pi 的真实做法。

总目标：两周内，你的 Harness 能完成这句话——"在 ./demo 项目里修复 util.py 的 bug 并跑通 pytest"，全程无人工干预，且崩溃后可 resume。

第 0 步 · 需求清单（先写下来，做完逐条打勾）

  1. LLM Provider：至少 1 家真实 API + 1 家 mock（测试用），可切换
  2. Agent Loop：toolCall 驱动；无 toolCall 退出；工具异常 → isError 消息回模型
  3. Tool Registry：注册 ≥3 个工具（read / write / shell）；名称冲突报错
  4. Tool Execution：参数 JSON Schema 校验；输出截断（2000 行/50KB）；错误不抛出
  5. Context Builder：systemPrompt（分 3 段：preamble/tools/rules）+ messages + tools 声明
  6. Session Store：JSONL append-only；条目含 id/parentId；支持从文件恢复
  7. Compaction：tokens > 窗口 − reserve 时触发；切点不落 toolResult；结构化摘要
  8. Skill Loader：扫 SKILL.md 目录 → 提示词只注入 name/description/location
  9. Extension Hook：至少 2 个事件（before_llm_request 可改 context；tool_call 可 block）

第 3 步 · 运行流程（第 2 课的循环 + 第 6 课的压缩检查）

def agent_loop(context, tools, stream_fn, hooks, session):
    while True:
        if should_compact(len_tokens(context), WINDOW, reserve=4096):
            compact(session, context, keep_recent=3000)     # 第 6 课
        hooks.emit("before_llm_request", context)           # 扩展可改写
        msg = stream_fn(MODEL, context)                     # 失败→error 消息
        calls = [c for c in msg.blocks if c.type == "toolCall"]
        if not calls and not session.pending():
            session.append(msg); return                     # agent_end
        for call in calls:
            verdict = hooks.emit("tool_call", call)         # 可 block
            if verdict.blocked:
                result = error_result(verdict.reason)
            elif not validate(call.args, schema_of(call.name)):
                result = error_result("参数校验失败")
            else:
                try:    result = tools[call.name].execute(call.id, call.args)
                except Exception as e: result = error_result(str(e))
            result = truncate(result, 2000, 50*1024)
            tm = tool_result_message(call, result)          # isError 也在内
            context.messages.append(tm); session.append(tm)

第 4 步 · 最小实现顺序（严格按依赖排序，每步可运行）

  1. Day 1–2 · Session Store：append/restore/projection（30 行）——先有记忆再谈循环
  2. Day 2–3 · LLM Provider：mock 先行（返回写死的 toolCall），真 API 后接
  3. Day 3–5 · Agent Loop + Tool Execution：read/write/shell 三工具；mock 测试全绿
  4. Day 5–6 · Context Builder：3 段 systemPrompt + tools 声明 + 投影喂入
  5. Day 7 · Extension Hook：before_llm_request / tool_call 两个 emit 点
  6. Day 8–9 · Compaction：mock 超长会话触发；摘要用真 API
  7. Day 10 · Skill Loader：目录扫描 + XML 菜单注入 + 手工验证模型会去 read

第 6 步 · 扩展方向（做完基础版再选做）

  • 流式输出：增量渲染——Pi 的 AssistantMessageEvent（ai/src/types.ts:769）

  • 提示词 sections diff：只发变更段，保 prompt cache

自查清单（对照 Pi 的灵魂拷问）

  1. 你的 toolCall 是不是建议而非执行？（模型没有执行权）
  2. 工具错误是否回给模型而不是抛给用户？
  3. 历史是否只增不删，投影才可变？
  4. 切点是否绝不落在 toolResult 上？
  5. 技能是否只注入目录？
  6. 扩展能否在不碰你 Core 代码的前提下拦截一次调用？
  7. 进程被 kill 后，你能在 1 分钟内恢复到崩溃前的状态吗？

七问全"是"——恭喜，你写出的已是一个 Pi-like Harness，而不是一个套壳聊天机器人。把它与 Diagram 01 对照着讲给下一个人听，就是你毕业的时刻。
