从 Pi 抽象出通用 Agent Harness

现在把 Pi 的名字从图上拿掉。哪些部件是任何 Agent Harness 都必需的？哪些是 Coding Agent 特有的？哪些纯属 Pi 的设计口味？这一课给你一张"设计空白目录"时可以 starting 的图。

本课核心问题：Pi 做的事情，哪些属于所有 Agent Harness 都需要？哪些是 Coding Agent 特有？哪些是 Pi 自己的设计选择？

一、这张图要解决什么问题

前 11 课的所有结论都带着"Pi"的标签。要能"不看任何现成 Agent、从空白目录自己设计"，就必须把观察升级为模型——同时诚实标注每块的证据等级，不为图的完整而虚构。

二、如何从图上读懂（按三个证据层级分箱）

第一箱：所有 Harness 都需要【推断＋业界共识】。Agent Loop（没有循环就没有多步）；Context Management（模型失忆，必须有人喂）；Tool Runtime（注册/校验/执行）；State/Session（可恢复性）；Interfaces（交互/自动化/嵌入三形态）；Observability（图上未画——Pi 的 AgentEvent 事件流就是它的雏形【源码】，完整的 trace 方案各家仍在演化）。

第二箱：Coding Agent 特有【推断】。文件读写/Shell 执行的工具组与"工作区"概念；项目指令发现（AGENTS.md 一类）；以仓库/目录为中心组织会话。这些放到"客服 Agent"上就不成立——领域决定了工具集。

第三箱：Pi 自己的设计选择【源码】。同样必备的部件，Pi 做了有个性取舍：① 日常 CLI 用 JSONL append-only 会话树 + leafId 分支（session-manager.ts）。1.0 起实验包 pi-durable 自己带 SQLite 和 JSONL，并且先提交再展示；那不是 pi 打开会话时走的路径。② 无子代理编排、无内置权限系统（docs/security.md）。MCP 自 0.99 起以可替换的内置扩展接入，1.0.2 仍如此，默认启用的 Core 工具仍是 read / bash / edit / write（第 15 课）。③ 扩展面厚而循环包极薄——1.0 把实验性 AgentHarness 从 packages/agent 拿掉之后，这个包只剩循环。④ TUI 为自研差分渲染框架（pi-tui 零业务依赖），1.0 起默认全屏。共性是必需品，个性是竞争力——审阅任何新 Agent 时先分这两箱，就不会被宣传页牵着走。

三、本课七问（针对"抽象方法"本身）

  1. 解决什么问题？把对单一产品的理解升维成可迁移的设计模型。
  2. 没有它会怎样？每见一个新 Agent 都要从零理解，且容易被营销语言误导。
  3. 输入是什么？第 1–11 课的全部源码级观察。
  4. 输出是什么？一张分箱标注的通用架构图 + 三箱判定清单。
  5. 由谁控制？你自己——这张图之后，评判标准在你手里。
  6. 和前一概念的关系？第 11 课的总时序提供了"运行时证据"，本课把它静态化。
  7. 源码依据？本课每个"Pi 选择"都已在对应课程给出文件级证据（见各课映射表）。
