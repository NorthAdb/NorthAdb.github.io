Pi vs Claude Code vs Codex vs OpenCode

用第 12 课的三箱模型去检验另外三个 Agent。先声明证据规则：Pi 的每一格都有本仓库源码背书；另外三家的核心不完全开源，只能以公开文档/公开仓库资料为准——证据等级整体降一级，且截至 2026 年 9 月，请以最新官方文档复核。

本课核心问题：不同 Agent 在"哪些事情应该进入 Core，哪些留给 Harness / Extension"上的设计差异发生在哪些层？（不做谁最好的排名）

二、差异真正的战场：Core vs Harness 的划线

把上表压缩成一句话：四家在"必需品"上高度趋同（Loop/Context/Session/压缩/工具），真正的分歧在三条划线上——

划线一：安全放哪？Pi 放环境（容器）；Codex 把 OS 沙箱内置进产品；Claude Code 用产品内权限模式。同一问题，三个答案，决定了三家的信任模型与目标用户。

划线二：生态协议放哪？MCP 是"工具生态"的行业协议。0.99 之前 Pi 完全不实现，是四家里最显眼的分歧；0.99 起 Pi 把它接成了可替换的内置扩展——协议进来了，Core 工具表没有变，工具默认还不声明给模型（exposure: "codemode"）。其他三家默认把 MCP 工具直接暴露给模型。分歧从"接不接"移到了"接了之后占不占上下文"——这是比"进不进 Core"更细的一层价值排序。详见第 15 课。

划线三：多代理放哪？Claude Code 把子代理做进产品；Pi 认为扩展 + 多会话（runtime 的 fork/switch）已够。Subagent 本质上是"并发与隔离"问题——它可以长在 Runtime 里，也可以长在 Harness 编排层，还可以完全交给用户 shell。

用第 12 课的三箱法看：三箱（通用必需）四家几乎一致；二箱（Coding 特有）趋同；所有争执都发生在三箱（设计选择）——而三箱的争执，恰恰是"Minimal Core 划在哪条线"的哲学之争。

三、七问（针对"比较方法"）

  1. 解决什么问题？防止把"某家的选择"当成"行业的必然"。
  2. 没有它会怎样？学完 Pi 就以为 Agent = Pi，做设计时盲目照抄。
  3. 输入是什么？同一张比较表（统一维度、分级证据）。
  4. 输出是什么？三条"划线"级的洞察，而非排名。
  5. 由谁控制？你——比较的结论要能落到你自己的 Minimal Harness 设计决策上。
  6. 和前一概念的关系？第 12 课的三箱模型是本表的分组器。
  7. 证据？Pi 列全为源码；他列全为公开资料（2026-09 截止，需复核）。
