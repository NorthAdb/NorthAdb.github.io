Same Runtime, Multiple Interfaces

为什么同一个 Agent 能在终端里交互、在 CI 里一键跑、在别的进程里被遥控？答案不是运气，而是接口层与 Runtime 的彻底解耦。这一课看 Pi 怎么做到"四种入口，一个会话"。

本课核心问题：为什么一个好的 Agent Harness 不应该把 TUI、Agent Runtime、Agent State 写死在一起？Interactive / Automation / Embedding 三种形态分别意味着什么？

一、这张图要解决什么问题

很多 Agent 的第一批"架构债"就是把循环和 UI 写在一起：想在服务器上跑一次批处理？想给自己的 Web 应用接一个后端 Agent？都得重写。这张图展示解耦后的样子：入口层（TUI/print/RPC/SDK）各走各的，全部汇入同一个 AgentSessionRuntime。

二、如何从图上读懂 Pi

源码四种模式是一次分发，不是四套代码。main.ts:111-122 的 resolveAppMode：RPC/JSON 由参数指定，管道输入自动降级为 print，否则 interactive。三种 CLI 模式全部接收同一个 AgentSessionRuntime（agent-session-runtime.ts:74，提供 newSession/fork/switchSession 与 setRebindSession）。

源码SDK 绕过 CLI 直接组装。sdk.ts:175 的 createAgentSession()：组合 Agent（agent-core）+ streamFn（pi-ai）+ SessionManager + 扩展——这是"把 Pi 嵌进你的 Node 程序"的入口。更彻底的是 RPC 模式（modes/rpc/rpc-mode.ts，stdio 上的 JSON 行协议），专为"Agent 在别的进程、UI 在你的应用"设计；仓库还有一套实验性的二进制协议（protocol/server/client 包，CBOR 分帧 + Chord 服务语义）。

源码事件是公共货币。第 2 课的 10 种 AgentEvent 从循环里发出，AgentSession 转发（agent-session.ts:437），TUI 订阅渲染（interactive-mode.ts:3272），print 模式把它们打到 stdout，RPC 把它们编码成 JSON 行。三种形态 = 同一个事件流的三种消费者。连扩展的 UI 请求都经 extension_ui_request/response 在 RPC 下透传。

三、新概念的七问：接口层解耦

  1. 解决什么问题？同一套 Agent 能力，服务交互、自动化、嵌入三种完全不同的使用形态。
  2. 没有它会怎样？循环和 UI 焊死：没有终端就没有 Agent；想嵌入就得重写。
  3. 输入是什么？用户按键 / 命令行参数 / RPC 请求 / SDK 方法调用。
  4. 输出是什么？渲染的界面 / stdout 文本或 JSON 事件 / 进程间消息 / SDK 回调。
  5. 由谁控制？main.ts 分发；每种模式独立消费事件；Runtime 与 State 始终居中。
  6. 和前一概念的关系？安全边界（第 9 课）在环境层，接口边界在进程层——Pi 用同样的"分层"思路对待信任与交互。
  7. Pi 在源码哪里实现？源码main.ts / modes/* / core/sdk.ts / core/agent-session-runtime.ts。
