为什么 LLM 不是 Agent

从一个空白目录到"Pi 这样的编码智能体"，中间隔着一整层工程。这一课我们先看清这层工程的全貌，并回答整个课程的第一块基石：LLM 和 Agent 之间，到底差了什么。

本课核心问题：Pi 作为一个 Coding Agent Harness，核心组件有哪些？这些组件之间如何连接？——以及最根本的：为什么 LLM 本身不是 Agent？

一、这张图要解决什么问题

你大概已经用过各种 Coding Agent：输入一句话，它自己读代码、改文件、跑测试。直觉上"是模型在干活"。这张图要打破这个直觉：把 Pi 拆开，看清里面的每一个部件——哪些是 LLM，哪些不是，谁在指挥谁。不看清这个，后面 13 课的所有机制都没有挂靠点。

二、如何从图上读懂 Pi

源码图上有三个颜色/边界层次，对应 Pi 仓库的真实分层：

外层是外部系统：你和你的操作系统（Shell、文件系统）。Harness 能通过"工具执行"触碰 OS，但 OS 本身不归它管。

中间是产品层 Harness（pi-coding-agent）：TUI 交互界面、AgentSessionRuntime（会话宿主）、AgentSession（产品状态机）、Tool Registry（read/bash/edit/write 等工具）、Session JSONL（磁盘上的历史）、以及 Compaction·Skills·Extensions 这组服务。你日常看到的"Pi"几乎全部是这一层。

内层是 Core Runtime（pi-agent-core + pi-ai）：agentLoop() 双层 while 循环、Context 数据结构、以及 Model Provider 抽象（多家模型厂商，统一成一个 streamSimple 流式接口）。源码1.0 起 packages/agent 只剩循环、Agent 和 proxy，不再包含会话或压缩。关键证据：这一层完全不知道"编码"的存在——包里没有 read/bash/edit，这些是产品层注入进去的。另一条实验线 packages/durable 做可恢复的 Harness，日常 pi 不走它。

为什么 LLM 本身不是 Agent？因为图上粉色卡片说的三件事：LLM 只做一件事——收一份 Context，吐一段 token，请求结束即"失忆"。它不能执行工具（只能建议调用哪个工具）、不能持久化任何东西、看不到文件系统。图上所有"持久的、会做决定的、能动手的"部件，全部住在 Harness 侧。Agent = LLM + 一整套让它稳定持续安全干活的工程，这套工程就叫 Harness（线束/马具——套在 LLM 这匹"马"上的那套装备）。

三、新概念的七问：Harness

  1. 它解决什么问题？让一个"只能生成 token 的函数"变成能持续、稳定、安全完成多步任务的系统。
  2. 如果没有它会怎样？你要手动把文件内容粘贴给模型、手动把它的修改写回磁盘、手动重试每一次失败——它只是一个聊天窗口。
  3. 输入是什么？用户的自然语言任务 + 工作区环境（文件、目录、git 状态）。
  4. 输出是什么？对真实世界的副作用（改了哪些文件、跑了什么命令）+ 给用户的答复。
  5. 它由谁控制？循环和状态由 Harness 代码控制；模型只在每一步被咨询一次意见。
  6. 它和前一个概念的关系？这是课程第一个概念——它是后面一切机制（Loop、工具、会话、压缩……）的容器。
  7. Pi 在源码哪里实现？源码三层各自成包：packages/ai（模型 IO）、packages/agent（循环）、packages/coding-agent（产品组装）。实验性可恢复 Harness 在 packages/durable，与日常 CLI 分开。
