MCP 深潜：协议、上下文预算与「内置扩展」这条中间路线

第 13 课的比较表里，MCP 是 Pi 与其他三家分歧最大的一条划线。当时的答案是「Pi 零实现」。上游 0.99.0 改写了这个答案：MCP 进了 Pi，但不是作为 Core 工具——它成了一个可被第三方顶替的内置扩展，工具默认只在脚本里可见。这一课讲清协议本身、这次接入的每个决策点，以及一条可迁移的判断框架：一个协议该进 Core、进内置扩展，还是留给用户扩展？

本课核心问题：MCP 是什么？Pi 用什么方式接入了它（0.99 接入，1.0.2 仍保持）？以及最重要的——为什么答案不是「加第五个工具」，而是「加一个默认不占上下文的可替换扩展」？

一、这张图要解决什么问题

MCP（Model Context Protocol）是当前工具生态的事实协议。0.99 之前，Pi 一个字都没实现；0.99 之后，它随 Pi 一起发布，却仍然没有出现在 Core 的工具清单里。这句话同时引出三个问题：协议本身长什么样（不搞懂就没法评判取舍）？「接了但不算 Core」在源码里到底是什么形态？以及——对于你自己的 Harness——什么时候该把某个协议放进 Core？这张图把三者画在一张画布上。

二、MCP 三十分钟速成【公开资料】

公开资料以下按 Model Context Protocol 规范（modelcontextprotocol.io，spec 仍在演化，请以最新版为准）：

角色分工：Host 是嵌入 MCP Client 的应用（比如一个 Coding Agent）；Client 与 Server 保持 1:1 会话；Server 是暴露能力的服务——可以是本地子进程（stdio 传输），也可以是远端服务（Streamable HTTP 传输；旧的 SSE 传输 Pi 不支持）。底层消息全部是 JSON-RPC 2.0。

三种原语：tools（模型可调用的函数——对应第 3 课的 toolCall 机制）、resources（可读取的数据）、prompts（预置提示词模板）。连接时双方先做 capability 协商（"我有哪些工具"）。

它解决的问题：工具生态的 N×M 问题——没有协议时，M 个 Agent 要各自适配 N 个工具源；有了协议，工具作者写一次 Server，所有支持 MCP 的 Agent 都能用。这正是第 13 课"生态协议放哪条线"的背景。

三、Pi 的接入方式【源码 · 1.0.2】

源码核心事实：MCP 是内置扩展，不是 Core 工具。随 Pi 加载的扩展清单里就有它（packages/coding-agent/src/extensions/index.ts:7-14）：

export const builtInExtensions: InlineExtension[] = [
  { name: "llama.cpp", factory: llamaExtension, builtin: true },
  // Replaceable: an extension that registers `codemode`, `tool_search`, or `/mcp` … takes over.
  { name: "codemode",    factory: codemodeExtension,    replaceable: true, builtin: true },
  { name: "tool-search", factory: toolSearchExtension,  replaceable: true, builtin: true },
  { name: "mcp",         factory: mcpExtension,         replaceable: true, builtin: true },
];

三个关键词值得记：builtin（随产品发布，无需安装）、replaceable（第三方扩展可以整个顶掉它）、以及「不在 read/write/edit/bash 之列」。客户端能力本身被拆成独立包 packages/mcp（@earendil-works/pi-mcp，导出 McpClient），它不依赖 Pi，可以单独嵌进任何 Node 应用。

源码关键设计：默认不占用模型上下文。文件头（src/extensions/mcp/index.ts:1-27）把策略写得很清楚：MCP 工具注册成 mcp__<server>__<tool>，默认 exposure: "codemode"，不声明给模型，也不写进 codemode 工具清单。脚本用 searchTools() 发现、用 describeNamespace() 读服务器说明。服务器名字出现在系统提示的 mcp_servers 段，一行摘要，而不是把每个工具的 schema 塞进上下文。只有改成 direct 才会立刻声明给模型；deferred 则等 tool_search 装载后再声明。

源码两个容易看错的细节。第一，配置值 codemode 在注册成工具时，toToolExposure（extensions/mcp/tools.ts:45）把它映射成工具暴露 deferred。配置档位没有合并：codemode 激活 codemode 工具，deferred 激活 tool_search。第二，脚本里的名字把 - 换成 _，所以 mcp__my-server__x 在脚本里是 mcp__my_server__x。第一条 prompt 只等待带 direct 工具的服务器，其余在后台连接，脚本或 tool_search 真正用到时才等它们。

文档四种暴露等级的对照（packages/coding-agent/docs/mcp.md）：

exposure模型能直接看到吗典型用途
codemode（默认）不能，只能被脚本调用大多数 MCP 服务器；需要脚本组合/过滤调用时
deferred先不能，tool_search 找到后装载工具很多的服务器，但希望发现后直接调
direct能，像内置工具一样声明小而高频的工具集
hidden不能注册但保持不可达

源码配置与信任。配置来自两份 mcp.json：用户级 ~/.pi/agent/mcp.json 与受信任项目的 <project>/.pi/mcp.json（config.ts:4-5、:147-148）。项目级那份属于需要项目信任的资源，和 settings.json、extensions/ 并列（trust-manager.ts:30-39）。1.0.1 起，项目文件里一条没有 command / url 的条目，只覆盖用户级服务器的 enabled、exposure、toolExposure（config.ts:9），不必把启动命令再写一遍。能起子进程的东西仍然不能被未受信任的项目静默加载。

文档两种用法。零代码路径是配置：

pi mcp add filesystem -- npx -y @modelcontextprotocol/server-filesystem .
pi mcp list
# 会话内：/mcp 查看连接、登录、改 exposure、启停服务器

需要按环境动态注册时，才写扩展代码（src/core/extensions/types.ts:1853）：

export default (pi: ExtensionAPI) => {
  pi.registerMcpServer("jira", { url: "https://mcp.example.com/jira", exposure: "codemode" })
  pi.on("session_start", () => { for (const s of pi.getMcpServers()) { /* 观察别人注册了什么 */ } })
}

注册不是持久化的（每次加载都要重新注册），mcp.json 里的同名条目优先；另一个扩展若接管 mcp_servers_change 事件，内置实现就把连接权让出去——这正是第 8 课「替换而非叠加」的注册面语义。

四、作者的反方论证，与 Pi 的工程回答

文档作者 Mario Zechner 的博文《What if you don't need MCP at all?》（2025-11-02）给过三条批评。有趣的是，0.99 的实现几乎是逐条作答——批评没有被否定，而是被机制吸收了：

  1. 上下文开销：Playwright MCP 有 21 个工具、13.7k tokens 的描述；Chrome DevTools MCP 26 个工具、18k tokens。"That many tools will confuse your agent."
    → Pi 的答案：默认 codemode。工具 schema 不进模型声明，也不进 codemode 工具清单。系统提示的 mcp_servers 段只留服务器名字和一行摘要；模型写脚本，用 searchTools() 按需发现。这与第 7 课 skills 的渐进披露是同一个哲学，只是搬到了工具面。
  2. 可组合性："Results returned by an MCP server have to go through the agent's context to be persisted to disk or combined with other results."
    → Pi 的答案：让脚本做组合。codemode 脚本可以直接拿到结构化结果（工具的 structuredContent），在沙箱里过滤/合并后再回给模型，避免每个中间结果都进上下文。
  3. 难扩展：改一个 MCP Server 的输出格式 = 读别人的代码库；改自己的 CLI 脚本 = 改十行。
    → Pi 的答案：不强迫二选一。你可以继续用 CLI + skills；MCP 是可替换的内置扩展，不满意就连同它的语义一起换掉。

他的替代方案（四个 bash 可调的 Node 脚本 + 一份 225 tokens 的 README）核心信念是 "Bash and code are composable."。0.99 的 codemode 实际上是把这句话内化了：协议负责搬运能力，脚本负责组合能力。

五、判断框架：Core、内置扩展，还是用户扩展？

把第 12 课的三箱法与第 13 课的划线收拢，再补上 0.99 给出的新样本。依次问四个问题：

  1. 生态需求密度：你的用户每周都要接新的 Server 吗？偶发 → 写 CLI 工具或让用户装扩展；高频 → 内置才摊薄固定成本。Pi 的答案：MCP 密度已经够高，所以内置。
  2. 信任模型：每个 stdio Server 都是以你的 OS 权限运行的子进程（图上虚线框——第 9 课的边界）。内置意味着产品要定义"哪些 Server 默认可信、如何审批"。Pi 的答案：项目级配置走项目信任门禁，用户级配置由用户自己写。
  3. 上下文预算：能力进 Core 之后，它默认占不占模型上下文？这一问是 0.99 最值得学的地方：接入 ≠ 声明。MCP 接了，但默认一条工具声明都不加。
  4. 归属层级：Core 工具（不可替换，永远在）、内置扩展（随产品发布但可替换）、用户扩展/包（自己装）、外部进程（不进产品）。Pi 把 MCP 放在第二层——这是比"进不进 Core"更细的一档。

四问之后，你会得到与 Pi 相同或不同的结论——重要的是你做过这四问，而不是结论与谁一致。

六、动手：两种接入路径（选做练习）

路径 A（零代码，先试这个）：写配置 → 验证连接 → 会话内用 /mcp 看工具数量；然后对比 exposure: "codemode" 与 "direct" 两种配置下的上下文占用差异。这是本课最直观的实验。

路径 B（写代码）：写一个扩展，用 pi.registerMcpServer() 动态注册一个只在某个项目里可用的 Server，并把它设为 hidden + toolExposure 放行个别工具——体验"能力可达性"与"模型可见性"解耦的设计。

七、七问（MCP-in-Pi 专场）

  1. 解决什么问题？MCP 解决工具生态的 N×M 适配；Pi 的接入方式解决"接了协议但别撑爆上下文"。
  2. 没有它会怎样？工具生态靠 CLI + skills + 扩展（第 7/8 课）；每接一个新服务都要写桥。
  3. 输入是什么？Server 的 capability（工具/资源清单）与 JSON-RPC 调用；对模型侧则是 codemode 脚本里的 searchTools()。
  4. 输出是什么？注册进工具表（默认不声明）的 mcp__server__tool，以及脚本回给模型的精简结果。
  5. 由谁控制？协议：spec；会话：pi-mcp 客户端；加载：项目信任 + mcp.json；可见性：exposure；策略：你的扩展代码。
  6. 和前概念的关系？第 13 课"生态协议划线"的深潜 + 第 8 课注册面 + 第 9 课信任边界 + 第 7 课渐进披露的联合应用。
  7. Pi 在源码哪里实现？源码客户端在 packages/mcp/src/index.ts；内置扩展在 packages/coding-agent/src/extensions/mcp/index.ts；装配清单在 src/extensions/index.ts:7-14；扩展开口 registerMcpServer 在 src/core/extensions/types.ts:1853。

九、这张图在整个体系中的位置

第 15 课是主线之外的第一门"选修"：它不引入新的 Harness 机制，而是用已建立的 14 课框架（三箱法、注册面、信任边界、上下文预算）去消化一个真实的生态协议。它比原版多给了一样东西：一个可以观测到的历史答案——同一个项目在 0.87 说"不必等内核"，在 0.99 真的接入时，做的仍然是"不进 Core"。以后遇到任何"XX 协议该不该进 Core"的争论——A2A、OpenAPI-as-tools、浏览器协议——都照这一课的四问重演一遍。
