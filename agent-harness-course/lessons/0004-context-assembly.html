Context Assembly：模型的全部世界

模型是健忘的：每一轮请求它都只认识你这一次发给它的内容。所以"发给它什么"就是 Harness 最重要的设计决策。这一课看 Pi 如何把十几种来源拼装成一份 Context——以及为什么 Session ≠ Context。

本课核心问题：Context 是如何形成的？哪些信息静态、哪些动态、哪些按需加载？哪些内容影响 prompt cache？Context 和 Session 是一回事吗？

一、这张图要解决什么问题

打开任何一次 Agent 请求，你看到的不是"用户一句话 + 系统提示"，而是：基础提示词、环境信息、全局与项目 AGENTS.md、技能目录、整段会话投影、历史工具结果、当前请求……。这张图把这些来源按"静态/动态"分开，走一遍它们汇入 Context 的流水线。

二、如何从图上读懂 Pi

源码组装层是分块的（sections）。packages/coding-agent/src/core/system-prompt.ts:121 的 buildSystemPromptSections() 把系统提示词拆成 preamble / tools / rules / docs / addendum / project_context / skills / cwd 八段，各自独立生成、独立替换。模型看到的最终提示词 = 各段包上 XML 标签的拼接。

源码项目指令是"沿目录向上收集"的。resource-loader.ts:127-212 按候选名 AGENTS.override.md → AGENTS.md → CLAUDE.md 先读全局 ~/.pi/agent/AGENTS.md，再从 cwd 沿祖先目录向上收集——这是"项目级指令"的动态来源。

源码分块 + diff 是为 prompt cache 服务的。diffSystemPromptSections（system-prompt.ts:204）只把变化的 section 下发；静态段在前、动态段在后，配合 coding-agent 侧的 cacheWarmer 预热——上下文没变的部分命中缓存，省钱且降延迟。影响缓存的设计原则：内容稳定的大块放前面，易变的小块放后面。

Session ≠ Context。Session 是磁盘上完整的历史树（第 5 课）；Context 只是本轮送给模型的那一份投影。投影会因 compaction（第 6 课）和 context_edit 条目而与原始历史不同——历史永远在，模型看见的被精心裁剪过。

三、新概念的七问：Context Assembly

  1. 解决什么问题？在有限窗口与有限预算下，把"模型该知道的一切"按时组装好。
  2. 没有它会怎样？每次请求都是裸 prompt——项目约定、工具说明、历史一概不知。
  3. 输入是什么？静态文本、AGENTS.md、skills 目录、会话投影、tools 声明。
  4. 输出是什么？一份 { systemPrompt, messages, tools }（pi-ai 的 Context）。
  5. 由谁控制？coding-agent 的 system-prompt / resource-loader；扩展可在 before_agent_start 改写。
  6. 和前一概念的关系？第 3 课的工具声明与结果都是 Context 的组成部分。
  7. Pi 在源码哪里实现？源码system-prompt.ts（组装/diff）+ resource-loader.ts（发现）+ agent-session.ts（投影）。

五、这张图在整个体系中的位置

Context 是 Loop 的"每轮输入"，也是后面两大机制的舞台：历史从哪来（第 5 课 Session）、太长了怎么办（第 6 课 Compaction）。记住这句：Context 是"本轮送进模型的信息"，Session 是"长期保存的任务历史与状态"。
