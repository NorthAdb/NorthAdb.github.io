能力边界：Core 刻意不做安全

这一课可能是 Pi 最反直觉的设计：bash 工具执行前没有任何确认弹窗，核心里也搜不到 permission 系统。这不是疏忽，而是一个立场清晰的安全模型。我们把它拆开看。

本课核心问题：Pi 哪些权限是 Core 自带的？为什么安全边界可以（应该？）位于 Harness 外部？为什么 Tool Calling ≠ Permission System？Capability / Authorization / Sandbox 三个词差在哪？

一、这张图要解决什么问题

从 LLM 到"你的生产数据库"之间隔着几层？每一层由谁负责？把这三层混为一谈（"模型会调工具所以有权限问题"）就无法讨论安全。这张图把链路画出来，并把 Pi 实际部署的三道边界——Trust、扩展门、外部容器——标在正确的位置上。

二、如何从图上读懂 Pi

文档官方立场原话（packages/coding-agent/docs/security.md:3）："Pi can read, change, and execute files with the permissions of the account that started it, and it does not ask for approval before every tool call." 同文还明确："Project trust … does not limit what tool calls can access or affect."（Project trust 不限制工具调用的触及范围。）

源码Core 自带的安全机制只有一道：Project Trust。trust-manager.ts + main.ts:704-764：首次进入一个项目目录时，用户必须显式信任，之后该目录的 .pi/extensions、.pi/skills、.pi/settings.json 等才会被加载。它防的是供应链攻击（clone 一个恶意仓库 → 其 .pi/extensions 自动执行），不是工具行为审批。

源码工具层留了"接缝"而非"审批"。bash 工具的 BashOperations 接口（tools/bash.ts:59）注释明说"Override these to delegate command execution to remote systems (for example SSH)"；BashSpawnHook 允许扩展改写 command/cwd/env。也就是说：执行去哪是可插拔的，执行前要不要问人也是可插拔的（permission-gate 扩展）——但两者都不在 Core 里。

文档官方推荐的硬边界在容器。docs/containerization.md 给出四种隔离方案（Plain Docker / Docker Sandboxes / OpenShell / Gondolin micro-VM）与 Dockerfile 示例——把整条 LLM→Runtime→Tool→OS 链关进笼子，笼子由环境负责，不由 Harness 负责。Tool Calling ≠ Permission System：结构化的 JSON 调用解决的是"可靠地动手"，不是"该不该动手"。

三个词的辨析：Capability＝工具给了模型什么本事（read/bash/edit…）；Authorization＝动手前谁说了算（Pi Core：无人审批，启动者即授权人；想审批→扩展钩子）；Sandbox＝动手时物理上碰得到什么（OS 用户权限 / 容器 / micro-VM——全在 Harness 外部）。

三、新概念的七问：Capability / Authorization / Sandbox

  1. 解决什么问题？在"能干活"与"不闯祸"之间划一条清晰的、不撒谎的线。
  2. 没有它会怎样？如果 Core 假装弹窗就是安全，用户会带着虚假安全感在生产机上跑 bash——比"明说没有"更危险。
  3. 输入是什么？工具调用的意愿（来自模型）+ 执行环境的事实（来自 OS/容器）。
  4. 输出是什么？放行/拦截的决策（扩展层）+ 被物理约束的副作用（环境层）。
  5. 由谁控制？三层各自独立：Capability=工具作者；Authorization=用户与扩展；Sandbox=运行环境。
  6. 和前一概念的关系？第 8 课的 tool_call 钩子正是 Authorization 层的挂点——Core 提供接缝，不提供政策。
  7. Pi 在源码哪里实现？源码Trust：trust-manager.ts；接缝：tools/bash.ts；官方容器指南：docs/containerization.md；文档立场声明：docs/security.md。

五、这张图在整个体系中的位置

这是"Minimal Core"哲学的压力测试：安全这样的大事也敢外包？看完这一课你应该能自己论证：弹窗审批挡不住真正的破坏（容器才能），而 Core 假装安全比诚实更危险。下一课看接口层如何同样贯彻"核心最小"。
